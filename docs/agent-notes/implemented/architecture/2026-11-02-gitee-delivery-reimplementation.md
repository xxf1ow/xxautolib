# Agent Note: Gitee 版本化交付重做

Status: implemented

## 问题

下游需要从 Gitee 取得指定版本的预编译库，以同一套 CMake 入口完成下载、校验、依赖准备、链接和运行。生产端要支持三个原生平台，发布端要能复用一次已完成的构建而不重新编译；上传成功、版本选择正确和下游可消费是不同的结果，不能只用 CI 状态代表全部完成。

已有第四阶段实现没有通过用户验收。[构建运行 41416032231](https://github.com/xxf1ow/xxautolib/actions/runs/41416032231)及[发布运行 41416852464](https://github.com/xxf1ow/xxautolib/actions/runs/41416852464)均显示成功，发布报告 16 个资产上传且元数据提交已确认，但目标库的 eigen、queue、lz4、flann 均没有包级 `package.toml`。精确版本资产齐备不能弥补裸名选择入口缺失。构建、运输、发布输入与元数据更新需要有明确的完整交接，验收必须覆盖真实消费者。

## 决定

从第三阶段基线 `964fcfb2a3a4a0b329980271fafe69d5054eda89` 重新实现第四阶段。保留已验收的版本化构建、本地消费和 Git 元数据远端消费契约；建立“构建并验证安装结果 → 运输 → 独立打包 → Gitee 发布 → 下游消费”的闭环。重构围绕这条链路的实际职责，不整批回放旧第四阶段提交，也不默认保留旧实现的模块结构。

### 范围

[自定位消费入口与工具专用 CI](2026-11-03-entry-delivery-and-tool-only-ci.md)拥有已实现的入口安装与运输、发布副本目标注入、工具专用及严格 `all` 选择和可信 fork 来源。它部分替代本文的空列表、无包平台跳过、固定上游源码身份和发布二次筛选，完整交付原构建结果并增加不写 Git 元数据的入口附件；本文其余发布、权限、latest 和历史验证依据继续适用。

只发布到 Gitee，只支持 Windows x86_64、Linux x86_64、Linux aarch64 三个原生组合。沿用现有 `GITEE_REPOSITORY`、`GITEE_RELEASE_TAG` 和 secret `GITEE_TOKEN`，不增加同义配置。GitHub Actions 仍提供构建运行及 artifacts，不向 GitHub Release 发布二进制；已有 GitHub 消费协议和适配不扩大也不移除。基线中的旧源码 Release 上传和 GitHub Release 到 Gitee 的中转入口不再参与新交付链，避免保留第二条可被误触发的生产发布路径。

允许调整 CI 精确版本身份、独立根闭包验证、安装结果运输、发布端暂存打包和 Gitee 元数据管理，消除其中的重复解析和跨层推断。消费侧仅作使新交付协议成套成立的必要适配，包括允许根 LICENSE、统一工具摘要路径；不顺带重写消费模块或构建引擎，不重组全部配方，不新增版本范围、多版本同工程隔离、交叉编译、ABI 变体、发布事务或通用恢复服务。

全文件注释整理、默认操作及下载进度、哈希版本标识精简均为独立后续事项，本轮不实现，也不搬入暂存分支中的进度草稿。新改代码的非显然约束和错误诊断仍按项目规范表达。版本标识精简不等于截断完整性校验的 SHA256；长度和完整来源映射不在本文中决定。

### 组件与职责

| 组件 | 负责的事实与动作 | 不负责的动作 |
|---|---|---|
| builder | 解析配方、构建安装、记录精确身份和依赖及包级 latest，从安装副本修正路径并生成归档 | 不读取发布凭据，不调用托管平台 API |
| autolib-ci | 通过 builder 取得选择和闭包，驱动原生构建及逐根消费验证，运输已验证安装结果 | 不重复解析 TOML，不上传 Release，不另写归档算法 |
| 发布准备 | 核对原构建 run/attempt、提交和输入，调用该提交的 builder，形成明确发布输入 | 不编译三方库，不改取其他运行，不从当前分支猜版本 |
| Gitee 发布 Action | 检查或创建目标库，上传选定资产，由一个协调器提交摘要和 latest | 不扫描配方，不重新打包，不让上传 worker 各自写 Git |
| workflow | 提供事件、环境、权限、参数传递和同目标串行调度 | 不在 YAML 或 shell 中再维护包选择、摘要和 latest 算法 |
| CMake 与 importer | 引导宿主工具，检查 Git 元数据，准备精确包及依赖，加载 adapter | 不编译源码，不修补发布仓库，不从目录猜 latest |

上述职责可以在现有模块内保持清晰，不为每行增加一个服务或抽象层。CI 策略、构建语义和远端写入不混编为同一个工具；跨组件复用公共 CLI 或明确的数据输入，不复制其内部规则。

### 构建与运输契约

构建入口允许当前可信源码仓库普通分支的手动运行，包括 fork，拒绝 tag 和 PR 引用，检出事件对应提交。平台参数只包含三个既定组合及 all。模块未提供或空字符串仅交付工具和入口，严格 `all` 发现合资格版本，普通列表选择有效闭包；裸名读取源码包级 latest，精确引用严格匹配。没有自身或传递依赖 adapter 的根按既有规则过滤，全部过滤仍为所选平台交付工具和入口。

每个根的精确闭包独立验证，两个 Eigen 版本不能被放入同一次消费者 configure。共享精确依赖可复用构建结果，结果、目录和消费验证不能互相覆盖。平台无关包使用既有 any-any 身份并保留唯一 publisher；宿主 importer 按三个宿主分别生产，保持去符号的单程序 tar.xz 分发约定。

构建输出是已验证安装结果的 tar 运输封装，而不是 Release 上传结果。运输包含可信来源的仓库、分支、提交、run/attempt、原生平台、精确包及依赖身份、宿主 importer、原样入口及其验证摘要、包级 `package.toml` 和原始生产安装前缀，与原计划及结果对应。入口与原构建提交源码逐字节一致；可信仓库来自 GitHub 运行上下文，不采用运输自报身份。完整性按原计划所选平台检查；同包跨平台 latest 必须一致，即使精确构建也不能遗漏包级选择。零库运输不要求库候选。

每个平台的运输封装包含 UTF-8 JSON 清单 `transport.json`；`platform` 为该原生平台标识，`producer_prefix` 为该平台生产安装根的非空绝对路径字符串。Windows 保留生产端原始盘符及路径分隔符，由 JSON 转义反斜杠；Linux 保留以 `/` 开头的原始路径。归档成员和清单内的文件引用统一采用以运输根为基准的 `/` 相对路径。发布端按 `platform` 解释前缀，只将其作为文本修正输入，不用发布宿主的路径解析、绝对化或存在性检查改写它；Windows 前缀对应的 CMake 正斜杠表示由同一原始值派生，不另存第二份前缀事实。plan 固定其余字段和调用参数，使清单、计划、验证结果及 builder 输入逐项对应。

运输保留 Linux 工具可执行性和合法相对软链接；安全解包允许规范化权限，不要求逐位恢复生产访问策略。包内容、版本及依赖不得改变。运输前的安装树及发布端解包输入保持只读，解包只进入本次新建目录，拒绝越界路径、危险链接和不支持的对象，不清空已有数据来容纳输入。

原始生产前缀与当前输入目录是不同事实。打包从当前目录读取文件，只在副本中修正包内对原生产前缀的引用；不按解包目录反推原值，也不据原值访问生产机数据。Windows 原始路径和 CMake 路径表示、含空格路径、Linux 相对软链接需要定向验证，不通过恢复生产机绝对目录解决。

### 发布入口与发布输入

自动发布使用构建 workflow 的 `workflow_run.completed` 事件，在所选平台及汇总成功后启动一次，不由各 Matrix Job 分别启动；零库成功运行同样交付工具和入口。发布使用触发它的精确 run/attempt；手动发布显式指定原 run/attempt，可以不重新编译三方库而重跑。发布只接受当前可信源码仓库、预期 workflow 的成功运行，核对来源分支、提交、运输身份、原计划所选平台和验证结果。输入缺失、过期或不符就失败，不取最新运行、不混用其他运行、不回退旧缓存。

发布端检出原构建提交，使用该提交的 builder 从新路径中的安装输入暂存修正并打包。发布输入由明确选定的归档、对实际归档字节计算的摘要、精确包与平台身份、包级初始 latest 候选构成。选择、输入身份、包级候选的完整性及跨平台一致性在任何远端写入前检查；不要求为每个原文件另建一份重复身份清单。

发布准备与 Gitee 写入均使用 `ubuntu-24.04` runner；准备端通过原构建提交的 `src/autolib-builder/go-sdk.cmake` 获取该提交固定并校验的 Go SDK，以只读模块模式现场编译该提交的 builder，不依赖 runner 预装 Go，不运行运输输入中的其他平台 builder 或 importer。准备端提供 Git、CMake 和 Python 3.12；Gitee Action 的 Python 依赖按参考记录的 requirements 与 constraints 在隔离环境准备。Linux 发布端可按输入平台身份打包已安装文件，不执行 Windows 或 aarch64 的库和工具，也不在发布端重新编译三方库。

库使用 `<name>-<version>-<os>-<arch>.tar.zst`，通用库使用 any-any。工具分别为 `autolib-importer-windows-x86_64.exe.tar.xz`、`autolib-importer-linux-x86_64.tar.xz`、`autolib-importer-linux-aarch64.tar.xz`，归档顶层只有同名程序。摘要始终对应本次最终上传的实际字节，不因重新打包得到不同字节而复用旧摘要。

自动及手动 artifacts 发布完整交付原构建有效库、所选平台工具和唯一入口，没有二次包选择。目标仓库和 tag 必须显式提供，入口注入、并发组和上传使用同一实际目标，无上游默认值。入口接受路径、大小及 SHA256 检查，参与整体成功判定但不写 Git 摘要或 latest；入口失败时其他成功工具和库仍登记，整体失败。产物发布可附显式 latest 映射；无映射时只初始化缺失指针。latest-only 不读取构建资产，不上传工具或入口，不要求构建来源或平台齐备。

### Gitee 仓库生命周期

发布启动时固定目标仓库及 Release tag，使用现有变量和凭据。只有查询明确 404 才建库；认证、权限、网络和限流错误不得解释成不存在。Gitee 建库使用 `private=true`、`auto_init=true`，创建确认后重新查询默认分支与 `permission.push` 再克隆；没有合法分支就失败，不猜 master。结果不确定的创建不自动重放。

新库接受服务端首提交，但删除默认 `README.en.md`，完整覆盖 `README.md` 为规范项目说明，写入源码根 MIT LICENSE 和专用身份。README 和简介说明这是预编译产物发布仓库、源码来自 `https://github.com/xxf1ow/xxautolib`：源码仓库负责编译，发布流程分发指定构建的已有结果，发布库不编译三方源码。MIT 只覆盖项目自身内容，不替代各三方库许可。

初始化写入前确认固定目标缺失或是普通文件，不跟随软链接、不递归清理其他路径。提交并核对初始化树，确认 push 后才写 Release。身份文件为 `.autolib-repository.json`，值为 `{"type":"xxautolib-artifacts","schema":1,"upstream":"https://github.com/xxf1ow/xxautolib"}`；发布端和消费者共同核对其字段类型及值。

已有仓库缺身份、身份错误或混入非允许内容，在任何 Release 写入前拒绝；不能自动认领、清理或覆盖说明。已有合法库不要求补 LICENSE，不自动改 README、简介或可见性。新建库可以保持私有完成发布，由用户在匿名下游消费前自行公开，消费端不配置令牌。

每个发布任务只使用一份 Git 工作副本。每份输入快照检查一次身份与递归树，允许 README、LICENSE、身份、库包级选择及合法摘要路径，不遍扫历史或逐包克隆。上传与元数据提交复用该副本；同一 host、repository 的所有发布模式串行，不引入多写者合并、分布式锁或额外状态库。

### 元数据与 latest

Git 树不保存实际归档，归档放在同库固定 Release。库摘要路径为 `<name>/<version>/<完整归档名>.sha256`，工具摘要路径为 `autolib-importer/<工具归档名>.sha256`，不使用 tools。生产端摘要文件只含完整的 64 位小写十六进制 SHA256 和 LF 换行。库和工具的消费端统一忽略摘要文本首尾的空格、Tab、CR、LF，再严格校验剩余内容；不删除中间杂字符，不接受多份摘要或其他正文。正常文本空白由解析器处理，不按平台增加分支，也不要求用户修改 Git 换行配置。包级选择位于 `<name>/package.toml`，只含 `latest` 字符串；工具目录不是库包，不生成 latest。路径、身份、包内精确依赖及消费者查询必须成套一致，带 LICENSE 的合法仓库不能被入口拒绝。

首次初始化候选来自原构建安装结果随运输携带的 `package.toml`，不是发布分支当前的源码值，也不是最后上传版本、数字排序、SHA 排序或目录枚举。builder 将原构建提交的源码包级 `package.toml` 原样复制到安装根的 `<name>/package.toml`，不按正在构建的版本改写 latest；同次构建 Eigen 3.4.0 和 5.0.1 仍只有同一份包级候选，执行顺序不参与决议。裸名构建选择和安装候选来自同一原构建提交，发布端只读取运输快照。一个库只有一个版本也必须携带候选。候选缺失、格式非法或跨平台冲突属于发布输入错误，在远端写入前失败；不把 latest-only 的独立模式误判成缺少构建候选。

普通产物发布对本次至少有一个资产确认就绪的库包执行缺失初始化：上传成功或远端实际字节核对一致均算就绪。远端没有包级指针时写入候选，已有合法指针时原样保留。已有专用库首次增加一个库包适用同一规则；没有成功项的库包不因普通发布新增指针。候选可以指向本次未选择发布的版本，不隐式追加构建或上传；该版本缺对应产物时不能算裸名消费已通过。

显式 latest 更新优先于缺失初始化，可以覆盖已有合法选择，也可以没有任何构建或上传输入；不以产物存在、平台齐备或其他上传成功为前置条件。存在的非法指针或非普通文件明确失败，不借初始化覆盖。只发布旧版本、补平台或正常重跑，均不自动推进已有 latest。

远端 latest 不是发布完成标志。消费者裸名只读取指针，精确请求不重选版本，也不自动改写消费缓存 latest；缺包或摘要错误失败，不换版本。完整缓存不自动刷新，用户清理受影响缓存后才取得新选择，不新增后台更新或自动迁移。

### 上传、提交与重跑

附件更新只接收选定的本地资产。worker 返回本项上传、核对一致后跳过或失败，已确认就绪项的摘要和按上述规则选定的指针由协调器在结束后一次 commit/push；未选择的文件保持原样，不整树覆盖。部分更新失败仍登记就绪项，任务整体失败；元数据 push 未确认则报告失败，不把附件就绪当成完整交付。

正常重跑从精确原构建输入重新打包并计算摘要；单个附件更新及其重试固定同一份本地快照，不反复打包。同名附件下载后计算实际 SHA256，与本次快照一致才跳过，否则替换；同名、同大小或 Git 中已有相同摘要均不足以证明远端字节一致。跳过项也可补齐未登记的摘要与缺失 latest，不能将未核对的旧资产与本次摘要组合。重跑以启动时取得的合法库状态更新本次就绪项，不恢复旧附件、不维护发布进度数据库；原构建输入不可用时明确失败。

每次附件尝试从目标 Release 查询当前列表，定位唯一同名附件并核对内容。内容不同时沿用参考本体的先删后传顺序，确认删除后上传固定快照；没有同名附件则直接上传。多个同名附件作为歧义失败，不自动批量删除。查询失败不能视为缺失，未确认删除不能直接继续上传。复用上游 multipart 实现，不猜测直接覆盖 API 或依赖未经查证的冲突状态码。

临时网络或服务故障在退避后重新执行完整附件尝试，从查询观察远端事实，不盲目重发失败步骤；服务端已完成删除或上传但客户端丢失响应时，同一次发布即可继续补齐或核对后跳过。首次尝试之外最多重试十次，等待依次为 2、4、8、16、32、32、32、32、32、32 秒，累计等待 222 秒，另计请求耗时。附件只有这一层重试；认证、权限、非法输入及响应校验错误直接失败。现有发布 Job 的 60 分钟总超时仍生效，不保证长时间请求下必定跑满重试预算。建库和创建 Release 的未知结果仍失败，不自动重放。

先更新附件、后提交元数据可能形成短暂或持续的不一致；消费者遇到摘要不符直接失败，不使用旧快照或另一托管兜底。重试耗尽仍失败，不登记该项本次摘要；删除后持续上传失败可能使旧附件缺失，允许显式重跑但不回滚。每次退避及最终失败均保留脱敏诊断，不能把未知结果当作确认成功。不引入跨附件事务、备份回滚或不可变发行快照。

### 参考接入与重构约束

附件上传参考来源和许可证以仓库[UPSTREAM 记录](../../../../.github/actions/gitee-release/UPSTREAM.md)为准。先辨明基线中参考本体与已有项目定制，保留可直接复用的本体，只作必要接口适配，形成可验证基线后才作有依据的调整。不能以重新实现第四阶段为由重写上游附件上传细节或反复猜测 API。

Cent 用于借鉴已记录的 Header 认证、JSON 普通请求、服务端初始化与重新查询默认分支顺序；它不是完整的 Release 附件上传 Action，不能证明该环节可用。不同语言和接口的必要适配明确列出；不复制其源码、Contents 逐文件存储或额外恢复机制。参考读取、受控测试和真实托管结果分别说明，不能相互代替。

重构以消除职责冲突和重复事实为依据。包选择只由 builder 解析，平台编排归 CI，归档归 builder，远端写入及指针合并归发布端。不为维护旧实现结构增加兼容层，不为了缩短代码拆出通用框架；偏离本范围或出现需要改变前三阶段契约的设计问题时暂停受影响工作，交由用户决定。

### 数据保护与交接

本设计不授权重置 master、删除旧分支、清理本地安装或缓存、删除远端仓库或资产。当前 master 历史和暂存分支保留作核对；旧实现是参考，不作为新代码的自动来源。已有数据不要求迁移或旧接口兼容，但任何实际读写都须保护直接受影响内容。

整合采用新第四阶段整体替代旧实现，保留 master 历史与替代范围外的改动，不重放旧专用模块、测试或发布入口，不为旧第四阶段增加兼容层。用户手动验收通过后才进行本地整合；普通合并的自动结果不能代替替代范围核对。任务分支和暂存分支保留，不建 worktree，也不重写历史。

设计确认与本地提交不包含 Git push、PR、触发远端 CI 或实际建库、发布、故障注入授权。Git push 由用户执行；其他远端写入须取得对应对象、范围和阶段的明确授权。定向源码传输和验证沿用[开发指南](../../../development.md#远端构建与源码传输授权)中既定的机器、目录与数据保护要求；本机不编译，不取得或测试最低 CMake 的旧工具。

发布 CI 的完成范围止于上传结果、元数据提交及失败报告，不自动公开仓库，也不把私有库的匿名下载失败算作发布失败。用户公开目标仓库后，再由用户手动执行或明确授权触发三平台匿名消费验证，最后由用户验收；三平台消费不属于新建私有库后的必经发布 Job。实际触发前核对默认分支上的 `workflow_run` 入口及其目标，不能假定事件执行任务分支的新 workflow；旧自动入口可能响应时先停止触发，不能为取得自动触发证据而提前合并。

## 备选方案

**继续在当前 master 上增量修复。** 可以复用现成实现并减少重新开发量，但未验收版本的构建、运输和发布改动已经交叉累积，逐处补洞难以建立清晰的交接基线。选择保留旧实现作参考，从第三阶段重新实现第四阶段，不据此断言所有旧代码都应丢弃。

**重新实现整个构建和消费系统。** 能统一更多结构，但会重新打开已验收的前三阶段，放大范围和验证成本。只重构第四阶段职责与必要接口，已验收契约不动。

**继续经 GitHub Release 中转到 Gitee。** 可以沿用旧镜像输入，却增加一次二进制上传和第二个发布结果，并与本阶段仅 Gitee 的要求冲突。构建只交付运输 artifacts，独立发布直接生成 Gitee 资产。

**只有显式 latest-only，没有首次初始化。** 能保持更新动作完全独立，但正常首次自动发布仍会缺少裸名消费入口。选择从构建输入初始化缺失指针，后续已有值只由显式更新改变。

**每次发布都同步源码 latest。** 能自动追随源码，却会在补旧版本、补平台或重跑时覆盖已有选择。只初始化缺失项，已有值不自动推进。

**发布事务、自动回滚或持久化进度。** 可以减少某些失败窗口，但会扩大状态和恢复职责。当前接受消费者失败退出、保留成功项及明确重跑，不为重做增加通用恢复系统。

## 验证范围

交付验证针对同一版源码，平台仅 Windows x86_64、Linux x86_64、Linux aarch64，真实发布目标仅 Gitee。代表集为 `eigen@3.4.0`、`eigen@5.0.1`、queue、lz4、flann，两个 Eigen 版本各自使用独立消费者。代表集通过不等于全部第三方库全量编译通过；空列表发现和过滤由定向测试检查，不默认重编全库。以下是各项验证的判定规则，实际证据及未记录专项见下一节。

1. 构建和交接：精确根及依赖身份、运行及 attempt、原始前缀与包级 latest 完整运输；发布在不同路径从输入打包，原安装和解包输入不变。Linux 执行权限及相对软链接、Windows 路径与含空格目录均有对应证据；损坏、缺失或身份错误的输入在远端写入前失败，不误取其他运行。
2. 仓库生命周期：明确不存在才建私有库，初始化 README、简介、LICENSE 和身份符合本文要求；已有非专用库在任何 Release 写入前拒绝，合法库复用不覆盖无关记录。真实新库须由用户自行准备或授权目标，不以删除当前库取得测试条件；用户公开后才能匿名消费。
3. 资产与元数据：三个宿主工具、各平台库及唯一 any-any 资产正确；实际下载字节的完整 SHA256 与 Git 摘要一致，工具摘要位于 autolib-importer。所有所选并有上传成功项的库包均有合法包级 `package.toml`，其中包含有两个版本的 eigen 和仅一个版本的库；工具没有包级 latest。
4. latest 生命周期：首次自动发布从构建候选补齐缺失指针；补旧版本、补平台和重跑不改已有合法值；产物发布可同时显式更新 latest，显式 latest-only 不需要构建或附件，可独立改变指针。两个 Eigen 版本共用原构建提交的包级候选，不随安装顺序改变；初始候选缺失、非法或本次所选平台间冲突不得被成功流程掩盖，部分失败不能为全无成功项的包隐式初始化。
5. 三平台真实消费：发布报告形成且用户公开目标库后，每个平台从空入口缓存取得已发布 importer，经公共 `autolib_import` 分别完成两个 Eigen 版本及代表集的 configure/build/运行。另以裸名 eigen、queue、lz4、flann 验证实际版本与远端指针一致，不只测显式版本。FLANN 自动取得包内记录的精确 LZ4；合法元数据包含 LICENSE 时不能再被拒绝。该验证由用户手动执行或另行授权触发，发布 CI 成功不能替代。
6. 缓存：完整有效工具和精确闭包在 Git/HTTPS 不可达时仍能 configure/build/运行；严格禁止缺输入时联网使用内置地址为空的入口，不使用旧来源变量。完整缓存不追随远端 latest，新的空缓存按新指针选择。链接和动态加载来自对应缓存，不能由生产树或系统同名库冒充。
7. 失败与重跑：受控覆盖部分上传失败、元数据 push 失败及相同原构建输入重跑，失败报告准确且无错误成功登记。真实托管验收正常同名重跑及上述两类失败后的显式重跑；故障注入须另获目标及数据保护授权，未授权或未执行的必需场景保持未完成，不用受控测试冒充。
8. 发布边界：不向 GitHub Release 上传、不经旧同步入口重复发布、不注入 GitHub 目标写令牌。workflow 和工具拒绝不允许的引用与 host，同 Gitee 目标串行；所选平台及汇总全部成功后只启动一次自动发布，任一失败不启动写入。单平台完整输入可以发布，缺少原计划选定平台的输入必须失败，不能将单平台发布误判为缺少三平台。

先取得构建运输、打包和发布端的定向证据，再完成真实托管及下游消费；阶段末验证本阶段及受影响接口，复用未失效的前三阶段证据。文档事实与代码同步，使用 Agent Note、项目文档校验和差异空白检查。最终由用户按上述可观察结果验收；CI 绿灯、上传响应、通过数量、审查或合并均不能替代，任何缺口须显式列出。

## 影响

包级 latest 独立于资产发布，可以指向尚无所需平台产物的版本。缺失初始化只保证选择确定，不保证裸名消费已成立；真实消费必须单独验证。已有 latest 不会自动跟随源码，用户需要显式更新。

附件替换与 Git 提交不是原子操作，部分上传或 push 失败后可能保留不一致，消费者校验失败而不是自动回退。任务需明确失败并允许显式重跑，不承诺跨包或跨平台快照一致性。Git 与 Gitee 网络的可用性不是本项目保证。

Gitee 自动建库保持私有，发布成功不代表匿名下游可访问；用户公开是匿名消费前置条件。SHA256 只核对记录与字节一致，不认证发布者；元数据写入者、importer 和包内 CMake 均须可信。公开二进制沿用既有平台 ABI 基准，不能据结构一致承诺任意本地编译器或运行库兼容。

从第三阶段重做需要重新取得第四阶段受影响证据，不能用旧版成功状态抵扣。限制重构范围并保留参考可以控制成本，但不保证旧数据与新实现自动兼容；实际整合方式必须在验收后明确，不能擅自重写用户历史或删除既有成果。
