# Agent Note: Gitee 版本化交付重做

Status: implemented

## 问题

下游需要从 Gitee 取得指定版本的预编译库，以同一套 CMake 入口完成下载、校验、依赖准备、链接和运行。生产端要支持三个原生平台，发布端要能复用一次已完成的构建而不重新编译；上传成功、版本选择正确和下游可消费是不同的结果，不能只用 CI 状态代表全部完成。

已有第四阶段实现没有通过用户验收。[构建运行 41416032231](https://github.com/xxf1ow/xxautolib/actions/runs/41416032231)及[发布运行 41416852464](https://github.com/xxf1ow/xxautolib/actions/runs/41416852464)均显示成功，发布报告 16 个资产上传且元数据提交已确认，但目标库的 eigen、queue、lz4、flann 均没有包级 `package.toml`。精确版本资产齐备不能弥补裸名选择入口缺失。构建、运输、发布输入与元数据更新需要有明确的完整交接，验收必须覆盖真实消费者。

## 决定

从第三阶段基线 `964fcfb2a3a4a0b329980271fafe69d5054eda89` 重新实现第四阶段。保留已验收的版本化构建、本地消费和 Git 元数据远端消费契约；建立“构建并验证安装结果 → 原生 CI 打包及运输 → 校验成品 → Gitee 发布 → 下游消费”的闭环。重构围绕这条链路的实际职责，不整批回放旧第四阶段提交，也不默认保留旧实现的模块结构。

### 范围

[自定位消费入口与工具专用 CI](2026-11-03-entry-delivery-and-tool-only-ci.md)拥有已实现的入口安装与运输、发布副本目标注入、工具专用及严格 `all` 选择和可信 fork 来源。它部分替代本文的空列表、无包平台跳过、固定上游源码身份和发布二次筛选，完整交付原构建结果并增加不写 Git 元数据的入口附件；本文其余发布、权限、latest 和历史验证依据继续适用。

Gitee 是下游发布目标，GitHub Release 保存跨运行缓存。当前平台与自动同步由缓存记录及 Darwin 扩展记录拥有；历史三平台交付证据不能代替新四平台缓存恢复。目标仍使用 `GITEE_REPOSITORY`、`GITEE_RELEASE_TAG` 和 `GITEE_TOKEN`，没有同义配置或第二条生产发布入口。
允许调整 CI 精确版本身份、独立根闭包验证、CI 成品运输、原生安装副本打包和 Gitee 元数据管理，消除其中的重复解析和跨层推断。消费侧仅作使新交付协议成套成立的必要适配，包括允许根 LICENSE、统一工具摘要路径；不顺带重写消费模块或构建引擎，不重组全部配方，不新增版本范围、多版本同工程隔离、交叉编译、ABI 变体、发布事务或通用恢复服务。

全文件注释整理、默认操作及下载进度、哈希版本标识精简均为独立后续事项，本轮不实现，也不搬入暂存分支中的进度草稿。新改代码的非显然约束和错误诊断仍按项目规范表达。版本标识精简不等于截断完整性校验的 SHA256；长度和完整来源映射不在本文中决定。

### 组件与职责

| 组件 | 负责的事实与动作 | 不负责的动作 |
|---|---|---|
| builder | 解析配方、构建安装、记录精确身份和依赖及包级 latest，从安装副本修正路径并生成归档 | 不读取发布凭据，不调用托管平台 API |
| autolib-ci | 通过 builder 取得源码事实及闭包，驱动原生验证、打包和缓存访问 | 不重复解析 TOML，不另写归档算法 |
| 独立同步 | 固定最新源码快照，核对缓存指纹、来源及实际下载字节 | 不编译三方库，不重新打包 |
| Gitee 发布 Action | 检查或创建目标库，上传选定资产，由一个协调器提交摘要和 latest | 不扫描配方，不重新打包，不让上传 worker 各自写 Git |
| workflow | 提供事件、环境、权限、参数传递和同目标串行调度 | 不在 YAML 或 shell 中再维护包选择、摘要和 latest 算法 |
| CMake 与 importer | 引导宿主工具，检查 Git 元数据，准备精确包及依赖，加载 adapter | 不编译源码，不修补发布仓库，不从目录猜 latest |

上述职责可以在现有模块内保持清晰，不为每行增加一个服务或抽象层。CI 策略、构建语义和远端写入不混编为同一个工具；跨组件复用公共 CLI 或明确的数据输入，不复制其内部规则。

### 构建与同步交接

构建以可信普通分支的事件提交生产，版本化库、唯一 any-any publisher、宿主 importer 和入口仍须原生验证。builder 生成最终 `.tar.zst` 与单程序 `.tar.xz`；独立同步根据最新分支快照及相关输入指纹复用跨 run 成品，不要求原计划所有平台同时成功。入口只随实际更新的 importer 交付，工具摘要等待入口成功；latest-only 使用源码事实校验显式映射，不读取缓存或上传入口。

同步的源码读取、删除规则、逐项立即提交及 Git 摘要信任由上述缓存记录拥有；这里不保留旧 transport/publication 格式或按成功 run/attempt 选择 Artifacts 的入口。安装副本修正、执行权限及合法相对软链接仍归 builder，原安装与成品输入保持只读。

### Gitee 仓库生命周期

发布启动时固定目标仓库及 Release tag，使用现有变量和凭据。只有查询明确 404 才建库；认证、权限、网络和限流错误不得解释成不存在。Gitee 建库使用 `private=true`、`auto_init=true`，创建确认后重新查询默认分支与 `permission.push` 再克隆；没有合法分支就失败，不猜 master。结果不确定的创建不自动重放。

新库接受服务端首提交，但删除默认 `README.en.md`，完整覆盖 `README.md` 为规范项目说明，写入源码根 MIT LICENSE 和专用身份。README 和简介说明这是预编译产物发布仓库、源码来自 `https://github.com/xxf1ow/xxautolib`：源码仓库负责编译，发布流程分发指定构建的已有结果，发布库不编译三方源码。MIT 只覆盖项目自身内容，不替代各三方库许可。

初始化写入前确认固定目标缺失或是普通文件，不跟随软链接、不递归清理其他路径。提交并核对初始化树，确认 push 后才写 Release。身份文件 `.autolib-repository.json` 使用整数 schema 2；发布端和消费者共同核对字段类型及固定值，格式由上述 JSON 记录拥有。

已有仓库缺身份、身份错误或混入非允许内容，在任何 Release 写入前拒绝；不能自动认领、清理或覆盖说明。已有合法库不要求补 LICENSE，不自动改 README、简介或可见性。新建库可以保持私有完成发布，由用户在匿名下游消费前自行公开，消费端不配置令牌。

每个发布任务只使用一份 Git 工作副本。每份输入快照检查一次身份与递归树，允许 README、LICENSE、身份、库包级选择及合法摘要路径，不遍扫历史或逐包克隆。上传与元数据提交复用该副本；同一 host、repository 的所有发布模式串行，不引入多写者合并、分布式锁或额外状态库。

### 元数据与 latest

Git 树不保存实际归档。库记录位于 `<name>/<version>/<完整归档名>.json`，工具记录位于 `autolib-importer/<工具归档名>.json`，只含 sha256、size 和有序 urls；格式和校验由上述 JSON 记录拥有。包级选择位于 `<name>/package.toml`，只含 `latest` 字符串；工具目录不生成 latest。Windows 工具保留 `.exe.tar.xz` 命名，合法树允许 LICENSE。

首次初始化保留原构建记录的包级 latest 候选；原候选从源码删除时，按当前源码合法 latest 修复。已有合法值不因补旧版本、补平台或无变化重跑自动推进；显式 latest-only 仍优先，删除修复在同包提交中完成。源码合法不保证全平台资产齐备，缺失平台须在覆盖报告中体现。具体规则由缓存与独立同步记录拥有。

远端 latest 不是发布完成标志。消费者裸名只读取指针，精确请求不重选版本，也不自动改写消费缓存 latest；缺包或摘要错误失败，不换版本。完整缓存不自动刷新，用户清理受影响缓存后才取得新选择，不新增后台更新或自动迁移。

### 上传、提交与重跑

Gitee Git JSON 是唯一跳过依据，三个字段语义相同时不下载归档或核对附件。普通变化项按需下载有效缓存、校验字节、删除同名附件后上传；每项即时在共用 Git 锁中 commit/push 并确认。超限项只确认 GitHub 地址 JSON，再清理同名 Gitee 旧附件。未知 push 结果停止后续写入，不 rebase 或强推。

GitHub 缓存先就绪，必要的 Gitee 附件上传后才确认 JSON。替换与提交之间可能不一致，消费者拒绝不匹配字节并按记录尝试备用来源；全部来源失效则失败。删除后持续上传失败可能使附件缺失，下次显式重跑，不回滚。每次退避及最终失败保留脱敏诊断，不引入跨附件事务、备份回滚或不可变发行快照。

### 参考接入与重构约束

附件上传参考来源和许可证以仓库[UPSTREAM 记录](../../../../.github/actions/gitee-release/UPSTREAM.md)为准。先辨明基线中参考本体与已有项目定制，保留可直接复用的本体，只作必要接口适配，形成可验证基线后才作有依据的调整。不能以重新实现第四阶段为由重写上游附件上传细节或反复猜测 API。

Cent 用于借鉴已记录的 Header 认证、JSON 普通请求、服务端初始化与重新查询默认分支顺序；它不是完整的 Release 附件上传 Action，不能证明该环节可用。不同语言和接口的必要适配明确列出；不复制其源码、Contents 逐文件存储或额外恢复机制。参考读取、受控测试和真实托管结果分别说明，不能相互代替。

重构以消除职责冲突和重复事实为依据。包选择只由 builder 解析，平台编排归 CI，归档归 builder，远端写入及指针合并归发布端。不为维护旧实现结构增加兼容层，不为了缩短代码拆出通用框架；偏离本范围或出现需要改变前三阶段契约的设计问题时暂停受影响工作，交由用户决定。

### 数据保护与交接

本设计不授权重置 master、删除旧分支、清理本地安装或缓存、删除远端仓库或资产。当前 master 历史和暂存分支保留作核对；旧实现是参考，不作为新代码的自动来源。已有数据不要求迁移或旧接口兼容，但任何实际读写都须保护直接受影响内容。

整合采用新第四阶段整体替代旧实现，保留 master 历史与替代范围外的改动，不重放旧专用模块、测试或发布入口，不为旧第四阶段增加兼容层。用户手动验收通过后才进行本地整合；普通合并的自动结果不能代替替代范围核对。任务分支和暂存分支保留，不建 worktree，也不重写历史。

设计确认与本地提交不包含 Git push、PR、触发远端 CI 或实际建库、发布、故障注入授权。Git push 由用户执行；其他远端写入须取得对应对象、范围和阶段的明确授权。定向源码传输和验证沿用[开发指南](../../../development.md#远端构建与源码传输授权)中既定的机器、目录与数据保护要求；本机编译在 `build/` 隔离目录进行，最多四线程，Go 只使用仓库 SDK；不取得或测试最低 CMake 的旧工具。

发布 CI 的完成范围止于上传结果、元数据提交及失败报告，不自动公开仓库，也不把私有库的匿名下载失败算作发布失败。用户公开目标仓库后，再由用户手动执行或明确授权触发三平台匿名消费验证，最后由用户验收；三平台消费不属于新建私有库后的必经发布 Job。实际触发前核对默认分支上的 `workflow_run` 入口及其目标，不能假定事件执行任务分支的新 workflow；旧自动入口可能响应时先停止触发，不能为取得自动触发证据而提前合并。

## 备选方案

**继续在当前 master 上增量修复。** 可以复用现成实现并减少重新开发量，但未验收版本的构建、运输和发布改动已经交叉累积，逐处补洞难以建立清晰的交接基线。选择保留旧实现作参考，从第三阶段重新实现第四阶段，不据此断言所有旧代码都应丢弃。

**重新实现整个构建和消费系统。** 能统一更多结构，但会重新打开已验收的前三阶段，放大范围和验证成本。只重构第四阶段职责与必要接口，已验收契约不动。

**继续经 GitHub Release 中转到 Gitee。** 可以沿用旧镜像输入，却增加一次二进制上传和第二个发布结果，并与本阶段仅 Gitee 的要求冲突。构建只交付运输 artifacts，独立发布直接分发已生成的 Gitee 资产。

**只有显式 latest-only，没有首次初始化。** 能保持更新动作完全独立，但正常首次自动发布仍会缺少裸名消费入口。选择从构建输入初始化缺失指针，后续已有值只由显式更新改变。

**每次发布都同步源码 latest。** 能自动追随源码，却会在补旧版本、补平台或重跑时覆盖已有选择。只初始化缺失项，已有值不自动推进。

**发布事务、自动回滚或持久化进度。** 可以减少某些失败窗口，但会扩大状态和恢复职责。当前接受消费者失败退出、保留成功项及明确重跑，不为重做增加通用恢复系统。

## 历史验收范围

交付验证针对同一版源码，平台仅 Windows x86_64、Linux x86_64、Linux aarch64，真实发布目标仅 Gitee。代表集为 `eigen@3.4.0`、`eigen@5.0.1`、queue、lz4、flann，两个 Eigen 版本各自使用独立消费者。代表集通过不等于全部第三方库全量编译通过；空列表发现和过滤由定向测试检查，不默认重编全库。以下保留该历史交付阶段的判定规则，当前同步按上述新记录验证；实际证据及未记录专项见下一节。

1. 构建和交接：精确根及依赖身份、运行及 attempt、成品与包级 latest 完整运输；发布原样分发并验证实际字节，原安装和解包输入不变。Linux 执行权限及相对软链接、Windows 路径与含空格目录均有对应证据；损坏、缺失或身份错误的输入在远端写入前失败，不误取其他运行。
2. 仓库生命周期：明确不存在才建私有库，初始化 README、简介、LICENSE 和身份符合本文要求；已有非专用库在任何 Release 写入前拒绝，合法库复用不覆盖无关记录。真实新库须由用户自行准备或授权目标，不以删除当前库取得测试条件；用户公开后才能匿名消费。
3. 资产与元数据：三个宿主工具、各平台库及唯一 any-any 资产正确；实际下载字节的完整 SHA256 与 Git 摘要一致，工具摘要位于 autolib-importer。所有所选并有上传成功项的库包均有合法包级 `package.toml`，其中包含有两个版本的 eigen 和仅一个版本的库；工具没有包级 latest。
4. latest 生命周期：首次自动发布从构建候选补齐缺失指针；补旧版本、补平台和重跑不改已有合法值；产物发布可同时显式更新 latest，显式 latest-only 不需要构建或附件，可独立改变指针。两个 Eigen 版本共用原构建提交的包级候选，不随安装顺序改变；初始候选缺失、非法或本次所选平台间冲突不得被成功流程掩盖，部分失败不能为全无成功项的包隐式初始化。

## 影响

包级 latest 独立于资产发布，可以指向尚无所需平台产物的版本。缺失初始化只保证选择确定，不保证裸名消费已成立；真实消费必须单独验证。已有 latest 不会自动跟随源码，用户需要显式更新。

附件替换与 Git 提交不是原子操作，部分上传或 push 失败后可能保留不一致；消费者拒绝错误字节并按 JSON 换源，全部来源都不匹配时明确失败。任务允许显式重跑，不承诺跨包或跨平台快照一致性。

Gitee 自动建库保持私有，发布成功不代表匿名下游可访问；用户公开是匿名消费前置条件。SHA256 只核对记录与字节一致，不认证发布者；元数据写入者、importer 和包内 CMake 均须可信。公开二进制沿用既有平台 ABI 基准，不能据结构一致承诺任意本地编译器或运行库兼容。

从第三阶段重做需要重新取得第四阶段受影响证据，不能用旧版成功状态抵扣。限制重构范围并保留参考可以控制成本，但不保证旧数据与新实现自动兼容；实际整合方式必须在验收后明确，不能擅自重写用户历史或删除既有成果。
