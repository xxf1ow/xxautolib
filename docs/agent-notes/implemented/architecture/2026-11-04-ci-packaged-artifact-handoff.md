# Agent Note: CI 成品归档交接与重复发布

Status: implemented

## 问题

用户需要反复发布同一次成功构建，补齐网络失败项，同时跳过远端已存在且字节相同的附件。发布成功不能使未变化的库和工具产生新的摘要或无意义的元数据提交。

若构建只运输安装树，发布准备就需要重新调用 builder 打包。builder 复制文件到暂存目录时产生新的修改时间，归档保留这些时间；同一构建输入在不同发布运行中会生成不同字节。因此，即使上传端正确比较实际 SHA256，重新打包仍会导致附件替换。固定单次上传快照只能保证一次运行内重试的输入稳定，不能保证跨发布运行稳定。

本决定将最终归档作为 CI 与发布准备之间的交接对象，不扩大为全局可复现构建、发布事务或恢复服务。

## 决定

CI 在原生平台完成编译、安装和消费验证后，调用同提交的 `builder package`，保存最终库归档与宿主 importer 归档。发布端只校验并分发这些归档，不生成归档。

本地构建仍只完成安装；需要归档时手动调用同一个 `builder package`。CI workflow 自动调用该命令，不给 builder 增加 CI 环境判断、自动打包开关或第二套归档算法。

### 归属与不变项

现行 CI 逐项保存 Release 缓存，由[Release 成品缓存与独立 Gitee 精确同步](../../implemented/architecture/2026-11-09-release-cache-and-independent-gitee-sync.md)拥有；本记录保留 builder 生成最终字节、安全归档和避免发布端重打包的理由及历史验收。按成功 run/attempt 运输成品的生产入口及专属校验已退役，不再提供历史 Artifacts 发布兜底。

本文部分替代 [Gitee 版本化交付重做](../../implemented/architecture/2026-11-02-gitee-delivery-reimplementation.md)中安装树运输、发布端暂存修正及重打包的职责，部分替代[自定位消费入口与工具专用 CI](../../implemented/architecture/2026-11-03-entry-delivery-and-tool-only-ci.md)中对应交接描述。两份记录的包选择、精确依赖、资格过滤、入口消费、可信来源、latest、上传、权限及历史证据继续适用，不整体归档。

builder 继续拥有安装描述、暂存副本、路径修正、安全归档和本地打包命令。CI 按原计划驱动构建、验证和打包，Release 缓存及独立同步负责来源、实际字节与入口核对。

`modules` 为空、为 `all`、为具体包列表的规则保持不变，三种情况都包含各所选平台的宿主 importer 和入口。CI 不在打包阶段重新选择库、重新解析依赖或追加库。平台无关库仍只由原计划指定的 publisher 交付一份；其他平台仍完成各自原有的安装及消费验证。

### CI 打包与完成条件

每项在本平台消费验证成功后，使用该次安装结果和该提交的 builder 执行打包并立即入库。精确库参数取自计划中可发布的包及版本；平台无关库按既有 publisher 规则过滤，宿主工具始终打包。库集合为空时仍生成工具归档和记录中的原始入口，不要求库候选。

打包输出进入本次工作目录中的独立目录，不覆盖生产安装树。路径修正只发生在 builder 的暂存副本内，沿用现有输出范围、输入只读、包身份、相对软链接和权限保护；生产安装根可作为打包时的前缀输入，但不作为发布协议字段运输。

CI 对最终归档计算实际大小和 SHA256，并将其与精确身份绑定到交付记录。打包、摘要或入库失败使该项失败并阻断依赖者，无关项继续；最终汇总仍失败，已入库合格项不失效。整体成功构建自动触发独立同步；手动同步无需原运行整体成功。

### 成品交接与范围

CI 缓存保存 builder 生成的最终字节，记录绑定来源、精确身份和实际归档 ID；发布端不解开内部归档、不修正生产路径、不重新打包。包内正确性由构建验证、安全归档和生产到消费闭环负责。缓存和独立同步的来源、失败恢复、入口关联及摘要规则由上述新记录拥有，不能恢复整次成功 run 的运输门槛。

归档稳定性只承诺同一份成品逐字节复用；重新构建、重新打包或改变工具版本仍可能生成不同字节。本决定不扩大为全局可复现构建、跨资产事务、消费者快照或恢复服务。上游 multipart、本地打包接口、合法相对软链接、执行权限和消费端安全解包保持各自职责，实际远端操作仍须明确授权。

## 备选方案

**保留发布端打包，规范全部归档元数据。** 统一时间戳、所有者等可解决本次摘要变化，改动可以较小。但发布仍需取得并编译原 builder、解释跨平台安装前缀和重新生成最终字节，构建成功也不代表成品已生成。选择一次构建交付成品，直接消除重复发布重新打包的原因；不同时捆绑独立构建间的全局可复现要求。

**根据 CI 环境自动打包，同时保留发布端重打包兜底。** 可以同时读取两种运输格式，但会保留两套交接规则和重复生成字节的路径，还使 builder 行为取决于运行环境。选择 workflow 显式调用同一打包命令，并拒绝旧输入。

## 影响

打包失败表现为构建失败，原生 job 包含打包耗时；每个平台只执行一次交付所需的打包，不另加一套构建。不同原生平台的打包能力通过对应 workflow 验证，发布 Linux 宿主不代替 Windows 打包。

稳定性承诺仅覆盖同一构建保留的同一份成品。重新构建、重新打包或改变工具版本可能生成不同字节；同一源码 SHA 不能替代成品及其原生产身份。缓存缺失时需要重新构建，不能从旧安装树恢复同一份成品。

独立同步不解开内部成品，包内正确性由原构建验证、既有 builder 保护及生产到消费的联动验证负责。成品摘要用于发现交接损坏，不是对不可信构建的独立安全认证；可信源码仓库、workflow 和运行来源检查必须保留。

部分成功与无回滚语义保持不变，远端并发人工修改仍可能影响重复发布结果；本设计不承诺跨资产原子发布，也不因摘要稳定而扩建全局事务或持续协调服务。
