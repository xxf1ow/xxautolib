# Agent Note: CI 成品归档交接与重复发布

Status: implemented

## 问题

用户需要反复发布同一次成功构建，补齐网络失败项，同时跳过远端已存在且字节相同的附件。发布成功不能使未变化的库和工具产生新的摘要或无意义的元数据提交。

若构建只运输安装树，发布准备就需要重新调用 builder 打包。builder 复制文件到暂存目录时产生新的修改时间，归档保留这些时间；同一构建输入在不同发布运行中会生成不同字节。因此，即使上传端正确比较实际 SHA256，重新打包仍会导致附件替换。固定单次上传快照只能保证一次运行内重试的输入稳定，不能保证跨发布运行稳定。

本决定将最终归档作为 CI 与发布准备之间的交接对象，不扩大为全局可复现构建、发布事务或恢复服务。

## 决定

CI 在原生平台完成编译、安装和消费验证后，调用同提交的 `builder package`，保存最终库归档与宿主 importer 归档。发布端只校验并分发这些归档，不生成归档。

```text
构建时选择一次 → 编译安装 → 消费验证 → builder 打包 → 保存成品 Release 缓存
                                                         ↓
历史手动选择精确 run/attempt → 校验全部成品 → 注入入口上传副本 → 核对/跳过/替换 → 登记元数据
```

本地构建仍只完成安装；需要归档时手动调用同一个 `builder package`。CI workflow 自动调用该命令，不给 builder 增加 CI 环境判断、自动打包开关或第二套归档算法。

### 归属与不变项

现行 CI 逐项保存 Release 缓存，由[Release 成品缓存与独立 Gitee 精确同步](../../proposed/architecture/2026-11-09-release-cache-and-independent-gitee-sync.md)拥有；本记录继续拥有原样成品分发、安全运输格式及历史手动发布。构建 workflow 不生成成品 Artifacts，以下运输协议供仍持有原格式 Artifacts 的历史成功 run 手动发布使用，不作为新缓存的输入。

本文部分替代 [Gitee 版本化交付重做](../../implemented/architecture/2026-11-02-gitee-delivery-reimplementation.md)中安装树运输、发布端暂存修正及重打包的职责，部分替代[自定位消费入口与工具专用 CI](../../implemented/architecture/2026-11-03-entry-delivery-and-tool-only-ci.md)中对应交接描述。两份记录的包选择、精确依赖、资格过滤、入口消费、可信来源、latest、上传、权限及历史证据继续适用，不整体归档。

builder 继续拥有安装描述、暂存副本、路径修正、安全归档和本地打包命令。CI 负责按原计划驱动构建、验证、打包与运输；发布准备负责可信输入、完整集合、实际字节和入口注入检查；Gitee Action 负责附件协调及成功项元数据登记。

`modules` 为空、为 `all`、为具体包列表的规则保持不变，三种情况都包含各所选平台的宿主 importer 和入口。CI 不在打包阶段重新选择库、重新解析依赖或追加库。平台无关库仍只由原计划指定的 publisher 交付一份；其他平台仍完成各自原有的安装及消费验证。

### CI 打包与完成条件

每项在本平台消费验证成功后，使用该次安装结果和该提交的 builder 执行打包并立即入库。精确库参数取自计划中可发布的包及版本；平台无关库按既有 publisher 规则过滤，宿主工具始终打包。库集合为空时仍生成工具归档和原样入口运输内容，不要求库候选。

打包输出进入本次工作目录中的独立目录，不覆盖生产安装树。路径修正只发生在 builder 的暂存副本内，沿用现有输出范围、输入只读、包身份、相对软链接和权限保护；生产安装根可作为打包时的前缀输入，但不作为发布协议字段运输。

CI 对最终归档计算实际大小和 SHA256，并将其与精确身份绑定到交付记录。打包、摘要或入库失败使该项失败并阻断依赖者，无关项继续；最终汇总仍失败，已入库合格项不失效。自动 Gitee 发布关闭，历史手动发布仍要求原运行全部平台及汇总成功。

### 成品运输协议

计划 artifact 保留 `ci-plan-<run_id>-<attempt>`。历史平台成品 artifact 使用 `ci-package-<run_id>-<attempt>-<platform>`，其中仍只有一个 `transport.tar`，用于保留清单及成品的关联。验证结果 artifact 的既有职责不变。

`transport.tar` 中保留 `plan.json`、`result.json`、`transport.json`，并使用以下固定内容布局：

| 路径 | 内容 |
| --- | --- |
| `assets/<完整归档名>` | builder 已生成的库 `.tar.zst` 或 importer `.tar.xz`，逐字节运输 |
| `candidates/<包名>/package.toml` | 原构建安装中的包级 latest 候选，按包名唯一，不按构建版本改写 |
| `autolib.cmake` | 已验证、与原提交源码逐字节一致的安装入口 |

运输清单保留 `run`、`platform`、全部已验证 `packages` 的精确身份、依赖和 `publish` 规则，以及 `entry` 路径；使用 `assets` 表达成品，不含 `producer_prefix` 或裸 importer 路径。每项资产使用现有发布清单的 `kind`、`name`、`path`、`size`、`sha256` 表达：库带 `package` 精确身份，工具带 `platform`。`entry` 固定为 `autolib.cmake`，其验证摘要继续由 `result.entry` 承载，不另建一份入口验证状态。

每个平台必须恰好运输一个对应宿主的 importer 归档，以及该平台 `publish=true` 的全部库归档；`publish=false` 的平台无关库不重复运输归档。候选仍覆盖该平台计划中的全部库包名，以保留跨平台一致性检查。无库时 `packages`、库资产和候选集合均为空，不省略工具和入口。

归档名称、包身份、平台、数量及唯一性从原计划核对，不能信任运输清单自报的交付集合。运输成员只允许必要目录和普通文件，不包含安装树、裸工具、builder、软链接或硬链接；内部库归档中的合法软链接和执行权限由 builder 保留。builder 本地输出的 `.sha256` sidecar 不重复运输或上传，实际字节摘要由运输清单承载，本地命令输出接口保持不变。

### 发布准备

发布继续依据可信 GitHub 上下文选择当前源码仓库中指定的成功 run/attempt，核对预期 workflow、分支、提交、artifact 来源及过期状态。fork 使用自己的运行上下文，不恢复固定上游仓库限制。缺少原计划中的任一平台、混用运行、额外或重复交付项均拒绝，不取最新运行、不降级为部分平台发布。

准备端将外层运输封装安全解包到本次新目录，拒绝越界路径、重复成员、链接及不支持对象；输入及原安装结果保持只读，不清空已有目录。准备端核对计划、运行、平台、验证结果、包集合及候选一致性，再逐项重算归档实际大小和 SHA256。损坏、缺失、命名冲突、身份或摘要不符均在任何 Gitee 写入前失败，不依靠上传时才发现缺项。

准备端只读取内部成品归档的完整字节，不解开库和工具归档、不修正其内容、不执行运输中的文件、不调用 builder。生成的 `publication.json` 沿用现有 Action 输入格式，资产可以从只读成品副本引用或逐字节复制；复制后仍按实际待上传文件检查，不能修改、重压缩或重新归档。latest 候选和显式 latest 映射沿用原有决议规则。

发布 workflow 不执行 builder 编译、Go SDK 准备或 CMake 打包，不接收发布 `--builder-file` 参数。保留原构建源码 checkout 或等价的只读 Git 获取，以核对原提交入口；控制分支提供发布代码，原构建提交提供已验证成品与入口来源，两者不混用。

### 入口注入例外

`autolib.cmake` 不是提前绑定发布目标的二进制归档。各平台仍运输原样安装入口，准备端必须将每份入口与 `result.entry` 和原构建提交的 `src/autolib.cmake` 逐字节核对，不能通过另取源码掩盖运输损坏。

核对完成后，准备端从原提交源码生成唯一上传副本，沿用现有严格注入规则：仅替换唯一完整的 `set(_autolib_release_root "")` 空赋值行，写入实际 Gitee 仓库和编码后的 Release tag；其他字节保持不变。相同源码入口、相同目标及相同注入规则必须生成相同字节，不加入时间、运行号或临时路径。

入口注入后计算实际大小和摘要，纳入同一资产清单和附件协调流程。入口仍不写 Git 摘要或 latest，源码、安装入口及运输输入均不回写。允许将同一构建发布到不同目标；入口字节随目标变化，库及工具成品字节不变。

### 附件协调与元数据

保留现有流程：固定本地待上传字节 → 查询远端同名附件并下载计算 SHA256 → 相同则跳过，不同则先删后传，缺失则上传。可重试错误从查询开始重做整个附件流程；首次尝试外最多重试 10 次，间隔为 `2、4、8、16、32、32、32、32、32、32` 秒。认证、权限、输入和响应校验错误仍直接失败，不扩建新的重试层或状态存储。

只有 uploaded/skipped 的就绪工具和库参与元数据登记；入口失败仍使整体发布失败，其他成功项仍按既有规则登记，不增加事务或回滚。汇总中的 `metadata_committed` 表示本次是否产生新的元数据提交；`metadata_commit` 是已确认的远端 SHA，无变化时返回已有 SHA，未确认时为 null。退出成功要求附件无失败且 SHA 已确认；no-op 不创建提交，也不误报任务失败。脱敏重试诊断保持不变。

跳过资产不等于永远禁止元数据变更：首次初始化、补齐已有缺项或显式 latest 变更仍可能产生提交。只有远端附件与元数据均已正确、且没有新的显式 latest 变更时，重复发布才要求零新提交。

### 退役、范围与文档

新流程只接受成品 artifact；旧 `ci-install-*` 安装树 artifact 明确报错并要求重新构建，不提供发布端重打包兜底，不迁移或删除历史 artifacts、远端附件、用户安装和缓存。升级验收必须使用新流程完成的一次成功构建，不能直接复用安装树运输的历史运行。

发布准备不包含 builder 调用、跨宿主生产前缀解释或安装树遍历；CI 外层封装只写成品、候选及原样入口，不递归运输安装树。保留仍有生产消费者的 builder 暂存修正、安全归档、共享路径检查和消费端安全解包；混合职责文件只删除失去用途的部分，不按文件年龄或删除行数决定范围。

当前事实由 `docs/architecture.md`、`docs/development.md`、`docs/testing.md` 及相关决定记录共同维护。README 继续单独讨论。本设计不更改上游 multipart 参考本体、消费协议、三方配方、平台支持范围或最低 CMake 承诺，不安排全局归档确定性改造。

本决定形成一个独立的成品交付闭环，不预设后续重构阶段。真实 CI、附件写入、push 和合并仍须具体授权，受控测试不代替托管验收。

## 备选方案

**保留发布端打包，规范全部归档元数据。** 统一时间戳、所有者等可解决本次摘要变化，改动可以较小。但发布仍需取得并编译原 builder、解释跨平台安装前缀和重新生成最终字节，构建成功也不代表成品已生成。选择一次构建交付成品，直接消除重复发布重新打包的原因；不同时捆绑独立构建间的全局可复现要求。

**根据 CI 环境自动打包，同时保留发布端重打包兜底。** 可以同时读取两种运输格式，但会保留两套交接规则和重复生成字节的路径，还使 builder 行为取决于运行环境。选择 workflow 显式调用同一打包命令，并拒绝旧输入。

## 验证

109 的十个 CI 顶层定向用例通过，覆盖真实安装后打包、普通包、any/any 非 publisher、零库、候选与入口、安装只读、库内合法相对链接、危险链接和 FIFO、打包失败不留运输产物及 workflow 接线。该轮两个 PowerShell 子例跳过；Windows 原生构建及可信仓库调用的证据见下节真实托管验收，Linux 结果不作为 Windows 证据。

[发布准备测试](../../../../tests/ci/gitee-release/test_prepare_publication.py)在 109 为 16/16，包括真实 builder 和生产 CI transport 交接、两次 prepare 的所有最终字节一致、真实库内路径修正和链接保留、输入快照不变，以及缺失/等长篡改/错大小/额外及重复资产、平台和运行身份、候选冲突、入口来源、旧格式及外层链接反例。三平台工具文件名正例是协议夹具，不宣称跨平台工具可执行。发布 workflow 的五项定向测试通过，核对无 builder 或 CMake 打包调用且保留来源、目标及权限检查。

[生产到消费联动](../../../../tests/ci/gitee-release/test_entry_delivery.py)在 109 通过：同提交 CI transport 打包真实 importer、dep@1/2 和 probe@1，prepare 返回的注入入口及成品经受控 Git/HTTPS 引导、下载、链接运行。GitHub/Gitee 两子例各在空缓存时下载工具与精确依赖，完整缓存及迁移离线消费为零 HTTP/Git 增量；输入和无关缓存保持不变。

[受控发布测试](../../../../tests/ci/gitee-release/test_publish.py)20/20。就绪的库、工具和入口重复发布满足 uploaded=failed=0、skipped=selected、metadata_committed=false，裸 Git HEAD 不变且无 DELETE/POST，真实 main 退出成功。相同附件补齐缺失元数据仍产生提交；受控故障覆盖从查询重试、十次退避上限、部分失败与 push 未确认，不声称真实网络恢复已验收。

消费日志目录回归先在旧实现确认失败，再在 109 通过 15 个 CI 顶层定向用例，覆盖 driver 的显式与缺省 evidence 目录、越界拒绝、路径软链接、真实安装二进制闭包及运行入口。driver 将 configure/build/CTest 日志写入指定 evidence 下的唯一运行目录，使其落入 workflow 现有诊断收集范围。importer 的精确依赖交接用例及五个子例通过；精简快照辅助函数后的发布准备测试为 16/16。此次日志修复未执行 Windows 原生 runner。

## 影响

打包失败表现为构建失败，原生 job 包含打包耗时；每个平台只执行一次交付所需的打包，不另加一套构建。不同原生平台的打包能力通过对应 workflow 验证，发布 Linux 宿主不代替 Windows 打包。

稳定性承诺仅覆盖同一构建保留的同一份成品。重新构建、重新打包或改变工具版本可能生成不同字节；同一源码 SHA 不能替代 run/attempt 和 artifact 身份。artifact 过期或丢失时需要重新构建，不能从旧安装树恢复同一份成品。

发布准备不解开内部成品，包内正确性由原构建验证、既有 builder 保护及生产到消费的联动验证负责。运输摘要用于发现交接损坏，不是对不可信构建的独立安全认证；可信源码仓库、workflow 和运行来源检查必须保留。

部分成功与无回滚语义保持不变，远端并发人工修改仍可能影响重复发布结果；本设计不承诺跨资产原子发布，也不因摘要稳定而扩建全局事务或持续协调服务。
