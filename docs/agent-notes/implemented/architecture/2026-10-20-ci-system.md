# Agent Note: CI 系统与三平台代表库发布

Status: implemented

## 问题

本地构建、打包和消费链路已经可用，但没有 CI 生产可下载的 Release 资产。先实现 HTTPS 消费仍缺少实际发行源；先批量增加第三方库也不能验证发布流程。首期需要用少量代表库建立三平台构建、打包、发布和真实消费的闭环，再按需增加耗时模块。

本地双平台安装验证不能替代三平台二进制发布，也没有定义发布环境 ABI。按依赖层分别启动 job、重复准备环境和传输完整包，会增加时间及存储；单平台单 job 则改变重跑边界与资源占用，需要保留依赖顺序和失败语义。

## 决定

生产缓存与 label 的决定由[每轮重建与文件名发布](../simplification/2026-10-24-ci-rebuild-without-production-cache.md)部分替代；本文继续拥有其余 CI 职责、环境、发布与验证规则。

CI 是独立的生产与发布系统，本文统一拥有其目标、范围、组件协作、触发、环境、发布汇总、失败处理及验证要求，不作为 Go 工具层迁移或 HTTPS 消费的子阶段。首期手动触发的三平台原生单 job 完成代表库供给和并行预算实机验证。本地交付与当前消费接口保持可用，HTTPS 消费暂缓。系统之间的接入顺序由[路线图](../../../roadmap.md)拥有。

CI 使用独立 Go 可执行目标 `autolib-ci`，通过 CLI 调用既有生产与消费工具及 CMake 构建入口，不另造模块声明或消费协议。`autolib-ci`、`autolib-builder`、`autolib-importer` 是三个职责独立、源码和入口分离的可执行目标，严禁把 CI 作为 builder 子命令或将三个目标的业务实现混编。[Go 工具层设计](../../proposed/architecture/2026-10-21-go-tooling-and-offline-import.md)拥有工具准备与运行要求；[二进制交付设计](../../proposed/architecture/2026-10-20-name-only-artifact-delivery.md)拥有可搬迁打包及 adapter；[无全局清单的双来源包消费](../../proposed/architecture/2026-10-24-manifestless-package-consumption.md)拥有目标消费协议，替代统一清单、单一 URI 与调用者列全包的要求。本文拥有 CI 如何组合调用这些能力，不要求普通本地构建依赖 GitHub、workflow 或 CI 程序。

环境主要参考 `D:/Work/AutoLibBuilder` 的最终设计 `docs/agent-notes/proposed/process/2026-10-08-native-linux-single-job-tiers.md`，参考基线为 `4ae4d92`。该方案本身尚未实施；不复制参考仓库现有 manylinux、多 job 传完整包、Python 工具及 YUM 元数据再重写，也不继承历史清理操作或远端授权。

### 首期范围与入口

首期构建与 Release 发布只覆盖 queue、lz4、flann。queue 覆盖平台无关头文件包，lz4 覆盖源码静态库，flann 覆盖源码动态库与显式 `flann → lz4` 依赖。复用 `tests/autolib/` 已有本地消费夹具，并补齐 Linux x86_64 的真实执行证据。OpenCV 等其余模块不进入首期构建或验收，不因已能本地构建便自动加入 CI；流程验收后再按需增加，不要求先补新库。

仅提供 `workflow_dispatch`，输入为目标平台、代表集内的模块选择；默认选择三平台及三库。`autolib-ci plan` 通过 builder 的通用只读模块信息取得稳定依赖闭包，选择 flann 时带上 lz4；未知或超出首期集合的模块报错。首期不增加 push、PR、定时或自动发布触发。

平台和模块输入采用逗号分隔的完整标识列表，去除各项两端空白后去重；平台标识为 `windows-x86_64`、`linux-x86_64`、`linux-aarch64`。省略输入使用默认值，显式空列表、空项及未知标识均在规划时失败。仅选 lz4 或 queue 合法，仅选 flann 得到 lz4、flann；单平台请求只执行该平台，不额外启动未选平台。

发布目标为 `xxf1ow/xxautolib` 的固定 Release tag `autolib-release`。CI 只接受默认分支运行，其他分支在开始构建前拒绝；workflow 和 CI 程序分别检查，不提供非默认分支只验证模式。每次检出事件记录的 SHA，不切换为默认分支的最新代码。普通本地构建及离线验证仍不受 CI 分支限制。

写入前以目标仓库 API 返回的默认分支名核对运行 ref，要求为对应 `refs/heads/<分支>`，并核对实际 checkout HEAD 等于本次运行记录的 SHA；禁止从默认分支事件改为 checkout 其他代码后发布。分支判定及代码一致性检查在创建 Release 或写入任一资产及其元数据之前完成，tag ref 不作为可发布分支。默认分支在运行期间新增提交不要求本次自动追赶最新 HEAD。

所有受支持的 Release 写入，包括手动重跑、初始化和平台上传，均由同一 workflow 入口协调；整个运行使用按目标仓库和固定 Release 命名的同一并发组，不按 ref、平台或 workflow 名拆组，不取消正在运行的替换操作。同一运行的平台只写各自获准的槽位，finalize 只汇总运行结果。独立直接调用发布程序、其他 workflow 或人工编辑不支持与它同时写入；人工维护须先等发布结束，不为此增加分布式锁或 CAS 协议。

Release 不存在时，唯一初始化步骤在分支检查后创建；固定 tag 缺失时以本次获准 SHA 初始化，已有 tag 则复用，不自动移动或删除。固定 tag 是资产集合入口，不表示全部资产都由该 tag 指向的提交构建；各次运行的生产提交记入运行记录。已有 tag 或 Release 不能读取、认证或网络失败时停止，不当作不存在，也不强制修复 tag。

workflow 默认仅授予 `contents: read`；初始化和已选平台的发布 job 授予 `contents: write`，只汇总结果的 finalize 不需要 Release 写权限，其余权限不额外开启。checkout 不持久保存凭据，发布凭据只传给需要它的步骤，不写入源码、日志或持久配置。权限按 job 生效；同 job 内保留成功层发布能力，不承诺构建与发布步骤之间存在独立安全隔离。

确认目标仓库和 tag 只确定设计对象，不授权立即 push、触发远端 CI 或写 Release；这些操作需另获明确授权。本设计不包含 Gitee 镜像、历史资产迁移、远端删除或自动清理。

### 组件职责与数据流

workflow 负责手动输入、原生 runner/container、具名步骤、job 权限及条件执行；`autolib-ci` 负责 CI 输入校验、平台和依赖层规划、publisher 选择、环境基线与并行证据、发布授权、Release API 操作及运行结果汇总。CI 程序通过命令行调用 builder、importer 和 CMake，不直接调用另外两个目标的内部 Go 函数。

builder 负责模块声明解析与校验、通用依赖闭包、原生 CMake 生成、暂存修正、本地打包及包内身份和直接消费依赖生成；CMake/ExternalProject 继续负责实际源码获取、补丁、配置、编译和安装。builder 不认识 GitHub 仓库及远端 Release、workflow、run identity、CI 平台集合或 publisher，不读取 CI 配置、凭据和运行环境，也不提供 `ci` 子命令。隔离安装根、指定 Make 程序和固定 libdir 是通用构建能力，不因此归入 CI 策略。

importer 负责本地/远端消费查找、包内依赖遍历、包校验、安全解包和准备结果，不解析生产模块、处理生产编排或写 GitHub Release。消费端只读资产发现与下载属于其消费职责，不因 CI 也使用 GitHub 就转交 CI。builder 与 importer 不相互调用业务命令，也不依赖 CI；CI 可以调用二者完成生产和本地消费验证，但不能把生产编排或网络发布转交 importer。

三个目标共用根 go.mod 固定的 SDK 和第三方依赖版本，分别从 `src/autolib-ci/`、`src/autolib-builder/`、`src/autolib-importer/` 独立构建。每个目录维护自己的入口、实现和测试，不互相导入、复制或通过符号链接、build tags 等方式混编业务源码，不为 CI 抽取整个 builder 到共享层。CI 的计划、环境、ABI 验证、GitHub、发布和编排实现及其测试均归 `src/autolib-ci/`；配置和准备脚本归 `.github/`，嵌套 Make fixture 归 `tests/ci/jobserver/`，真实消费夹具继续归 `tests/autolib/`。不引入独立产物源码层、Python 工具、后台服务或持久步骤数据库。

普通根 CMake configure 只准备并构建 builder，不构建或执行 CI 程序；CI 相关源码及配置不进入普通生成器的重配置输入清单。CI 经既有私有 SDK 包装入口分别准备三个宿主工具，根 SDK/缓存机制不因新增目标复制一套。下游仍只需要 importer 和单文件 CMake 消费入口，不取得或启动 CI、builder。

规划输出选中平台、模块依赖层和通用包唯一 publisher；各平台准备一次环境，构建所选模块及依赖，暂存打包并完成消费验证，随后上传获准发布的资产。独立汇总步骤只报告本次各槽结果，不合并或发布 `manifest.json`、`build-cache.json`。规划及汇总只传实际需要的小型元数据，不通过 Actions artifacts 传完整包。

CI 沿用本地打包链路生成本机 importer，随本平台发行物提交，并在该原生平台执行 smoke 和本地消费验证；importer 仍严格按宿主平台区分，不使用 any/any。这里不实现消费入口的 HTTPS 下载：消费验证使用本地根进入 `autolib.cmake` 且不传远端来源，完整输入与缺包路径均不联网。本地消费使用无清单协议，不以含清单的夹具替代当前接口验证。

CI 发布以本地协议验证为前提：实际 builder 产物含固定四行身份及依赖头、固定资产名和 Zstd 内容校验，CMake 只请求根包即可通过 importer 准备完整闭包。本地与 CI 的 prepare 调用、发行就绪判断及相关测试统一使用当前 CLI，不为旧清单缓存增加过渡兼容。CI 上传后核对实际资产名称、唯一性、`state=uploaded`、有效 `sha256:` 摘要及上传字节；真实三平台本地消费和 API 事实通过后，才交接远端消费阶段。公开 Release 消费的分页与下载重定向由远端阶段验收，不借 CI 的上传成功提前宣称消费端 HTTPS 可用。

规划成功后才启动选中平台；规划失败不执行发布。平台之间不因一个平台失败而取消其他已选平台，矩阵使用 `fail-fast: false`。finalize 在平台成功或失败后均检查可取得的成功记录，校验其代码、计划和目标一致，不以依赖 job 默认成功条件跳过失败汇总，也不将缺失记录视为成功。成功层的验证与上传不能只依赖最后一个全库验证步骤。

手动取消、runner 中断及超时均不能保证 finalize 或清理必达。超时值在 workflow 中显式配置，不设置后台恢复任务；这些运行不计为验收成功，已完成上传且满足消费检查的槽位可供消费者使用，不依赖 finalize 是否完成。临时文件只在本次受控构建目录内准备，不清理用户目录或历史远端资产。

### 独立命令之间的调用

CI 入口为 `autolib-ci plan`、`init`、`run` 和 `finalize`；运行与发布语义全部由本目标拥有。需要生产或消费工具的命令显式接收其可执行文件路径，不从源码目录拼接 Go 文件构建临时混合程序。子进程使用参数列表传递输入，不把 workflow 输入拼进 shell 代码；调用失败、非零退出或结果损坏时停止相关工作，不读取旧结果作为成功。

builder 提供通用只读命令 `describe`，必填 `--source-root`、`--system-name`、`--architecture` 及至少一个可重复的 `--module`，复用实际生成路径的声明校验、平台生效规则和稳定依赖闭包。全部校验成功后才向 stdout 输出确定性 JSON，诊断写 stderr；失败不输出可用的成功结果。它不下载来源、不配置或编译库、不改写安装树，也不生成 CI 计划。未知模块、依赖环及非法声明与普通生成同样失败，命令适用于全部合法模块，不包含首期三库或 CI 平台白名单。

模块信息包含稳定依赖先序的模块集合、各模块已生效的归一声明、直接依赖、通用包声明、系统依赖、实际引用的补丁及专用文件清单、独立 adapter 输入、根 Go module 固定输入及相关 builder 生产文件清单；路径相对于 source root，不泄漏临时 checkout 绝对路径。无 adapter 的合法模块仍可描述，adapter 输入只在实际存在时报告，不能把可打包资格当作通用描述前提。CI 使用这些信息选择层、合并本次系统依赖，不解析 TOML 或复制依赖闭包算法。builder 只描述生产事实，不输出 publisher、发布授权或运行结果；CI 不反向要求 builder 读取 `.github/ci-tools.json`。确定性 JSON 字段和错误规则由模块描述测试验证，不增加旧输出兼容或协议协商。

CI 通过根 CMake 入口构建所选模块，再调用 `autolib-builder package` 取得带身份和依赖的本地归档，不在 CI 中重写暂存修正或打包引擎。CI 核对本次待发布资产并计算实际摘要，不能要求 builder 上传远端资产。ABI、CRT 和行为验证由 CI 调用消费夹具和本机工具取得证据，不转变为 builder 的 CI 命令。

每轮构建及跨运行缓存的取舍由[生产缓存收缩决定](../simplification/2026-10-24-ci-rebuild-without-production-cache.md)拥有。本记录保留组件、环境和逐槽发布约束，不要求恢复其他运行的安装负载。

### 原生分层与并行

Windows x86_64、Linux x86_64 和 Linux aarch64 各使用一个原生构建 job，平台间可以并行。C++ 库不使用交叉编译、Zig 或 QEMU；Go importer 的交叉编译与逐宿主运行验证由 [Go 工具层设计](../../proposed/architecture/2026-10-21-go-tooling-and-offline-import.md)拥有。Linux 每个平台共用一个 Actions 原生 container job；Windows 保留 Visual Studio/MSBuild，不传 Linux Make 参数。规划和最终汇总可保留独立辅助 job。

每平台按具名步骤执行环境准备、实际依赖层、消费验证和产物汇总；首期只有代表集需要的层，不为参考方案的 tier 数量或 OpenCV 创建空步骤。依赖层顺序执行，不增加后台调度器；非空前置层失败时不继续依赖构建或报告成功。后续加入 OpenCV 时仍按实际依赖排序，不预建专用调度机制。

环境和该计划所需系统依赖集中准备一次；后续层使用本 job 已校验的安装产物和归档。每个成功层保留固定槽 Release 发布能力，让成功产物及时可供消费者下载，不另存步骤完成数据库。只在获得发布授权时启用写操作，完整性和独立槽位发布规则由下文拥有。

不上传供层间传输的完整包 Actions artifacts，正式产物使用 Release；独立规划/finalize 实际需要的小型元数据仍可用 Actions artifacts。单 job 不能单独重跑某一步，接受重跑时重新准备环境的成本。

### 环境与 ABI

| 对象 | 沿用的目标 | 边界 |
| --- | --- | --- |
| Linux 基础环境 | Docker Official Image Ubuntu 20.04，GCC/G++ 9.4 来自官方 APT | glibc 2.31；不加 Toolchain PPA，不逐包换编译器；实际镜像 digest 须覆盖两架构。 |
| Linux 运行库 | Ubuntu 官方配套 libstdc++ 与 libgcc，动态链接 | 不要求运行库包版本号等于 GCC，不静态捆绑运行库或切换旧字符串 ABI。 |
| Linux 并行 | GNU Make 4.4.1 FIFO jobserver | 公共入口传 `--jobserver-style=fifo` 并统一预算，父子用同一 Make，不逐包追加独立 -j。 |
| CI CMake | Kitware 官方 CMake 3.31.12，显式固定补丁版 | 版本更新须修改配置并验证；项目最低版本仍为 3.20。 |
| Windows | windows-2022 原生 VS 2022 x64、Release、普通模块默认 v143 | 保留完整父生成器身份和显式 CRT；不全局降为 v142，不承诺 runner 的 MSVC/SDK 补丁固定。 |

Linux 原生 runner 分别采用 `ubuntu-24.04` 和 `ubuntu-24.04-arm`；Ubuntu 20.04 是 job 内容器用户空间，不是 runner 宿主版本。首个远端运行前检查目标仓库可使用这些 runner，启动后校验 runner 与容器实际架构；标签不可用或架构不符即失败，不回退 QEMU、交叉编译或不同 ABI 基线。

实现配置固定一个覆盖 `linux/amd64`、`linux/arm64` 的 Ubuntu 20.04 多架构索引 digest，两平台引用同一索引并记录各自实际子镜像 digest；不能只写可漂移标签。首次固定及后续更新均从官方镜像索引检查两种架构，更新通过显式配置修改，并在受影响两平台正常运行中验证，不维护自动镜像升级器。具体 digest 是实施配置中的校验值，不从参考实验照搬。

APT 使用 Ubuntu 官方 Focal 源及其 updates/security pockets：x86_64 使用 `archive.ubuntu.com/ubuntu`、`security.ubuntu.com/ubuntu`，aarch64 使用 `ports.ubuntu.com/ubuntu-ports`。首期不接入 Ubuntu Pro/ESM 订阅，不承诺这些公开源仍提供持续安全维护；记录实际包修订和来源。源不可用或所需版本缺失即停止，不自动改用 old-releases、第三方源或升级发行版；涉及来源或基线变化时交由人工决定。[Ubuntu 官方支持状态](https://ubuntu.com/20-04)明确 20.04 已结束标准支持。

工具从官方来源取得并校验，版本更新须显式修改，不动态选择 latest。`.github/ci-tools.json` 的 `cmake.version` 和 `make.version` 分别唯一拥有对应工具版本，同文件维护下载地址、摘要和显式生产基线；根 go.mod 与既有 SDK 配置继续拥有 Go 选型。准备脚本校验实际工具版本，CI 程序读取配置校验字段、平台、格式及摘要，不各自维护相同选值的硬编码副本；jobserver 探针只核验并行行为。Linux 系统依赖只维护 APT，Windows 保留 Chocolatey；不为只支持一个 Linux 发行版的目标复制 YUM/DNF 准备。各模块声明自己的系统依赖，不靠其他模块的构建步骤偶然安装。

公共配置沿用 `CMAKE_INSTALL_LIBDIR=lib` 与 `CMAKE_POLICY_VERSION_MINIMUM=3.5`，均已由普通构建入口传入子项目；模块显式 cache 优先。policy 只提供低版本下限，不覆盖上游更高要求，机制见[模块扩展决定](../../proposed/architecture/2026-10-20-module-expansion.md)。Linux 源码构建产物的 glibc 需求不得高于 2.31；C++ 运行需求独立记录 GLIBCXX、CXXABI、libgcc 符号，不用 glibc 版本代替 C++ ABI 判断。静态归档须经实际下游链接验证，预编译输入单独记录兼容要求，不能因默认 GCC 9.4 就视为同基线源码产物。

正式构建记录配置、实际命令及工具自然输出的版本、来源和发行版包修订；Windows 沿用 runner 和 CMake 的工具链选择与诊断，不另用 vswhere、目录枚举或包清单选择第二套工具链并作为成功门槛。只记录相关字段，不转储进程环境或通过重读 PATH 判断运行是否成功。容器内只对实际 checkout 设置必要的 Git 信任，不修改用户机器的全局信任列表。显式环境基线变更仍须确认并验证，不预建通用工具链状态管理。

GCC 9.4 是配置决定，不是全部模块已成功的声明；不额外全包试编译来重新决定选型。正常 CI 失败如实报告，不自动升级编译器。Ubuntu 20.04 的工具来源可信不等于仍有免费安全维护，落地时须明确镜像及补丁来源；任何改变基线的方案须另行确认。

### 并行预算与 CI 历史核验

Linux 每个平台在容器内以 `nproc` 得到当前可用 CPU 数，取至少 1 的整数 N；顶层 Make 仅在公共入口设置 `-jN --jobserver-style=fifo`。同平台的各依赖层顺序执行并各自使用这一预算，平台间不共享 token；准备工具和测试进程不属于 Make 编译任务预算，也不与库构建后台重叠执行。

公共入口及生成逻辑确保父子构建使用同一 Make 4.4.1，保留嵌套调用所需的 `MAKEFLAGS` 和 FIFO 路径，向子 CMake 正确选择相同 `CMAKE_MAKE_PROGRAM`。子构建不重新传入独立 `-j` 或带数量的 `--parallel`，不让 `CMAKE_BUILD_PARALLEL_LEVEL` 覆盖继承预算。不逐包修改构建命令，也不以必须升级到 CMake 4 的 pipe jobserver 修复替代 FIFO 方案。

首次有真实编译的 CI，以及修改并行接线后的首个相应运行，必须及时查看运行历史、job 日志和实际父子构建命令，不等全部库扩展后才判断 `-j` 是否有效。记录运行 URL、提交 SHA、平台、N、Make 版本、jobserver 传递、warning 及 worker 探针峰值；仅记录相关参数，不输出完整环境或凭据。结合小型嵌套 Make 探针验证参与任务的峰值不超过 N，N 大于 1 时确有重叠工作，并检查真实 lz4/flann 构建没有独立预算重置或 jobserver 单线程回退。

历史记录只对相同并行接线和相关环境提供证据，不用旧的通过结果掩盖本次失败；仅有顶层命令带 `-j`、无 warning 或墙钟缩短，都不足以单独证明有效。缓存全命中时没有真实编译证据，应如实标记；需要补证时，在获得运行授权后仅选择一个受影响平台和小型编译库构建，不扩成耗时库或反复全量测试。发现预算失效先处理公共接线，不通过逐库追加 `-j` 继续扩大发布范围。

### 固定槽发布与汇总

每轮构建本次所选平台和模块的完整依赖闭包，包括自动补入的 lz4，使用本次隔离的构建安装目录；同轮共享依赖只构建一次。不从 Release 获取生产缓存，不计算生产 build ID，也不提供强制重建开关；源码和工具下载可按原规则复用。构建或验证失败且尚未上传时，旧槽位保持不变。

生产者和消费者共用正式包资产。包名为 `<name>-<os>-<arch>.tar.zst`，工具为 `autolib-importer-<os>-<arch>`（Windows 加 `.exe`）。上传不设置 label，响应的名称、状态、空 label 和 digest 必须与本次待发布输入相符；下载列表显示文件名。不上传 `manifest.json`、`build-cache.json`、摘要 sidecar 或第二份完成标志，不从已有全局记录恢复未选槽。各平台只替换自身获准写入的固定资产，未选平台、模块和其他资产保持不动。

finalize 只读取本次可取得的小型运行结果，报告各平台及槽位的构建、验证和上传结果，不再次下载已验证成功的资产，也不向 Release 提交元数据。结果必须绑定本次代码、run、attempt 和平台，缺失结果不算成功；汇总未运行不使已完整上传的资产失效。受支持写者遵守同一 workflow 的运行串行约束，不另增跨资产提交协议。

每个选中包必须本次构建并验证成功；机器码包和通用 publisher 还必须核验上传响应，其他平台的通用包只验证、不上传。整次运行只有全部选中工作及所需上传均成功才算成功。对消费者而言，固定名资产已完整上传、摘要有效且包内容通过消费检查即可使用，不需要全局清单提交或整次运行成功。

某平台或后续层失败时，汇总报告可取得的成功结果，但整个运行保持失败，不发布依赖于失败前置工作的产物。失败工作不能借旧资产或其他平台成功算作本次通过。同名替换先删除再上传，中断可能使本槽缺失或停在未完成上传状态；显式重跑重新构建选中闭包，不承诺旧槽备份、自动回滚、跨资产原子性或持续可用。认证、API 网络错误及无法解析的响应使运行失败，不悄悄当作空集合，不扫描修复全仓库。

### 平台无关头文件单槽位

只对模块显式声明且安装树及导出配置均不含平台相关内容的包启用通用槽，不以“没有 DLL/so”推断。首期对象为 queue：安装仅复制六个原始头文件，adapter 不包含平台路径或生成配置。固定资产名和包内身份统一使用成对的 `os=any`、`arch=any`，唯一固定资产为 `queue-any-any.tar.zst`；不支持半通用槽，生产者不得为同包发布通用和平台限定两种槽，不增加回退优先级。消费者仅检查实际查找层的候选，通用归档在不同目标平台目录中的准备副本不是发布槽冲突，具体规则由[消费设计](../../proposed/architecture/2026-10-24-manifestless-package-consumption.md#来源与查找顺序)拥有。

规划在本次选中平台中按 Linux x86_64、Linux aarch64、Windows x86_64 顺序唯一选择 publisher。其他已选平台继续正常消费验证，使用本轮构建的产物，不上传、不等待 publisher，也不在失败后自动接管；未选平台不执行验证。publisher 失败不取消其他已选平台的工作，最终该包发布失败并使整次运行失败，保留各平台实际验证结果。切换 publisher 不改变包身份。

模块声明维护者负责核实通用资格，builder 在通用打包时核对安装内容与声明；queue 限定为声明的六个原始头文件和平台无关 adapter，发现额外二进制、生成配置、平台路径或不符合已声明输入的内容即阻断通用发布，不仅发 warning，也不自动降级为平台槽。首期不开发可判定任意头文件库平台无关性的通用分析器。各平台本地验证包可有不同归档时间、权限等元数据及压缩摘要，不要求压缩字节相等；实际文件内容必须符合共同声明，唯一 publisher 上传的实际字节决定公开摘要。

模块声明、规划、打包、包内导入、资产发现、importer 和测试须同步支持通用身份；queue 的包身份不因 publisher 宿主变化而变化。通用包适用于已有支持的平台，不扩大操作系统支持；lz4、flann 及 importer 继续严格匹配各自 OS/架构。参考方案的 Eigen 不进入首期集合。新仓库从空发布集合开始，不迁移旧发布资产，不新增历史槽位兼容或自动远端清理；未来镜像若接入，须遵守相同身份约束。

### 发布前检查与消费验证

每槽上传前必须通过声明与身份检查、实际字节摘要、适用的 ABI 检查及相应真实消费验证；任何必需项失败禁止上传该槽。平台仅选择部分模块时，只验证实际依赖闭包：queue 执行入出队，lz4 执行压缩解压并比对原文，flann 在 lz4 就绪后执行索引创建、释放及动态库加载路径检查。逐槽复用 `tests/autolib/` 的相应最小消费，不为了让固定三库夹具通过而补建未选库，也不逐槽执行完整双搬迁。完整代表集的发行目录与准备包搬迁、两轮编译链接和 CTest、字节不变检查每平台执行一次；本机 importer smoke 和无 C/C++ 动态运行库依赖检查也只在平台准备时执行一次。

Linux 两架构分别以 glibc 2.31 及该发行版官方配套 libstdc++、libgcc 为消费基准，记录产物及最终消费者的 GLIBC、GLIBCXX、CXXABI、libgcc 实际需求；GLIBC 高于配置上限或基准环境内真实链接运行失败均禁止发布。C++ 运行库兼容性以该环境的真实链接运行验证，不扫描依赖运行库再比较符号提供集合，不自建动态链接器推演。静态 lz4 通过真实消费者最终链接与运行检查，不只扫描 `.a`。预编译模块不在首期，后续增加时须登记版本与归档摘要，并独立验证其运行要求，不冒充同基线源码构建。

Windows 首期使用 VS 2022 x64/v143、Release 和显式 `MultiThreadedDLL`（`/MD`）。CI 从生产基线为生产者、依赖与消费者传入相同生成器、架构、工具集、配置及 CRT，以 configure、build、CTest 的实际返回码和包内链接、DLL 实际加载来源判定成功；不在成功后重读生产或消费 CMakeCache、tlog 与编译日志作第二次审计。CI 的固定选型不成为本地消费夹具的必填限制，夹具保留原有默认行为。hosted runner 的 MSVC/SDK 补丁变化可在本次必要检查通过后发布；工具集、CRT、目标架构或显式基线变化须修改配置并重新验证。首期不承诺 v142 产物，v142 实机验收不阻塞 v143 发布；未来显式增加 v142 或改变相关支持承诺时再安排专项人工验收。

已有 importer 测试覆盖本地来源禁止联网、具体平台错配和危险归档拒绝；any/any 选择、半通用身份与槽共存拒绝、publisher 选择及局部发布为本次增量覆盖。普通 Go 测试使用确定的小型 fixture，不扫描历史 build 目录发现工具或发行包，也不因本机残留自动启动重型消费闭环；真实代表集由显式验证入口执行。各承诺平台仍须执行对应原生测试，不能以 Windows/aarch64 的本地历史证据代替 Linux x86_64。日志版本、耗时和磁盘峰值是诊断信息，不单独作为成功门槛；无空间等实际错误仍使受影响工作失败，不为首期额外设容量配额或多轮性能基准。

### 触发凭据与运行证据

人工或助手触发 CI 使用调用方提供的凭据，不把本地 token 上传为仓库 secret，也不以本地 token 代替 job 内的 `GITHUB_TOKEN`。实施前分别确认身份、仓库访问和 Actions 查询能力；读取公开 workflow 或运行列表成功不证明具有触发权限。fine-grained token 的 dispatch 需要目标仓库 Actions 写权限，首次真实 dispatch 必须在 workflow 可用且取得远端运行授权后执行，并确认对应 run 产生；没有 workflow、没有历史或未做 dispatch 时如实记录未验证，不发送伪造请求冒充权限测试。权限依据见 [GitHub dispatch 文档](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)。

实施过程中通过运行历史及时查看与当前提交对应的 job、失败步骤和原生构建日志，尤其核验上文 `-j` 与 jobserver 证据；不可只看 workflow 总状态。无历史时先记录证据缺口，不能据此声称并行已经生效，也不因此未经授权创建或触发远端工作。

## 备选方案

**CI 作为 builder 子命令。** 可直接调用 builder 内部函数，但会把 GitHub、运行身份和发布策略混入通用构建工具；三个可执行目标各自拥有职责，通过 CLI 复用生产与消费能力。

**为 CI 抽取共享 Go 引擎。** 可避免子进程信息传递，但需要改变现有 builder 的包边界并扩大本次迁移；选择通用只读模块信息接口，不复制解析规则，也不为本期预建 common/shared 层。

**每层独立 job。** 可以单独重跑并跨 runner 并行部分层，但重复环境准备和整包传输；选择单平台共享环境，保留具名步骤。

**交叉编译或预制第三方构建镜像。** 前者增加目标工具链与运行验证，后者增加镜像发布及补丁维护；采用原生 runner 和官方小镜像现场准备，实际瓶颈出现后再评估。

**升级 CMake 4 或逐包追加 -j。** 前者提高最低要求，后者可能超额并行；沿用公共 FIFO jobserver 方案。

**三个头文件平台记录共用一个资产。** 仍维护重复摘要和身份映射；显式 any/any 单槽直接表达范围，机器码包不放松检查。

## 验证与约束

### 回归覆盖

- CI、builder、importer 从各自源码目录独立构建和测试，业务实现不互相导入或混编。builder 无 `ci` 子命令、GitHub API 和 CI 配置/凭据读取，importer 无生产编排；普通根构建不准备或运行 CI 程序，改动 CI 源码不引发普通生成器重配置。CI 通过实际 CLI 完成模块描述、构建、打包和离线消费，不能用直接调用其他目标内部函数的测试替代。
- builder 的通用模块描述与普通生成共享声明校验和稳定闭包，覆盖非首期合法模块及非法输入；CI 不解析 TOML。针对缺失工具、非零退出、错误或残缺 JSON 的边界测试必须失败且不消费旧结果。实际 importer/CMake 入口验证包身份及依赖可用性，不只验证传给子进程的参数。
- 获得远端授权后，queue、lz4、flann 在三平台各自原生单 job 完成所需依赖层、打包和逐槽真实消费；完整代表集每平台完成一次双搬迁编译链接、运行和字节不变验证。环境准备及本机 importer smoke、无 C/C++ 动态运行库依赖检查每平台只执行一次，不执行 OpenCV 等其余库，不为形式完整建立空层。
- 手动选择平台和模块、flann 依赖闭包以及 workflow/程序两层默认分支运行限制均可观察；非默认分支在构建前失败且不产生 Release 写操作，无 push/PR 自动触发。
- 每轮从源码构建所选闭包；已有 Release 包不短路下一轮编译，共享依赖同轮只构建一次，不通过 Actions artifacts 传完整包。
- 单平台发布不修改其他槽位，无全局清单提交；资产上传不设置 label，finalize 只汇总。前置层失败阻断依赖工作，部分平台失败仍保留成功槽位且整个运行失败。用小型协议 fixture 验证这些分支，不反复重建完整代表集模拟每种故障。
- Linux 嵌套构建在 N 大于 1 时有实际重叠 worker 证据、参与任务峰值不超过 N 且无 jobserver 单线程回退；同一公共预算覆盖父子 Make，不靠逐包命令修改。首次真实编译及并行接线变更后的 CI 及时检查历史与日志，记录相应 run 和命令证据，缓存全命中不冒充有效性验证。
- 正常发布的必需检查按上文执行，部分模块不补建全代表集；配置是工具与生产选型的唯一来源，实际返回码、包内链接和 DLL 来源验证通过。Linux 检查 glibc 上限并记录 C++ 符号需求，源码与预编译覆盖分开报告；Windows 统一传入 v143、x64、Release 与 `/MD`，不增生产/消费日志审计或本地夹具限制，不以未承诺的 v142 作为首期门槛。
- queue 在多平台及单平台请求中只有唯一 publisher 和一个 any/any 槽；三平台正常消费成功，其他平台不上传、不等待或自动接管。混合身份、槽共存和机器码错平台均拒绝，选择与冲突以小型 fixture 覆盖。
- 在一致模块与下载缓存条件下报告环境准备、平台/整体墙钟、累计 runner 时间和磁盘峰值，不承诺单 job 必然更快。
- 输入错误在规划时拒绝，force 参数不再接受；首次获授权的真实 dispatch 确认凭据可触发运行，认证或只读 API 成功不能替代该证据。

## 影响

独立程序间需要维护通用模块信息和现有发行协议的调用，错误结果必须在进入构建或发布前拒绝；这项接口成本用于隔离 CI 策略，不以混编三个目标或复制业务实现消除。三个工具可以使用同一个 Go SDK 和模块缓存，但独立源码及 CLI 不是同 job 内的进程安全隔离承诺，workflow 权限仍按前文 job 规则生效。

合并 job 减少跨 runner 并行，可能增加整体墙钟；同 job 构建与产物长期共存会提高磁盘峰值，不能提前删除后续层仍需内容。运行环境、下载源和 hosted runner 会变化，本记录不把历史局部实验当作三平台全量验证，也不以提前增加自动恢复或自托管 runner 消除此限制。

Windows 本机以 CMake 3.31.12 执行 builder 的 `TestArchivePipeline/all_missing` 时，生成的 MSBuild 批处理忙循环并导致 Go 测试超时；同一用例以系统 CMake 4.2.3 执行约 2 秒通过。CI 目标在固定 3.31.12 下的回归通过不覆盖该生产失败路径，不能据此声称所有 builder 失败路径均已验证；该差异不改变本设计的固定 CMake 选型，也不以本机其他版本的通过代替固定环境实机验收。
