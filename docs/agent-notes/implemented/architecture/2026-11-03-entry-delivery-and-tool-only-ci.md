# Agent Note: 自定位消费入口与工具专用 CI

Status: implemented

## 问题

下游需要以尽量少的 CMake 代码接入预编译包。本地使用者不应把较长的入口文件从生产源码复制到自己的仓库，也不应分别指定安装来源和缓存目录；远程使用者不应安装 Go SDK、手选平台程序或维护多级引导脚本。

本地编译结果需要明确的离线行为。缺少工具或包时，消费不能意外转向上游远端仓库；远程发布的入口则必须指向本次实际发布的仓库，让 fork 使用自己的发布配置，而不是继承源码中写死的上游地址。仅为发布 importer 和入口运行 CI 时，也不应默认编译全部第三方包。

构建和发布不能分别维护一套包选择。一次构建已经确定并验证的交付集合，应完整进入发布；工具和入口是每次产物交付的基础，不是需要用户单独选中的包。取消的来源和选择能力也应连同实现、透传参数及专属测试一起退出，避免新流程继续承担两套行为的维护成本。

## 决定

保留 `autolib.cmake` 作为唯一 CMake 接入入口，将它与 importer 和版本化包安装到同一个 `3rdparty` 根。入口自身目录同时是本地查找根和远程下载缓存根。远程地址是入口内部的发布信息，不是用户配置：源码和本地安装版为空，CI 仅在上传副本中注入实际 Gitee Release 下载根。

### 设计归属与范围

本文拥有入口交付、本地与远程地址的确定方式、CI 三种构建选择、fork 构建发布的可信来源规则，以及相应退役范围。它部分替代[版本化包与统一产物交付](../../proposed/architecture/2026-10-29-versioned-artifact-delivery.md)的独立本地来源和四步选择，部分替代[CI 自动发现](2026-10-27-ci-discovery-and-release-sources.md)及[Gitee 交付](2026-11-02-gitee-delivery-reimplementation.md)的空列表、无包平台跳过、固定上游源码限制和发布二次筛选，并扩充入口运输及发布内容。上述记录仍拥有版本、依赖、资格过滤、校验、Git 元数据、权限及历史证据，保持原生命周期，不整体归档。

本设计不定义包信息预览，不重写构建引擎、包格式或 Gitee 上传参考实现，不把 Git 获取职责迁入 Go，不新增包装引导层、兼容入口、更新服务或全平台程序合集。普通本地根构建的 `BUILD_LIST` 语义不因 CI 输入变化而改变。

### 完整流程与职责

本地流程是“构建安装入口、宿主 importer 和所选包 → 下游 include 原安装入口 → 检查完整精确闭包 → 加载 adapter”。远程流程是“构建时选择一次 → 验证并运输安装结果 → 原提交发布准备生成注入副本及资产清单 → 上传全部资产并登记工具和库的元数据 → 下游下载入口 → 按需引导宿主工具和准备精确闭包 → 加载 adapter”。完整本地结果或缓存命中时，不进入元数据获取和下载步骤。

builder 继续拥有配方、版本解析、安装描述、路径修正和归档；CI 拥有平台计划、执行、验证与运输；发布准备核对原构建输入并生成最终发布字节；Gitee Action 上传明确清单并提交成功工具和库的元数据。workflow 提供可信运行上下文、目标配置和串行调度，不再维护另一套包选择。CMake 和 importer 的消费分工保持不变。

### 入口安装与下游接入

本地编译安装得到的 `3rdparty` 根包含 `autolib.cmake`、当前宿主的 importer，以及本次构建的版本化包和包级 latest。入口不依赖生产源码树中的旁置脚本，下游通过绝对路径直接 include 已安装的入口，再调用 `autolib_import`，不复制入口或包到另一份消费缓存。

远程使用者在其项目选定的目录下载 Gitee Release 中的单个 `autolib.cmake`，include 该文件，再调用 `autolib_import`。下载只是取得入口，不会自动执行 include 或导入；这三个动作由下游 CMake 按顺序执行。入口下载 URL 可以来自 HTTP(S) 或 `file://`，由 CMake 下载处理；入口不需要获知或反推该 URL，也不据其协议决定包来源。

入口始终以自身所在目录定位工具和包。远程首次使用时，该目录通常只有刚下载的入口；后续下载结果留在同目录，后续配置复用这些缓存，不假设每次使用都是空目录。复制入口本身不携带缓存；`file://` 下载也不会自动把原文件的同级包带入目标目录。本地直接消费安装结果应 include 原安装入口。

远程入口应放在专用、可写且不纳入项目版本控制的安装／缓存目录，例如 `3rdparty/`，不能把它当作只读 CMake 辅助脚本放入已有脚本目录。宿主工具直接位于该根，库按 `<包名>/<版本>/` 分目录存放，不将各包的 `include/`、`lib/` 平铺到入口目录。调用方负责目录放置与版本控制忽略；本设计不增加自动清理，也不删除同根的既有文件。

### 不可配置的消费来源

移除 `AUTOLIB_LOCAL_ROOT`、`AUTOLIB_REMOTE_ROOT` 两个用户配置接口，不读取同名 CMake 普通变量、缓存变量或环境变量来确定来源，不保留旧接口兼容或另一套覆盖开关。这里的不可配置指公共接口不支持覆盖，不是对用户手动修改脚本的防篡改承诺。

用户变量不表达离线策略：设置 `AUTOLIB_LOCAL_ROOT` 或将 `AUTOLIB_REMOTE_ROOT` 设为空，都不能禁止远程发布入口在缺失输入时联网。不增加旧变量检测或迁移兼容；离线保证由入口版本及完整缓存决定，不能沿用旧调用方式推断。

本地根由入口文件的实际路径确定，沿用真实路径解析。工具和包先查该根中的可用结果；不存在时，只有入口内部远程地址非空才允许按既有协议获取。内部地址为空时，缺少任何必需输入就明确报错，不获取 Git 元数据，也不下载工具或包。

完整有效的工具、根包和精确依赖闭包命中时，CMake 和 importer 都不访问远端，包括入口内部已带远程地址的情况。根包完整但缺依赖时，只补所记录的精确依赖；已有候选损坏、身份错误或校验失败时直接失败，不把损坏当作缺失，不自动覆盖或改用远端副本。版本选择、缓存 latest 不自动刷新及单消费闭包版本冲突规则沿用统一交付契约。

远程入口的完整缓存可在离线环境复用，但不承诺缺失输入时也绝不尝试联网；需要严格禁止联网时使用内部地址为空的源码／本地安装入口。远程入口不提供强制离线开关，网络不可用时按既有请求失败规则退出。

移除“独立本地来源目录 → 复制或解包到入口缓存”的配置路径。本地已安装文件直接作为入口目录中的可用结果；远端取得的文件仍经既有暂存、校验及安全解包后成为该目录中的缓存。不增加第三个搜索根或系统库回退。

### 平台识别、工具校验与职责

CMake 继续负责识别运行 importer 的宿主 OS 和架构、确定对应工具文件名及首次引导。它优先使用入口目录中的宿主程序；缺少时从发布根取得该宿主的工具归档，不要求一次下载所有平台，也不执行不匹配宿主的程序。

远程工具仍使用现有 Git 元数据中的预期 SHA256 校验，检查归档结构和预期程序，完成必要执行权限处理后才运行。已存在的不可用工具按错误处理，不隐式重新下载。下游无需填写工具 SHA256，也无需因工具发布而修改项目 CMake 中的摘要。

CMake 继续通过 FetchContent 获取并检查 Git 元数据快照；importer 继续负责精确包及依赖准备、包校验和结果输出，CMake 完整检查结果后才加载 adapter。首次工具和后续包复用同次配置的快照，完整本地命中不取快照。地址交给 importer 属于内部调用参数，不恢复用户来源配置能力。

### 构建时唯一的包选择

构建 workflow 的 `modules` 输入采用以下规则，平台输入及原生构建范围保持不变：

| 输入 | 结果 |
|---|---|
| 未提供或空字符串 | 仅生成并交付 importer 和 `autolib.cmake`，不编译第三方包 |
| 原始输入严格等于 `all` | 按现有发现及资格过滤规则选择全部可参与 CI 的配方版本，交付 importer、入口及有效包集合 |
| 普通逗号分隔包列表 | 沿用裸名 latest、精确版本与依赖闭包选择，交付 importer、入口及所选有效闭包 |

全量标记区分大小写，必须独占整个原始输入，不先去除空白或其他字符再识别。` all`、`all `、`ALL`、`all,eigen`、`eigen,all` 和 `all,` 均不能触发全量构建；其中混入 `all` 的列表作为非法输入拒绝，不过滤掉该项后继续，也不将其当作普通包名。非空但只有空白的输入按无有效列表项拒绝，不解释为工具专用或全量模式。普通包列表继续遵守现有列表校验。`autolib-importer` 不是可选包名，不提供单独选择工具或入口的语法。

三种选择都保留所选平台的计划和执行任务，生成、检查并运输各宿主 importer 及入口，不因库集合为空而丢弃整个平台。自身或传递依赖缺少 adapter 的根仍按原规则过滤，不放宽包资格；显式列表或 `all` 过滤后没有库时，仍交付工具和入口，不再产生整个平台零交付的例外。未知名称、格式错误、声明损坏及实际构建或验证失败仍报错，不把失败解释成过滤。

有效库集合为空时，不运行空的库构建层，不调用要求非空根的库消费验证，也不伪造库消费成功。工具构建、可执行性及入口检查仍须真实通过；汇总和自动发布按这些实际结果判定。有效库集合非空时，继续逐根验证精确闭包，两个 Eigen 版本使用独立消费者，any-any 包继续只有一个 publisher。

计划及结果摘要明确展示各平台的请求根、有效根和被资格过滤的根，过滤信息不是警告或失败。CI 成功表示有效集合完成交付，不表示所有请求根均被交付；未知包、损坏声明及实际执行失败仍不能作为过滤项处理。不新增严格选择开关。

CI 复用既有 SDK 和工具准备步骤，允许单独准备 importer 与安装入口。不能向普通根入口传空 `BUILD_LIST` 来表示“零库”，因为该入口的空值仍发现全部配方；必要的工具准备提取属于局部职责调整，不增加另一套构建引擎或面向下游的引导层。

### fork 与可信源码身份

fork 能使用自己的普通分支完成计划、原生构建、运输、自动或手动发布，不要求修改源码中的上游仓库常量。可信源码仓库来自 workflow 的 GitHub 运行上下文，传入 CI 和发布校验；运输清单或发布 JSON 中自报的仓库名不是信任依据。

构建事件、实际 checkout、运行身份、所选 run/attempt、原计划及各平台运输输入仍须一致。自动发布只接受当前源码仓库的成功构建事件；手动发布只从当前源码仓库读取指定的成功 run/attempt。保留普通分支限制、提交匹配、artifact 来源和所选平台完整性检查，拒绝跨仓库输入、tag、PR 引用及混用其他运行的结果，不能通过取消校验来支持 fork。

发布目标仍由 `GITEE_REPOSITORY`、`GITEE_RELEASE_TAG` 和 secret `GITEE_TOKEN` 提供，不增加同义变量，不从 GitHub fork 身份推测 Gitee 仓库。原仓库与 fork 均须明确配置目标仓库和 tag，缺失或非法时在远端写入前失败，不回退到源码中固定的上游目标。并发组、入口注入与上传使用同一实际目标；同一 Gitee 目标的发布仍要求串行，不增加跨 GitHub 仓库的分布式锁。

专用元数据仓库的身份和白名单协议沿用统一交付契约。其 `upstream` 字段标识 xxautolib 协议所属项目，不充当本次构建来源；支持 fork 不据此迁移既有元数据、放松专用仓库检查或要求消费者追踪 GitHub 源码仓库。

### 安装结果运输与完整发布

各平台安装根及运输封装都包含源码版 `autolib.cmake` 和该宿主 importer；有库时再携带所选精确包及包级 latest。运输和汇总校验包括入口的固定路径、普通文件类型与本次原构建来源，不只检查库根。继续保留 Linux 执行权限、合法相对软链接、原始生产前缀、run/attempt 和所选平台完整性，原安装树与解包输入保持只读。

安装入口、运输中的入口与已核对原构建提交的 `src/autolib.cmake` 必须逐字节一致；沿用仓库对 `.cmake` 的 LF 检出规则，不接受平台改写。构建验证检查安装副本，发布准备在任何远端写入前检查全部运输副本与原提交源码；缺失、内容损坏或来源不一致均失败。最终入口以该源码生成注入副本，不能以重新取源码掩盖运输入口损坏。

包选择只发生在构建 workflow 的 `modules`。自动发布和手动 artifacts 发布都完整交付指定原构建的全部已验证结果：所选平台各自的 importer、单个入口，以及有效库闭包中按现有 publisher 规则可发布的资产。删除发布 workflow 的 `packages` 输入、`PACKAGES` 透传和发布准备中的二次筛选，不另增 `all`、单独 importer 或入口选择。需要另一交付集合时重新选择一次构建，不借发布端静默删包。

构建、运输、汇总、打包及发布准备都支持只有 importer 和入口的输入，不因缺少库包或库包 latest 候选而拒绝。多个平台的运输中各有安装入口，但最终清单只生成一个平台无关的入口附件；发布准备从已核对的原构建提交取源码入口，不从任意平台枚举结果或当前控制分支选择入口。

latest-only 保留为不上传资产的独立元数据操作，不读取构建输入，也不上传 importer 或入口。artifacts 发布仍可携带既有显式 latest 映射；首次初始化、成功项登记和指针更新规则不因取消包筛选而改变。工具专用发布不产生库包候选或隐式库包 latest，不把工具交付成功表述为任意库包已可消费。

### 地址注入与入口特殊附件

源码入口中的内部远程地址固定为空，本地安装复制此版本。发布准备沿用实际目标仓库和 tag，从原构建提交对应的入口生成上传副本，注入 `https://gitee.com/<repository>/releases/download/<encoded-tag>`。tag 按 URL 路径段编码，不硬编码上游账户或 Release tag；注入与上传必须使用同一经校验的目标。目标字段及编码后的地址须满足现有 CMake 和 importer 的消费解析规则，不能只验证字符串拼接。

入口使用独立内部变量 `_autolib_release_root` 保存发布地址，源码中恰有一处完整赋值行 `set(_autolib_release_root "")`，发布准备仅替换该完整行。注入点缺失、重复或默认值不是空值均失败，不匹配或修改旧用户变量及其他赋值。生成的 URL 必须能作为单个 CMake 字符串完整解析；拒绝未编码的 CMake 插值、引号、反斜杠、分号和控制字符，不能以宽泛正则替换后直接上传。受控测试通过 CMake 入口和 importer 核对最终消费地址，覆盖需编码 tag 与无效注入点。

CI 只改上传副本，不回写源码入口、生产安装树或运输解包输入。注入在固定待上传字节和计算发布清单摘要之前完成，上传检查针对改写后的实际文件，不能组合改写前摘要与改写后内容。所有资产最终在同一明确清单中按实际字节检查，不增加旁路入口上传步骤。

`autolib.cmake` 是固定名称、平台无关的 `entry` 类附件，不放入工具归档，不带库包身份或平台身份，不为各平台生成不同命名的入口。它与工具和库一样要求合法的本地文件路径、大小及 SHA256，并采用既有唯一同名附件替换、字节固定、上传与失败报告机制。

入口的 SHA256 用于核对发布清单与实际上传字节，不写入 Git 元数据，不生成独立远端摘要或 latest，也不扩大 Git 文件白名单。上传 worker 返回入口的真实结果；协调器把它计入 selected、uploaded、failed 和整体状态，但只为成功工具和库登记 Git 摘要。入口上传失败时整体发布失败，不能因工具或库成功而报告完整交付；其他成功项仍按既有规则登记。元数据 push 未确认仍失败，不增加跨附件事务、回滚、自动重传或恢复数据库。

完整发布约束的是本次尝试的资产集合，不是跨附件与 Git 的原子可见性。部分上传或元数据提交失败可能使新消费者暂时或持续无法接入；任务明确失败，调用方显式重跑同一原构建修复，不把成功项登记解释为整次发行已就绪。

初次入口下载继续依赖 HTTPS 下载信任；发布清单摘要不要求下游手填，也不能作为已认证入口的承诺。已有下游保留已下载入口时，继续使用其内部发布信息，不新增入口自动更新或发行锁定。

### 旧路径清理与保留边界

清理是本次实现和验收的一部分，不另设后续重构阶段。不保留停用开关、兼容参数、仅由旧测试调用的实现，或同一能力的新旧两条生产路径；也不以删除行数或文件数量为目标。按实际消费者确认删除范围，混合承载保留能力的文件只删对应部分。

| 退役能力 | 连带清理 | 必须保留 |
|---|---|---|
| 独立本地来源 | CMake 两个用户来源接口、importer 的 `--local-root`、来源解析和来源与缓存同根拒绝、来源优先级及其透传状态 | 入口真实路径解析、缓存检查、内部远端调用参数 |

| 仅供复制搬迁的参数 | importer 中失去实际用途的 `--cmake-command`、`--work-root` 及调用方透传 | CMake 自己的快照与结果工作目录、builder 打包仍需的 CMake 命令及路径修正规则 |
| 发布端二次选择 | `packages` 输入、`PACKAGES` 环境透传、available/chosen 筛选、单独 importer 选项及工具随库根可选的分支 | 原构建计划、所选平台和完整资产核对、any-any 唯一 publisher、latest-only |

| 空库集合导致零交付 | 丢弃所选平台、跳过工具运输或发布的判断和空库构建层 | 非空库的资格过滤、真实构建与消费验证、工具和入口的失败判定 |

本地来源专属测试、fixture、driver 模式和指南随对应能力退出；将独立安装消费和远端缓存复用的有效断言迁到新公共入口，不只删除失败测试。负例保留旧 CMake 用户变量不能改变来源或启用联网的验证，不为了验证旧能力不存在而保留旧实现。

`fixup-metadata.cmake` 和共享路径检查仍服务 builder 从运输副本打包，不能随 importer 的嵌入搬迁路径整份删除。远端安全解包、元数据树及结果检查、精确依赖和版本冲突规则仍有生产消费者，不因来自旧实现而删除；既有 GitHub 消费协议不属于本次顺带清理范围。移除代码不清理、迁移或改写用户已有安装、缓存、归档和远端资产。

## 备选方案

**要求下游复制源码入口并配置来源。** 可以复用独立来源复制流程，但每个项目都要保存和维护较长文件，且本地安装结果不能直接作为完整接入入口；选择安装入口自定位并直接 include。

**直接下载 Go 程序，或增加包装脚本和多级引导。** 首次获取仍须处理宿主识别、程序校验和 CMake 接入，把这些逻辑搬给每个下游或再增加一层交付不能减少接入负担；选择下载现有单文件入口，再由它引导当前宿主工具。

**一次分发所有平台程序。** 可以把平台判断推迟到本地，但增加不必要的下载体积和分发对象；选择入口按宿主只获取所需程序。

**从入口下载 URL 推导来源，或允许用户覆盖本地与远程根。** 会让消费依赖调用方的下载方式及额外配置，并重新引入本地结果意外联网和来源分歧；选择自身目录与 CI 注入信息，不恢复入口原始 URL。

**在源码中固定上游远程地址。** 本地缺失会转向远端，fork 也可能继续消费上游资产；选择源码为空、发布副本由实际仓库和 tag 生成。

**空输入表示全部包。** 默认运行可能触发全库编译，不能低成本单独交付工具；选择空输入只生成工具与入口，全量必须明确输入 `all`。

**保留发布端包子集筛选和单独工具选项。** 可以从一次较大构建中发布不同子集，但会维护第二份选择、重复解释工具是否交付，并允许发布结果偏离原构建集合。选择构建时选择一次，发布完整交付该运行已验证结果；独立 latest-only 不受影响。

**支持 fork 时取消来源校验。** 可以绕过固定上游仓库限制，但会把跨仓库、错误提交或混合运行输入当作可信产物。选择用当前可信 GitHub 运行上下文替代固定仓库常量，保留完整来源核对。

**保留旧实现作为兼容或备用路径。** 可以让旧调用继续使用独立来源与筛选，但会保留已经取消的能力、参数和测试，使流程收缩失去维护收益。选择按已取消能力整链清理，不兼容旧入口，也不删除仍有生产消费者的协议和安全检查。

## 验证

[自定位入口测试](../../../../src/autolib-importer/self_located_entry_test.go)验证旧普通变量、cache 变量及环境变量不能改变来源；缺工具、根包或精确依赖时本地入口失败且零网络。[本地原生闭环](../../../../src/autolib-importer/versioned_local_loop_test.go)通过普通根实际安装入口，独立消费者直接 include，验证 dep@1 头与机器码版本、导入及链接路径和运行加载位置；错头版本在编译成功后运行失败。重复消费不改安装。

[CI 计划](../../../../src/autolib-ci/plan_test.go)和[运输测试](../../../../src/autolib-ci/transport_test.go)覆盖三种选择、过滤、零库保留平台、可信 fork 上下文、精确运行身份及运输入口。普通根和工具专用入口都真实构建并安装原样入口，不用纯文本匹配替代工具执行；工具检查失败不能算作成功。

[发布准备测试](../../../../tests/ci/gitee-release/test_prepare_publication.py)覆盖目标配置、注入点与编码、所有运输对原提交字节核对、输入只读、多平台工具及唯一入口；真实 builder 验证普通库及工具专用重打包。[上传测试](../../../../tests/ci/gitee-release/test_publish.py)通过真实 main、HTTP multipart 和本地裸 Git 验证入口成功及失败、其他成功项登记、无入口元数据和 push 未确认失败，不访问真实 Gitee。

[生产到消费联动](../../../../tests/ci/gitee-release/test_entry_delivery.py)复用[远端原生闭环](../../../../src/autolib-importer/versioned_remote_loop_test.go)，以 `controlled-fork/source` 构造已验证原构建运输，调用生产 `prepare_publication`，从返回清单读取真实唯一入口及工具、dep@1/2、probe@1 资产，核对最终大小和 SHA256。受控 Git/HTTPS 实际观测 `fixture/mirror` 与 `中文/release` 对应的 `%E4%B8%AD%E6%96%87%2Frelease`，工具引导和 importer 库下载都命中该地址，不由测试重新注入入口。

109 上联动 Python 1/1、Go RemoteLoop 的 GitHub/Gitee 两子项及 LocalLoop 均通过。每托管首次 clone/ls-tree 各 1、HTTPS 3 次，随后完整缓存、损坏已有候选拒绝及迁移离线消费增量均为 0。新 dep@2 请求和错误包内身份各取新快照，最终每托管 clone/ls-tree 各 3、下载 5、API/Raw 0；真实链接与运行来自当前 dep/1、probe/1，错误身份在 adapter 前拒绝。生产安装、运输、元数据、精确依赖及无关缓存的内容与权限保持不变。

这些结果只覆盖当前 Linux x86_64 原生工具和受控 fork/Git/HTTPS。真实 fork Actions、新入口的 Windows x86_64、Linux aarch64 及真实 Gitee 发布消费未执行；旧交付的用户验收不替代这些专项。执行环境及最低 CMake 政策由[开发指南](../../../development.md#远端构建与源码传输授权)拥有，不宣称最低版本已实测。退役核对保留协议身份、负例、builder 路径修正与安全检查，不清理用户既有安装或缓存。

## 影响

入口目录也是唯一缓存根，需要补包时必须可写；多个消费者引用同一入口会共享该根的缓存及 latest，不获得每工程独立缓存。已有同根写入串行约束保持不变，不增加缓存锁或恢复数据库。失去可配置来源是有意的接口收缩，不承诺旧变量、旧来源复制流程或历史消费者兼容。

同名入口附件更新不是不可变发布。已有下游保留下载的入口就继续使用其中的发布信息；本设计不增加入口自动更新、发行锁定或供应链签名。工具和包的 SHA256 不认证首次下载的入口本身，也不证明 ABI 兼容。

CI 与发布链路不能再以“是否存在库根”判断平台、工具及上传是否有工作，否则会出现成功但没有交付物的结果。取消发布二次筛选后，不能从原构建临时摘取子集；需要不同集合时必须重新选择构建。包资格过滤后的工具交付也不证明用户请求的库已经交付。

fork 的可信源码身份与 Gitee 发布目标是两个独立事实；支持 fork 不意味着自动获得目标权限或匿名可访问性。新建 Gitee 仓库仍可保持私有，公开仍由所有者负责；不同 GitHub 仓库若共用同一 Gitee 目标，须由调用者满足串行约束。

本文记录已实现行为及上述受控证据，不授权 push、触发 CI、上传附件或修改远端仓库，也不表示真实托管或未测平台已经验收。发布仓库 README 内容仍独立待讨论，不以生命周期更新代替用户决定。
