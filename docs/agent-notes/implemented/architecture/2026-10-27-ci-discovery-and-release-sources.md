# Agent Note: CI 自动发现与双平台 Release 消费

Status: implemented

## 问题

本地构建按模块声明发现包，但 CI 的选择、依赖闭包、发布文件名及消费验证仍限定 queue、lz4、flann。新增 adapter 不能自动获得 CI 发布资格，固定的两层执行步骤也不能覆盖更深的依赖链。没有 adapter 的模块只具备本地构建能力，不应消耗二进制发布 CI 的编译资源。

消费入口默认指向 Gitee，但首次 importer 引导与 importer 的远端获取只支持 GitHub。Gitee 镜像已经供给工具和库包，消费者仍不能使用默认来源。两平台的资产 API 和摘要来源不同，将判断散布到引导、包遍历和下载中会增加维护成本；首次工具引导又不能调用尚未取得的 importer。

## 决定

CI 按模块声明和 adapter 自动选择具备二进制交付条件的包。消费端以小型来源适配层集中处理 GitHub、Gitee 差异，共用下载及包准备能力。CI 调整、Gitee 工具引导、库包下载及正文 SHA256 校验作为单阶段完整交付，不提供先下载执行、后补摘要校验的中间能力，不改变公共消费接口。

### CI 发现与静默过滤

本地继续发现 `src/dependencies/*/module.toml`，不因缺少 adapter 改变普通构建行为。CI 使用相同目录匹配，并增加同目录 `autolib-import.cmake` 文件检查；不维护包名白名单，不引入资格数据库、单独发布配置或复杂发现框架，也不为本次任务批量补 adapter。

模块输入留空时选择全部发现的候选，显式列表仍可选择子集。存在模块声明但没有 adapter 的项目静默忽略，不输出警告、不生成失败结果，也不使最终汇总失败；显式选择此类模块同样过滤。未知名称、列表格式错误、声明损坏等输入错误不属于这一例外，仍明确报错。

builder 的既有只读模块描述继续拥有声明解析及依赖闭包，CI 不解析 TOML。CI 根据描述中的 adapter 与依赖信息过滤：自身或任一传递依赖没有 adapter 的根包不进入执行集合；仅为被过滤根包引入、且没有其他有效根包需要的依赖也不构建。过滤按实际目标平台处理，不以某个平台的成功替代另一个平台的声明有效性。缺少 adapter 及其导致的根包排除均不计为失败，不增加逐包跳过报告。

最终构建集合仅包含有效根包及其完整依赖闭包，共享依赖只执行一次。所有请求都被上述过滤排除时，本轮为无工作成功，不创建或修改 Release，也不为其启动平台生产和 importer 发布。最终汇总只要求执行集合中的构建、验证及应有上传完成，不拿过滤前的请求数判断结果缺失。

依赖层由现有拓扑信息计算，顺序执行全部实际非空层，不限定 layer0、layer1，也不引入后台调度器。平台、原生环境、公共并行预算、唯一通用包 publisher、提交身份、发布授权和固定 Release 串行规则保持不变。publisher 的选择根据实际是否存在平台无关包，不绑定 queue 名称。

上传检查从固定库名列表改为本次有效计划、包身份及正式资产命名规则，继续验证实际文件名、字节摘要和远端上传响应，不放开任意文件上传。消费验证也不能再以固定三库名单作为合法输入；新增 adapter 复用统一的实际导入、链接和适用 ABI 检查，现有三库的行为验证继续保留，不要求每个新包建立独立测试工程。adapter 存在只代表进入 CI，不保证其构建或消费必然成功。

计划阶段只检查模块声明、依赖关系有效性及 adapter 是可读文件，不执行或静态分析任意 CMake 正文来猜测消费目标。目标是否存在、实际链接及适用的运行检查由消费验证负责；损坏的 adapter 仍是实际故障，不转为静默过滤。

只有没有 adapter 的资格过滤采用静默语义。实际构建、打包、验证、上传及共享环境失败仍按原有 CI 规则报告，不把这些错误转成过滤，不提供任意执行故障下的继续调度机制。workflow 名称和独立同步的订阅关系保持不变，不因扩充包集合破坏已有 Gitee 同步触发。

### 小型来源适配层

importer 在需要远端时识别来源并选择 GitHub 或 Gitee 实现。平台实现分别负责地址解析、Release 与附件 API、候选身份检查、下载地址及预期摘要的提取；共用流程负责传输、下载字节摘要比较、安全解包、包头检查及依赖遍历。平台判断集中在选择入口，不散布在每个包或依赖处理中。不增加动态插件、注册中心、通用能力协商或新配置层。

GitHub 保留公开 Release tag URL、唯一匹配资产、uploaded 状态及原生 SHA256 要求，不因接入 Gitee 降低 GitHub 的检查。Gitee 接受当前默认的 `https://gitee.com/<owner>/<repo>/releases/download/<tag>` 来源根，从对应 tag 的 Release 与完整附件列表中选择既有固定文件名；不开放任意下载 URL、latest 或自动跨平台回退。

一次获取使用同一轮来源元数据，校验所选 Release 与 tag、附件名称、有效 ID 及可用下载地址。Gitee 所选附件必须唯一，目标平台包和 any/any 包仍遵守原有候选冲突规则；接口错误、找不到资产、同名重复或不完整结果直接使消费失败，不当作离线可用或自动换源。Gitee 请求不使用同步 workflow 的写令牌，不给消费者引入 Python、Go SDK 或外部下载器。

原始 API 响应继续仅在本次 configure 内共享。快照明确绑定来源及平台，平台适配负责解释，公共包流程不读取 Gitee 正文或 GitHub 专用字段；不同来源的快照不得混用。CMake 首次引导已经取得的元数据交给 importer 复用，避免工具和每个库包分别重新枚举全部附件，不增加持久发行清单、索引服务或跨 configure 的远端有效性状态。

### 单文件 CMake 引导

保留 `autolib.cmake` 单文件分发及现有公共接口。CMake 在远端引导时只分派一次平台，平台函数提供宿主工具归档的下载及校验信息，共用现有 FetchContent 下载、原生解包、预期程序检查及执行流程。Go 端负责后续库包消费，不在 CMake 中复制依赖下载引擎；必要的工具元数据处理是首次引导的独立职责，不以旁置 helper 或下载未校验脚本转移它。

本地程序、本地归档、配置远端的既有优先级保持不变。只有候选不存在才继续，已有坏程序、坏归档或不完整包直接失败；显式关闭远端及本地齐全时仍不联网。来源首次加载捕获、工作根、目标与宿主平台区分均保持不变。

### 完整交付与摘要要求

一次交付完成 CI 自动发现、静默过滤、实际依赖层执行、小型来源适配，以及 Gitee 首次 importer 引导和后续依赖包下载。GitHub 保留原生摘要检查；Gitee 工具与库包从接通起就要求有效正文摘要，HTTPS、附件身份及归档结构检查不替代下载字节比对，自行计算摘要也不替代预期值。

Gitee 来源适配从 Release 正文提取预期摘要，覆盖首次 importer 归档和后续库归档。复用同步端已有的标记、`files`、完整附件名、`sha256` 和 `gitee_asset_id` 格式，不新增 sidecar 或第二套索引。选中项的 ID 必须与当前附件一致，摘要必须为有效 SHA256；下载字节校验通过后才允许解包准备或执行工具。索引缺失、非法、选中项缺失、ID 不一致或字节不符均失败，不按名称或大小降级放行，也不提供关闭校验开关。

两平台适配均向共用下载流程提供下载信息与必需的预期 SHA256。正文解析属于 Gitee 实现，不进入通用包遍历；CMake 负责工具归档，Go importer 负责库归档，两者采用相同来源及摘要协议。平台差异集中于来源实现，共用下载和校验流程不含逐包的平台分支，不提供免校验的过渡路径。

正文摘要来自拥有 Release 写权限的同步程序或维护者，不是 Gitee 原生计算的内容摘要，也不认证发布者。消费校验会比较实际下载字节，可以发现索引未改而附件内容变化；不能防止攻击者同时篡改字节和正文。现有本地完整目录的复用规则不变，不因为接通远端校验而自动重新下载或散列历史目录。

### 设计归属与操作范围

本决定部分替代 [CI 系统设计](2026-10-20-ci-system.md)的固定代表集、两层执行和包名限定，不替代其环境、权限、并行及真实消费要求。[按目标导入与 Release 消费设计](../../proposed/architecture/2026-10-25-target-import-and-release-consumption.md)继续拥有公共接口及来源优先级，本决定拥有其 Gitee 消费与双平台适配。[importer 压缩分发设计](../../proposed/architecture/2026-10-27-importer-distribution-and-branch-release.md)继续拥有工具归档及原生解包格式。

[独立 Gitee 同步设计](../../proposed/architecture/2026-10-27-gitee-release-sync-workflow.md)继续拥有镜像写入、正文格式、去重信任前提与网络并发。本决定只消费已有供给，不改同步逻辑、写入凭据、触发条件或重试次数。正文索引的消费协议由本决定拥有，不从同步成功推定消费可用。

当前架构、开发和测试指南记录实现及验证边界。本地实现不代表真实远端验收；真实远端上传、push、触发 CI、合并和 Release 修改不在本设计授权范围内，需要另获明确授权；受控本地验证不覆盖现有消费输入或正式资产。

## 备选方案

**手工扩大代表包白名单。** 可以逐库控制，但新增 adapter 后仍需修改多处名单，不能达到自动发现目标；采用目录发现加存在性过滤，资格随包本身维护。

**CI 编译全部本地模块，再跳过无法打包的包。** 覆盖本地构建，但消耗无 adapter 模块的编译时间；CI 在执行前过滤，本地发现范围不变。

**缺少依赖 adapter 时使计划或最终汇总失败。** 能突出资格缺口，但会让未进入交付范围的包阻断独立包；自身及依赖链不齐全的根包静默不参与，不产生失败记录。

**在公共下载和包遍历中逐处判断平台。** 初始修改直接，但正文摘要加入后会让平台规则牵连共同流程；集中到两个具体来源实现，保留一处选择，不扩成插件系统。

**先接通 Gitee 下载，再补正文摘要校验。** 可以分别观察下载与校验，但会产生未做预期摘要校验的工具执行路径，并要求维护临时例外。下载与正文协议已有共同来源适配边界，选择一次交付完整能力，以实现任务的定向测试区分问题，不保留免校验过渡路径。

## 验证

- CI 的发现、静默过滤、共享闭包、空工作和实际三层执行由 `TestCIDiscoveryFiltering`、`TestCIDynamicRelease` 等 fixture 验证，使用真实 builder、消费链接及受控发布请求；通用 publisher 与正式资产摘要仍受计划约束。
- Go 与 CMake 消费同一组来源、正文索引和选择向量。CMake 的固定 schema 原始 token 检查拒绝重复及转义等价键、非标准 JSON、非正整数 ID 和额外字段；原生 `string(JSON)` 成功不能单独证明严格语法。
- Windows x86_64、CMake 4.2.3 的 TLS fixture 从空根引导当前 importer，跨两页读取附件，两次导入完成传递依赖准备、实际编译链接及运行；后续 configure 本地齐全零请求。内容不符的包不提交，显式新 configure 重新枚举后可成功。
- 工具 fixture 核对正确宿主名、摘要、索引缺失、选中项缺失、ID 不符、重复附件、证书、下载及解包失败，错误工具不提交、不继续加载 adapter；GitHub 摘要、本地离线和坏候选不回退由同组入口回归保留。

Linux x86_64、Linux aarch64、最低 CMake 3.20、真实 Gitee 完整消费及新 CI 发现策略的真实远端运行没有本轮验收证据。现有生产 Gitee importer 属于较早协议；完整网络验证需要另行授权发布匹配 `--source-response` 的工具，不能用只读 API 探测、镜像成功或替换现有本地程序代替空根引导。既有三平台代表库的历史运行仍由各自设计拥有。

## 影响

静默过滤会让部分请求不产生资产，这是有意选择的资格语义，不是发布失败。adapter 存在但损坏、声明无效或运行失败不能按同一规则吞掉；否则会把真正的交付错误藏起来。

新增 adapter 会自动进入 CI，可能暴露平台来源、系统依赖、ABI 或链接问题并增加运行耗时；不以自动升级工具链、批量适配库或放松发布验证处理。固定槽仍是逐资产供给，成功上传不依赖全局清单，发布及镜像之间仍可能有短暂不一致窗口。

CMake 首次引导与 Go 消费需要维护相同的来源和摘要语义。共用协议测试向量覆盖来源 URL 与 tag 编码、候选唯一性、附件身份、摘要格式和拒绝语义，不仅验证正常下载；不要求两套原生 HTTP 栈的所有行为一致，也不以引入消费者额外依赖或两套大框架消除这项必要重复。正文及附件不是事务快照，ID 或摘要不一致时失败并允许显式重试；显式重跑重新枚举，不持久标记为永久损坏，不增加自动恢复服务。
