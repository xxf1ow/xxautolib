# Agent Note: 构建缓存记录迁入 Gitee 独立分支

Status: implemented

## 问题

每个平台相关库版本在四个平台发布时，GitHub Release 需要保存四份归档及四份 `publication.json`，通用包则保存一对附件。记录提供构建来源、输入指纹、验证归属和归档绑定，不能仅凭归档名称重建这些事实；但将记录作为独立 Release 附件，会增加附件数量、分页和逐记录下载请求。用户要求只调整这些记录的存放位置，保留已构建成品的价值。

Gitee Git 已承担消费元数据的读取和提交，现有真实运行有成功依据。OpenCV、ONNX Runtime 的近期失败发生在 Gitee Release 附件上传阶段，不能据此认定 Git 提交不稳定。本方案接受构建缓存开始依赖 Gitee Git，不以切换 SSH、延长附件超时或调整镜像策略解决本次问题。

## 决定

GitHub 源码仓库的固定 `autolib-cache` Release 继续保存原名的库 `.tar.zst` 和 importer `.tar.xz`。完整构建记录移入现有 Gitee 产物仓库的固定 `autolib-cache` Git 分支，继续通过 HTTPS 和 Token 认证。Gitee 默认分支继续保存消费 JSON、latest 和原有仓库身份，消费者不读取缓存分支。

现有记录已完成一次性搬迁，GitHub 中对应 JSON 附件已移除；新构建逐项将记录提交到 Gitee，构建和独立同步通过新存储验证、复用及清理缓存，各平台并发提交保留其他身份的记录。归档内容、生产输入指纹、第三方配方、平台资格、consumer schema 2 和公共 CMake 接口保持原有约定。

### 决定归属

本记录只替代[Release 成品缓存与独立同步](../../implemented/architecture/2026-11-09-release-cache-and-independent-gitee-sync.md)中的构建记录存储、相应读写及清理交接，不替代逐项失败隔离、链式失效、源码清理依据、平台与运行互斥。该记录保留活跃状态。

本记录调整[双来源交付](../../implemented/architecture/2026-11-09-dual-source-artifact-downloads.md)中构建记录的来源位置，不替代消费 JSON、完整记录相等判断、100000000 字节阈值、上传与消费行为。该记录继续拥有双来源协议并保留活跃状态。两份既有记录均已更新存储事实，并与本记录交叉链接。

### 分支与文件

现有 Gitee 产物仓库由 `GITEE_REPOSITORY` 指定；不增加第二个仓库配置、分支选择参数或新的凭据类型。缓存分支名固定为 `autolib-cache`，与 GitHub Release tag 同名但属于不同托管和引用空间。

缓存分支采用独立根提交，不从默认分支复制消费树。分支根只保存 `.autolib-cache.json` 和 `<完整归档名>.publication.json`。身份 JSON 包含三个固定字段：`type` 为 `xxautolib-build-cache`，`schema` 为整数 `1`，`upstream` 为 `https://github.com/<可信源码仓库>`。可信源码仓库来自现有 workflow 运行上下文，不能由记录自行认领。

每份构建记录继续使用现有 schema 1 和完整字段：精确包或 importer 身份、归档 asset ID/名称/大小/SHA256、原始生产仓库和提交、run/attempt、输入及精确依赖指纹、验证归属和证据路径、latest 候选；importer 保留原始入口内容和摘要。不写入 Gitee 镜像完成标记、重试队列或消费 URL。

只接受符合现有身份和命名规则的普通文件，拒绝软链接、gitlink、非法路径及大小写碰撞。身份或树结构错误使本次缓存操作失败，不解释成空缓存；单份记录的内容或归档绑定无效时，继续按项报告不可复用。既有同名分支必须通过身份和树校验，不能覆盖或重置不认识的分支。

构建 workflow 的共享准备步骤确认目标仓库并初始化缺失的缓存分支，之后才启动平台写者。已有产物仓库及其默认分支身份沿用原有校验，缓存分支初始化不重置默认分支、不改仓库公开设置；不存在的目标仓库明确报错，本次不增加构建端自动建库机制。已有独立同步的建库职责不改写。

### 职责与认证

| 组件 | 本次职责 |
| --- | --- |
| `autolib-ci` | 统一读写缓存分支、校验构建记录与 GitHub 归档、管理归档上传下载及缓存清理 |

`GITHUB_TOKEN` 继续负责 GitHub 归档操作，`GITEE_TOKEN` 复用于缓存分支 Git 认证，`GITEE_RELEASE_TAG` 仍只属于附件同步。HTTPS Git 使用非交互凭据交付，不将 Token 放入 URL、命令行、记录或日志。现有凭据过滤继续覆盖第三方配置、构建和普通验证子进程；需要 Git 认证的缓存操作只在其专用子进程取得凭据。Windows 和 Unix 的认证入口均通过宿主定向测试，证据见下文。

### 读取与缓存判断

构建共享准备和独立同步各取得本次固定的缓存分支提交，完整读取记录并保存对应提交身份；平台任务复用构建准备得到的快照。每次入库或删除重新核对受影响身份的远端事实，以处理其他平台在准备之后新增的提交。一次操作中的快照不是长期完成状态，不新增缓存数据库。

GitHub 归档列表继续完整分页读取。只有记录合法、来源正确、输入及依赖指纹符合当前源码、绑定的归档 ID/名称/状态/大小/摘要有效，才允许复用或同步。记录与归档缺一不可，不因缺少记录就从名称猜测生产来源，不从 Gitee 消费 JSON 反推构建指纹。没有归档但仍合法的构建记录保留清理归属，不作为可消费候选。

正常代码只从 Gitee 缓存分支读取构建记录，不回退 GitHub `publication.json`。分支查询失败、认证失败和服务不可达必须明确报错，不能把它们解释为分支不存在并重建。GitHub Release 容量预检改为只为新归档预留附件名，仍计入远端实际存在的全部附件，不假设未知文件已经清理。

### 逐项入库与失败

一个产物的顺序为：本地验证和打包完成，上传或确认 GitHub 归档，再提交绑定该归档的 Gitee 构建记录。记录 push 确认后才报告 `stored`；有效缓存命中仍报告 `reused`，不改写原生产来源。记录迁移和缓存协调工具修改不进入库或 importer 的生产指纹；不通过整体源码 SHA 使现有成品失效。

同名归档替换继续只操作该精确受管身份，先完成本地准备再删除旧归档、上传新归档，最后更新对应记录。旧记录可以保留到替换记录提交成功，但旧 asset ID 不能绑定新归档，期间不可复用；新归档上传失败时不伪报旧记录仍有效。保留原有同名残留、歧义附件和上传响应不确定的处理，不增加跨托管事务或回滚。

GitHub 上传成功而 Gitee 提交失败，该项仍报告失败，其他已完成项不回滚，逐项失败隔离及依赖阻断沿用现有规则。后续运行重新读取实际记录和归档，不承诺凭一个缺少构建记录的归档免编恢复；沿用现有缺失或失配项重新准备的方式，不增加第二套持久化恢复记录。

### 多平台提交

继续由现有计划保证每个完整归档身份只有一个写者，`any-any` 只有一个 publisher；跨 run 构建、归档替换及同步清理继续使用现有 workflow 运行级互斥。各平台可向同一缓存分支提交不同文件。

一次记录更新或删除最多尝试三轮普通 push。每轮基于最新远端提交，只应用本次选中的文件，不合并或推送整个旧工作树。非 fast-forward 后重新读取；其他文件变化可以重放本次修改。如果选中文件相对本次操作基线发生不同改动，则报告该身份冲突，不覆盖其他写者。目标记录已经与本次期望完整语义相同，或待删除记录已被确认删除时，可作为相同结果处理。

push 响应不明确时重新读取远端，核对选中记录及归档绑定，确认本次结果已经存在才报告成功；未确认时在上述轮数内重新判断，仍不确定则失败。认证、非法树及同项冲突不作为普通分支推进盲重试。不强推、不改写远端历史、不引入跨机器锁服务。Git 操作接入现有调用上下文；GitHub 归档请求保留现有 HTTP 重试策略，不另建通用网络恢复层。

### 独立同步与清理

独立同步从缓存分支记录与 GitHub 归档生成原有缓存交接快照，继续依据源码指纹选择有效项，再按现有规则上传 Gitee 附件及提交默认分支消费 JSON。构建记录存在不代表 Gitee 附件已经上传；附件失败不得以构建记录替代消费确认。默认分支 Git 锁、逐项提交、importer 与唯一入口的关联顺序、阈值和失败传播不变。

源码仍是版本、平台及删除范围的事实来源。缓存清理由同一个 CI helper 核对并删除 GitHub 精确归档，归档删除确认后再删除缓存分支的相应记录。GitHub 删除失败保留记录；记录删除失败时报告错误，保留的孤立记录用于下次确认和清理，不成为有效缓存。Gitee Release 附件及默认分支消费记录的清理顺序沿用现有同步规则，不因这次存储迁移扩大删除集合。

### 数据切换与范围

一次性搬迁保留了所有可验证记录的原始字节、旧版本及原生产身份，不按当前指纹筛除合法旧记录。旧 JSON 的删除以无运行或排队的旧写者、新源码已可用于 workflow、Gitee 逐项回读一致及源附件身份未变为条件；未知文件、异常项和归档均受保护。最终清单与原始备份保留在本地忽略目录，产品不提供长期迁移命令或旧协议双读。

切换对象为 `xxf1ow/xxautolib` 的 `autolib-cache` Release 和 `xxf1ow/autolib-release` 的同名 Git 分支。Gitee 默认分支、公开设置、已有消费 JSON、latest、Release 附件和发布入口保持原状。产品修改限于相关 CI 工具、workflow、Python 缓存交接、测试和事实文档；OpenCV/ONNX 附件上传优化、大小阈值、镜像地址、双来源策略、第三方升级和新增回归 CI 均不属于本次改动。

## 备选方案

**继续逐归档保存 Release 附件。** 已有实现能隔离各项写入，但四平台包版本需要八个附件，并产生逐记录请求；不能达到此次减少 Release 附件的目标。

**每个平台或整个 Release 保存一份聚合索引。** 可以减少附件，但平台索引仍需逐项读改写，总索引还让四个平台竞争同一个文件。用户已选择将记录移入现有 Gitee Git，不为减少附件另维护聚合协议。

**在 Gitee 默认分支增加构建记录目录。** 一次克隆可取得全部记录，但构建与消费提交共用分支，需要修改消费树白名单，并让构建记录格式和写入故障影响消费元数据处理。采用独立分支，保留消费者默认分支和校验协议。

**改用 SSH。** 没有已观察到的 HTTPS Git 故障证明需要更换协议；还需新增密钥和主机身份配置，也不影响 Release 附件上传路径。沿用已使用的 HTTPS Token 认证。

**只迁移未来记录或长期双读。** 前者会让现有归档缺少新存储中的构建依据，后者长期维护两套发现和写入规则。采用校验后的一次性搬迁，保护异常项，不为过渡保留运行时兼容层。

## 影响

Gitee Git 成为构建缓存的必要依赖，GitHub 归档可访问但 Gitee 不可用时，新构建和同步可能无法判断或完成缓存入库。已准备的下游本地缓存不因此失效。本方案接受这一依赖，以换取 Release 附件和读取操作的减少；不承诺 GitHub 构建缓存能够脱离 Gitee 独立运行。

跨托管写入没有原子事务。归档替换、记录提交和消费 JSON 更新仍存在暂时不匹配窗口，失败可延续到显式重跑；记录绑定和摘要校验负责拒绝不匹配内容，不保证旧归档持续可用。三轮并发提交预算也可能耗尽，届时明确失败，不增加无限重试。

独立分支会积累记录变更历史，少量 importer 入口内容也随完整记录保存；不在本次增加压缩历史、轮换分支或垃圾回收服务。新分支的误删除和权限撤销仍可能使缓存不可用，不增加自动重建生产证明的机制。

已观察到的 OpenCV、ONNX Runtime 附件上传失败不由本方案修复。记录搬迁不能被当作该上传问题或双来源真实消费已经验收的证据。
