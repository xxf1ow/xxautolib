# Agent Note: 仓库基础设施与验证授权

Status: implemented

## 问题

仓库需要可独立准备和检查的开发起点。库专用规则分散在按文件类型划分的顶层目录，会使维护一个库时跨目录寻找相关内容；未经确认的 recipe 表达方式也不应成为基础设施的隐式前提。

## 决定

目录按维护对象划分：通用构建代码归 `src/build_system/`，库声明、补丁和专用执行脚本归 `src/dependencies/<库名>/`，测试对应放在 `tests/build_system/` 与 `tests/<库名>/`。根 CMake 以参考入口为基线，只适配项目名、最低版本、公共入口路径和范围内的调用，不顺手整理、重构原文。编译设置、摘要、模块选择及加载骨架保持原有组织，不以基础设施适配定义 recipe API。

每份工作副本只使用根目录 `.venv/`，Python 版本、环境创建、依赖解析与执行统一由 uv 管理。Python 工具环境不随某个库的编译配置变化，所以无需为每个构建或库重复创建环境。锁文件纳入版本控制，配置失败不回退到系统 Python。

当前架构、开发命令、测试命令分别由普通文档拥有；本记录保存理由与授权。普通文档预算位于 `scripts/doc-budgets.manifest.json`，按各页内容设置并保留至少 5% 余量；预算是防止无关内容累积的护栏，不以压缩字数为目标。

## 验证授权

Linux 验证设备为 `lxx@192.168.0.127`，限定工作目录 `/home/lxx/xxautolib`。用户永久授权将本仓库任务相关源码传输至该目录，并在其中配置、编译和测试；允许公开记录该账号、局域网 IP、路径及授权，无需重复询问。该设备为局域网内安全可信设备。

传输前检查目标已有内容并保留无关数据，不清空目录，不传输凭据、私有仓库历史、宿主 `.venv/` 或 Windows 构建产物。该授权不包含其他机器、其他目录、Git 推送、远端 CI 或托管平台写操作，工具实际权限仍按执行环境审批。

第三方包统一先在 Windows 下载并核对来源、固定版本及摘要，再传入上述 Linux 工作目录，避免设备反复联网重试。输入包括源码归档、仅含上游历史的 Git bundle 和平台所需的上游内部下载缓存；接收端再次校验摘要或固定提交。此规则不授权传输本仓库 `.git/`、凭据或 Windows 二进制产物，不改变模块声明的上游来源及原生校验机制。

## 备选方案

**按文件类型拆分库内容。** 将 recipe、补丁和库专用 CMake 脚本分别放入顶层目录，便于按语言查找，却增加单库维护的跳转成本；本项目选择按库集中。

**每个 build 创建 uv 环境。** 相同 Python 工具依赖会重复准备，且增加测试与开发脚本的环境选择成本；单工作副本根环境足以覆盖当前需要。

**直接沿用其他分支的完整实现。** 已有结果可以提供技术可行性的参考，但不能代替目录和 recipe 可读性的确认；基础设施不绑定该实现。

## 影响

根 CMake 启用 C/C++ 编译器，公共入口探测依赖并同步 uv 环境；空模块配置需要可用工具链，但不证明任何库构建通过。基础入口、构建摘要、缺失模块和环境失败边界由定向测试覆盖；Linux 授权不是平台验证证据。v142 实机一致性检查由后续人工验收，不阻塞开发，不以 v143 成功替代。

根入口发现按库目录组织的 TOML，通过公共引擎生成并加载原生 ExternalProject 声明；模块格式、执行规则与验证由[流水线设计](../architecture/2026-10-19-toml-externalproject-zlib.md)拥有。本记录不定义模块 API，也不承诺下游消费接口、发布流程或已有安装树兼容。
