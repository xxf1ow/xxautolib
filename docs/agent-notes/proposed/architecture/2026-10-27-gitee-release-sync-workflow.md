# Agent Note: 独立 Gitee 同步与正文摘要索引

Status: proposed

## 问题

GitHub 已有固定 Release 供给，Gitee 镜像需要独立重跑，不能让镜像网络耗时占用原生构建 job 或影响已经完成的 GitHub 发布结果。GitHub runner 到 Gitee 的连接可能很慢；全量重传会让只更新一个包的操作承担全部附件的传输成本，逐附件串行查询和上传又会累计网络等待。

Gitee 附件 API 不提供原生 SHA256，不能只凭文件名或大小跳过同名附件。Release 正文可以单独读取和更新，适合保存由同步程序维护的摘要索引，使全量检查仅传输实际变化的附件。该能力依据已核对的 [Gitee OpenAPI](https://gitee.com/api/v5/swagger_doc.json) 5.4.93；读取正文及附件列表的匿名请求不下载附件字节，正文更新仍待获授权的真实写入验收。

## 方案

增加独立同步 workflow：批量读取两端 Release 元数据，对比 Gitee 正文中的摘要索引，按 runner 可用 CPU 数的两倍并发处理变化附件，最后集中保存成功项并汇总失败。本轮交付同步能力，不接通 importer 或单文件 CMake 入口的 Gitee 消费，不改变包格式及来源默认值。

### 设计归属与参考范围

本文拥有独立同步入口、正文索引、跳过条件、附件并发、网络等待与验收规则，部分替代[按目标导入与分阶段 Release 消费](2026-10-25-target-import-and-release-consumption.md#独立同步-workflow-的交接约定)中“不以另一份持久化清单判断完成状态”的约定：允许在 Gitee Release 正文保存附件摘要索引，但不增加独立 manifest 资产、摘要 sidecar、恢复队列或跨运行生产缓存。该整体设计继续拥有消费接口、默认来源和后续 Gitee 消费阶段；[CI 系统设计](../../implemented/architecture/2026-10-20-ci-system.md)继续拥有原构建、GitHub 发布、平台环境和 finalize。

本地 Action 使用 [action-gitee-release](https://github.com/nICEnnnnnnnLee/action-gitee-release/tree/44b412edade0c837fb0ad7d73f4674ec07c8b722) 的固定提交 `44b412edade0c837fb0ad7d73f4674ec07c8b722`。先原样引入 `.github/actions/gitee-release/`，保留来源、许可和依赖记录，以受控请求验证原始入口，再最小适配。`feat/gitee-release-mirroring` 分支中的原样基线提交 `8845d6a`、后续 Release 创建或复用、同名删除上传及测试可作参考；不整体搬入平台 job 接线、autolib-ci 的镜像实现、网络对照实验或逐资产诊断框架，不以重写参考本体为接入目标。

Python、上游依赖及同步实现仅在独立 workflow 使用，不加入 builder、importer、autolib-ci 或普通本地构建。同步协调代码归本地 Action，workflow 仅负责触发、输入、环境、权限和运行级串行，不新建通用发布框架。

### 触发、来源与权限

新增 `.github/workflows/sync-gitee.yml`，使用单个 `ubuntu-24.04` job。自动入口监听 `Representative releases` 的 `workflow_run: completed`，仅本仓库上游运行成功时执行；原构建、消费验证及 finalize 全部成功结束后才启动，不修改原 workflow 的发布循环或成功判定。自动入口使用默认分支上的同步代码，不检出上游任意分支代码，不执行上游 artifacts；workflow 文件进入默认分支是自动触发启用前提，遵循 [GitHub workflow_run 规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)。

保留 `workflow_dispatch` 手动入口，可在不重编译的情况下按包名或全量同步。同仓库分支手动运行使用所选分支的事件提交，拒绝 tag 和 PR ref。选择该分支即允许其同步代码在同步步骤中使用 `GITEE_TOKEN`；该代码实际能够读取或向外部发送令牌，操作人必须先信任所选提交，日志脱敏不构成代码沙箱。本轮接受此权限模型，不限制为只执行默认分支代码。手动入口和自动入口共享来源、筛选、索引与上传实现。

来源固定为本仓库 `xxf1ow/xxautolib` 上已有的 GitHub Release，tag 使用本轮解析的 `GITEE_RELEASE_TAG`，默认 `autolib-release`；目标为 `GITEE_REPOSITORY` 中同名 tag 的 Gitee Release，仓库默认 `xxf1ow/autolib-release`。两个变量在任务开始时解析并固定。非法配置失败，不回退其他目标。来源不是构建 artifact、工作目录、latest 或另一份独立配置的 GitHub tag；来源 Release 不存在时失败，不创建来源 Release。

Gitee Release 由协调器在并发任务开始前创建或复用，只有一个初始化者。首次远端写入前必须完成配置与包名输入校验、来源列表完整读取、所有指定项匹配，以及所选来源附件的名称、唯一性、状态和摘要校验；远端写入包括 Release 创建、附件删除或上传、正文更新，只读查询可以提前。创建前确认 Gitee 认证身份、目标仓库及其有效默认分支；已有 Release 不改 tag 指向。只把已核实的按 tag 查询 `200` 且 JSON 为 `null` 视为缺失；认证、网络、格式及其他未核实响应不触发创建，404 不猜作缺失。创建使用 Gitee 仓库本身的默认分支，不传 GitHub SHA，不传输 Git 源码。

workflow 默认 `contents: read`，不授予 GitHub Release 写权限。`GITHUB_TOKEN` 仅用于来源元数据与下载；`GITEE_TOKEN` 仅从同名 secret 注入同步步骤，不传给依赖安装、checkout 或构建流程。缺少凭据使同步失败，不输出令牌、认证 URL、原始请求头、响应体或含凭据的异常文本。checkout 禁用凭据持久化，配置通过环境或 Action 输入传递，不拼接为 shell 源码。

同步 workflow 的并发组按 Gitee 仓库和 tag 命名，不按分支或触发方式拆组，`cancel-in-progress: false`。同一目标同时只有一个同步运行写附件及正文；它与 GitHub 构建发布使用不同的并发组，不让后续构建等待 Gitee。人工编辑目标附件或正文须避开同步运行：正文基于运行初始快照合并，即使只编辑区块外描述，也可能被末尾提交覆盖。此人工并发写入不受支持；不增加分布式锁、写前重读或 CAS，不把操作约定描述为并发更新保障。

### 同步范围与元数据读取

自动入口首先检查来源 Release 的全部实际附件；这不是无条件重传。上游成功但本轮没有发布附件时仍执行全量元数据检查，历史未同步附件也在处理范围内；接受这一运行成本和补齐语义，不把上游成功等同于本轮有新增资产。手动输入 `packages` 为逗号分隔包名，空白表示全部；去除各项两端空白并去重，列表内空项报错。普通包名精确匹配既有固定资产名中的包名部分，包含其已发布的全部平台及 any/any 槽，不按任意子串匹配、不重新计算生产依赖闭包。`autolib-importer` 作为明确选择项匹配当前三个宿主 importer 的 `.tar.xz`，选择库包不隐式选择 importer；至少一个指定项无匹配附件时，在远端写入前失败。

全量范围为 GitHub Release 资产列表，不包含 GitHub 自动生成的源码归档；不因 Gitee 有额外附件而删除它们。选定附件名必须可安全作为本次临时目录的文件名，拒绝路径分隔符及越界名称；来源同名重复或关键身份异常在写入前失败。只接受 `uploaded` 且具有有效 `sha256:` 摘要的来源资产，不以下载后自行计算摘要替代缺失的可信来源摘要。

GitHub 资产分页完整读取一次。Gitee Release 正文读取一次、附件列表按页完整读取一次，普通比较不为每个附件再发查询；互不依赖的来源与目标读取可以并行，依赖 Release ID 的读取保持必要顺序。出现网络重试或写入结果不确定时产生的额外请求须计入日志，不宣称任何运行固定只有两次 Gitee 请求。

一次同步使用读取得到的来源附件 ID、名称及摘要快照，不保证追赶随后开始的 GitHub 发布。来源在下载前被同名替换而消失时，该附件失败，不改从另一个资产或 tag 下载；后续同步重新读取事实。共享来源元数据失败时终止同步，不在未知状态下删除目标附件。

### 正文索引与跳过条件

Gitee Release 正文保留原有描述，只维护一对 `<!-- autolib-gitee-sync:start -->`、`<!-- autolib-gitee-sync:end -->` 标记之间的 JSON 代码块。两标记必须独占一行且无前后空白，区块内除空白外必须恰有一个以三个反引号加 `json` 开始、以三个反引号结束的代码块，不允许额外正文或第二个代码块。按原始文本识别标记，不解析 Markdown 上下文；代码示例中的完整字面标记也算标记，HTML 转义形式不算，引用或缩进后的字面标记不符合独占行规则而失败。

JSON 顶层必须是仅含 `files` 的对象；`files` 按完整附件名索引，每项必须恰含 `sha256` 和 `gitee_asset_id`，不接受额外字段或任何层级的重复 JSON 键。摘要为 64 位十六进制字符串，比较及新写入统一小写；ID 为正整数且不接受布尔值。JSON 非标准常量和其他类型拒绝。不保存另一份本轮完成清单、上传时刻或构建身份。索引是同步程序的记录，不冒充 Gitee 计算的原生内容摘要，也不自动成为 importer 的消费协议。

没有索引区块视为附件尚未建立可信记录，需要同步所选附件后建立索引；已有同名附件不凭名称直接跳过。标记重复、嵌套、逆序、不完整、JSON 无法解析或结构非法时，在修改附件前失败，保留原正文及附件，不猜测覆盖范围、不自动修复正文。无关描述和未选择附件的记录保持不变。

只有来源摘要与索引一致，且目标完整列表中存在唯一同名附件、其 ID 与记录一致、其大小与来源一致时，才能判为跳过。不下载 GitHub 或 Gitee 的该附件，也不重复上传。大小只是额外一致性检查，不是内容摘要；附件缺失、ID 改变、记录缺失或摘要不同均进入同步。目标同名重复或关键附件字段异常只使受影响附件失败，不猜测删除对象。

变化附件先从 GitHub 按既有资产身份下载到本次临时目录并核对 SHA256，再修改目标；下载或校验失败不删除 Gitee 旧附件。目标不存在则新增，存在唯一同名附件则按其 ID 先删后传，不删除整个 Release、不扫描历史或清理无关资产。删除失败不继续上传。上传响应必须确认有效附件 ID、名称、大小及下载地址，不能仅凭 HTTP 命令返回零判成功；成功后在内存中记录新 ID 及已校验摘要。

所有并发任务结束后，仅协调器合并成功项并更新一次正文；正文无变化时不写回。每个完整附件名只有一个任务，成功项覆盖该名称的旧记录；未选择项保持原记录，失败项不写入新的成功记录，也不清理旧记录。索引允许保留已失效或当前来源中不存在的记录，不作为目标附件库存；这些记录只有再次满足全部跳过条件才可使用。保留 Release 的名称、tag 及其他非索引内容，不将 Gitee 正文整段替换为 GitHub 描述。部分附件失败时仍保存其他成功项，然后整体失败；正文更新失败时亦整体失败，已经上传的字节不回滚。

删除后上传失败可能留下缺失附件，上传完成而响应丢失、或正文提交前中断可能留下未记录的新附件；后续显式重跑依据附件 ID 和摘要记录重新判断，允许再次传输，不承诺一次且仅一次上传。旧记录不能单独证明成功：附件缺失或 ID 不一致时不得跳过。

重跑先读取远端事实，再按下表处理所选附件；Release 已创建但首次同步未完成也使用同一规则，不增加单独的首次恢复流程。

| 本次读到的目标与索引 | 动作 |
|---|---|
| 目标缺失，索引有无记录均可 | 下载校验后上传，成功才写新记录 |
| 唯一同名目标且全部跳过条件成立 | 跳过，不传附件字节 |
| 唯一同名目标，但无索引、记录缺失或摘要、ID、大小不符 | 下载校验后按实际 ID 删除并上传，成功覆盖记录 |
| 同名目标重复或关键字段异常 | 该附件失败，不猜测删除，不写新记录 |
| 上次删除、上传或正文提交结果未知 | 不沿用上次调用结果，重新落入上述目标状态；允许重复传输，重复同名仍需人工处理 |

### Gitee 响应确认

以下路径省略 `https://gitee.com/api/v5`，`R` 表示 `/repos/{owner}/{repo}`；只约束本轮实际使用的接口，不枚举服务端全部错误码。成功码依据前述官方 OpenAPI，真实写入仍按验收授权执行。

| 操作 | 成功码与必要结果 |
|---|---|
| `GET /user` | `200`，对象内有效正整数 `id` 与非空字符串 `login` |
| `GET R` | `200`，对象内有效 `id`、匹配目标的 `full_name` 与非空 `default_branch` |
| `GET R/releases/tags/{tag}` | `200`，对象内有效 `id`、匹配的 `tag_name`、字符串 `name` 和字符串或 `null` 的 `body`；只有整个 JSON 为 `null` 才判缺失，正文 `null` 按空描述处理 |
| `POST R/releases` | `201`，有效 Release 对象，tag 与创建请求一致 |
| `GET R/releases/{release_id}/attach_files` | `200`，附件对象数组，完整分页读取；所选同名项须有正整数 `id`、非空 `name`、非负整数 `size` 及 HTTPS `browser_download_url` |
| `DELETE R/releases/{release_id}/attach_files/{asset_id}` | `204`，不要求 JSON 响应 |
| `POST R/releases/{release_id}/attach_files` | `201`，有效附件对象，名称与大小均匹配已校验的本地文件 |
| `PATCH R/releases/{release_id}` | 请求携带原对象的 `tag_name`、`name` 及新 `body`，满足官方必填字段；`200`，有效 Release 对象，ID、tag、名称与原对象一致，`body` 等于本次提交内容 |

身份与大小整数均不接受布尔值。未使用的 API 额外字段忽略；这不同于自有正文索引的严格字段规则。列表根结构或分页失败属于共享元数据失败；单项字段异常按附件身份定位，不能定位到名称时停止同步而非猜测。读操作的成功码不符、JSON 损坏或必要字段缺失均失败；不得把它们当作目标缺失。写操作收到成功码但必要结果损坏、缺失或不匹配时，不能确认为成功，也不能假定远端未写入，按结果未知处理。

### 并发、连接与等待

并发上限使用 runner 进程可用逻辑 CPU 数的两倍，不固定为 3 或 4。Ubuntu job 以 `len(os.sched_getaffinity(0))` 取得可用数，实际工作数不超过待处理附件数，开始时输出检测值和工作数；[Python 文档](https://docs.python.org/3.12/library/os.html#os.sched_getaffinity)明确区分进程可用 CPU 与系统 CPU 总数。GitHub [公开仓库标准 runner 配额](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories)中 `ubuntu-24.04` 为 4 vCPU，因此预期上限为 8，但真实运行以检测结果为准；不为此增加 larger runner 或自托管机器。

一个工作任务拥有一个附件从下载、校验到上传的完整过程，不建立下载与上传两套可叠加的并发池。同一附件内部保持下载校验、删除、上传顺序，不同附件可以同时推进；一个附件最终失败后工作槽继续接收其他附件。索引只由协调器修改，工作线程不并发更新正文。采用单文件 HTTP 请求，不把多个附件装进一个未经真实验收的上传请求。

协调器及工作线程各自持有并复用 `requests.Session`，线程不共享可变 Session；每个工作线程跨附件复用连接。完整读取或关闭响应，使连接可返回连接池；保留 TLS 证书校验，不通过关闭验证解决慢连接。API 请求不跟随未确认的重定向；GitHub 资产下载允许正常 HTTPS 重定向，拒绝降级，Gitee 凭据不进入下载请求。

连接超时为 10 秒，元数据及删除请求的读取超时为 30 秒，文件传输的读取超时为 300 秒。读取超时是等待网络数据的限制，不冒充整次传输的墙钟上限；workflow job 另设 30 分钟上限。每个 HTTP 操作独立计算重试，最多重试 5 次，含首次请求共最多 6 次，退避为 2、4、8、16、32 秒；上传与正文更新不共享次数。查询和下载可重试暂时性连接或读取失败及 HTTP 429、502、503、504；证书校验失败、权限错误、格式异常和摘要不符不重试。429 的 `Retry-After` 若比本次退避更长，则终止该操作并报告限流，不提前重发或无限等待。

写请求按可观察结果分类：预期成功码且必要结果有效才确认成功；完整收到的 `400`、`401`、`403`、`404`、`405`、`409`、`422`、`429` 作为明确拒绝，其中只有 `429` 可在上述有界等待内重试。请求发出后连接或读取失败、响应丢失、HTTP `5xx`、非预期重定向、其他未约定状态及无法确认的成功响应均保守报告结果未知；不从错误消息文字猜测远端状态。本地输入或文件打开失败属于发送前失败，不产生远端写入。

Release 正文是对同一 ID 的确定内容赋值，在已约定的单写者前提下，暂时性连接或读取失败及 `429`、`502`、`503`、`504` 可以按上述边界重试相同载荷；无需先证明上次未保存，也不承诺只发一个请求。格式、字段异常和其他状态不自动重试，最终仍未确认则整体失败。附件上传、删除及 Release 创建在结果未知时不自动重放，报告未确认并交给显式重跑重新读取远端状态，不增加恢复队列。网络故障持续存在时不保证上传成功，初始元数据不可用也不能靠附件并发绕过。

### 汇总、验证范围与后续条件

日志立即记录元数据请求及附件处理的开始、结束、尝试次数和耗时；汇总列出实际 CPU 数、所选、跳过、上传、失败数量及对应文件名，并单列正文提交结果、同步总耗时与 `429` 次数。不引入 Python/curl 上传对照或多阶段网络性能框架。单个失败不取消其他任务，最终失败只影响独立同步 workflow，不改已经结束的 GitHub 构建或发布结果。

本轮先交付正文摘要去重与 CPU 数两倍并发，通过获授权的真实 runner 运行记录元数据耗时、变化附件传输耗时及未变化附件的零字节传输，并结合总耗时、限流和失败情况评价效果。任务确实重叠只证明并发实现符合设计，不证明总耗时必然改善；不要求专门串并行对照压测。若该路径效果不好，再评估增加“自动入口仅同步本轮实际发布名单”；本轮不预先修改上游结果协议、读取构建 artifacts 或加入名单模式。名单模式可缩小工作范围，但不能免掉必要的目标元数据查询；是否增加由用户根据真实效果决定。

实现时同步更新当前架构及开发、测试指南，只描述实际交付范围；Gitee 默认来源消费仍作为独立后续工作。本提案不证明此前压缩工具供给的跨平台和真实 CI 验收已完成，不要求为镜像重复构建第三方库，也不把本地 fixture 当作网络性能证据。

指南只保留同步职责、操作安全及验证入口，参考来源和实现细节归本地 Action 说明；环境和测试命令不在两处重复。独立 Python 环境、令牌信任及远端验收缺口必须在各自指南可见，不能靠移走必要操作说明满足原有预算，因此三页的文档预算分别为 240、440、450，保留至少 5% 余量。

## 备选方案

**每次无条件全量替换。** 接线最少，但更新一个包也重传未变化的包；正文摘要索引允许全量检查而只传变化附件。

**自动入口只同步本轮发布名单。** 可减少处理范围，但需要额外获取上游实际发布结果，且不会顺带补齐此前遗漏的附件；作为效果不佳时的后续选择，不先与索引方案同时实施。

**下载 Gitee 全部附件计算 SHA256。** 能直接比较真实内容，但未变化的附件仍消耗网络传输；先使用明确绑定附件 ID 的同步记录，接受它不是服务端内容重算证明。

**独立摘要资产或外部状态数据库。** 同样能够保存摘要，但增加额外资产或存储所有者；选择已有 Release 正文的专用区块，不为一次同步维护第二套服务或清单文件。

**串行处理或一次请求上传多个文件。** 串行累计慢请求等待；上游有多文件 multipart 分支，但 Gitee 当前官方模型只声明单文件和单附件响应，未证明部分成功的可观察语义。采用 CPU 数两倍上限的单附件并发，保留逐附件结果。

**并发任务各自写正文。** 可以较早保存单项结果，但会覆盖其他任务的记录并增加慢 API 请求；选择协调器最后合并写入，接受中断时成功附件可能在重跑中再次传输。

## 验收标准

- 上游原样文件、固定提交、许可及依赖记录可核对，受控测试覆盖原始创建、上传及更新入口；复用有效证据，不把参考引入变成重写。新增适配不进入三个 Go 工具或原平台发布循环。
- workflow 条件验证成功上游才自动运行、失败及取消不运行、手动可独立重跑；同目标运行串行且不取消进行中的写入，GitHub 原流水线结果不依赖镜像。自动触发须在文件进入默认分支后实测，不能用本地条件测试代替。
- 相同 tag 来源、目标变量默认与覆盖、来源缺失拒绝、Gitee 首次创建与后续复用符合约定；认证和网络错误不误创建。按包选择、全部平台匹配、明确选择 importer、未匹配项及非法输入使用小型 fixture 验证，无关附件和描述保留。
- 两端元数据完整分页；相同摘要、附件 ID 及大小的正样本确实零附件下载、零上传、零正文写入。来源更新、目标缺失或换 ID、无索引及部分成功均按规定处理；坏索引在修改前拒绝，不凭名称或大小单独跳过。
- 定向覆盖同名附件重复、ID 相同但大小不同、无索引且已有部分附件、已失效和来源未知的索引记录，以及正文提交失败后的下一次运行。重复目标不删除；其他不一致不能误跳过；失败旧记录允许保留，成功项覆盖且未选择项不变。不要求检测同 ID、同大小的内容篡改。
- 索引解析覆盖唯一代码块、额外字段、重复 JSON 键、转义标记、非独占行和重复或嵌套标记；非法输入或任一指定包未匹配时，断言零 Release 创建、零附件修改和零正文提交。首次创建严格晚于来源校验。
- GitHub 下载字节与来源摘要匹配后才删除旧附件；受控失败证明下载损坏不删旧附件、删除失败不上传、上传或正文提交失败不伪报整体成功。后续重跑能利用已经提交的成功索引，并处理未确认或缺失附件，不要求自动回滚。
- 以受控阻塞的多个附件验证实际任务重叠、同时活跃数不超过检测 CPU 数的两倍，单附件内部顺序不变，失败后其余附件仍得到处理。索引合并保留所有成功项、未选择项及原描述，不发生工作线程互相覆盖；不以配置了线程池代替并发执行证据。
- 定向测试覆盖正文请求的必填字段及名称、tag 保留，连接复用、超时参数、各操作独立的六次尝试及退避、不可重试错误、结果不确定时不盲重放，以及凭据不出现在日志或普通子进程。不穷举底层网络故障；文档与 Agent Note 校验及差异空白检查通过。
- 获得单独远端授权后，在真实 Ubuntu runner 验证一次变化附件同步和一次相同内容跳过，记录实际 CPU、同步总耗时、元数据耗时、传输耗时、限流与失败数量及正文索引；以真实下载字节的 SHA256 验收至少一个上传附件，而非仅以上传响应证明内容正确。不为故障注入破坏正式 Release，不额外重建第三方包，不从本地验收宣称网络性能问题已解决。

## 风险

正文索引依赖同步程序、Release 写权限持有者与 Gitee 存储的可信性，不防恶意伪造，也不是 Gitee 对附件的原生摘要认证。跳过判断以同一附件 ID 对应的字节未被原地改写为前提；若内容改变而 ID、大小均不变，可能错误跳过，这一故障模型不在本轮检测范围内。人工改写索引可能破坏跳过判断；绑定附件 ID 及保留区块外描述只能约束正常维护，不构成整套发行事务或密码学证明。

CPU 数不是网络吞吐量保证。并发可能增加连接竞争或触发 Gitee 限流，初始元数据请求仍可能占据主要时间；需要真实 runner 数据评价，不承诺并发必然更快，不提前扩成自适应调度或网络探测系统。

同名替换的先删后传存在短暂缺失窗口，取消、超时或正文提交失败可能使成功字节没有索引，从而在重跑中再次上传。保留成功附件、报告失败并显式重跑，不增加备份回滚、持久重试队列或跨批次快照保证。

本文为待实现设计。书面确认后，先从更新的 master 创建普通任务分支，将设计作为首提交，再审核实施计划并选择执行方式；不创建 worktree。设计不授权 push、远端合并、触发 CI、传输源码或修改任一远端 Release，这些操作仍需明确授权。
