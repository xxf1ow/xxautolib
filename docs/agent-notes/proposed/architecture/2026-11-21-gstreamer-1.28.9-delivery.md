# Agent Note: GStreamer 1.28.9 的项目级构建与交付

Status: proposed

## 问题

Ubuntu 20.04 和 22.04 的系统 GStreamer 无法提供 `xxdeploy` 需要的统一版本和插件组合。下游项目需要从 xxautolib 获取同一版本的开发库、工具和运行插件，并在保留系统 GStreamer 的机器上安装到项目自己的 `3rdparty`。首批还须保留软件编解码、RTMP 与 RTSP、桌面采集，以及桌面 NVIDIA、Jetson 和 RK 的硬件路径。

## 方案

新增 `gstreamer@1.28.9`，发布平台为 `linux-x86_64`、`linux-aarch64`、`windows-x86_64` 和 `darwin-aarch64`。核心库、同仓上游插件、开发文件和工具统一使用 1.28.9。通过普通根 CMake 入口构建，模块内的 CMake 包装层调用上游 Meson，沿用现有配方、来源校验、依赖接线、打包和下游导入。`autolib_import(TARGET app PRIVATE gstreamer)` 从现有发布入口准备精确闭包，写入项目的 `3rdparty/gstreamer/1.28.9` 及其依赖目录。验收从空缓存开始。系统 GStreamer 继续服务系统应用。 [现有配方接口](../../../subsystems/module-recipes.md) · [GStreamer 1.28 发布说明](https://gstreamer.freedesktop.org/releases/1.28/)

复用 `ffmpeg@8.1.3` 作为 GStreamer 的精确直接依赖。FFmpeg 启用 `avfilter`，交付其头文件、共享库、Windows 导入库与可搬迁的 `libavfilter.pc`。Meson 从同一个 FFmpeg 安装前缀解析 `libavcodec`、`libavformat`、`libavutil`、`libavfilter`。FFmpeg 保留现有 LGPL 构建设置、`FFMPEGConfig.cmake` 的调用方式及既有组件的 CMake 链接接口。OpenCV 继续通过现有 `FFMPEGConfig.cmake` 使用 FFmpeg。OpenCV、ViSP 配方沿用现有声明，两者按缓存指纹传播定向重建并回归。 [FFmpeg 与 OpenCV 视频后端](../../implemented/architecture/2026-11-20-ffmpeg-opencv-videoio.md) · [缓存失效规则](../../implemented/architecture/2026-11-09-release-cache-and-independent-gitee-sync.md#输入指纹与链式失效)

### 构建输入与运行库

GStreamer 配方固定 Meson 1.10.2、Orc 0.4.41 和 vcpkg 注册表提交 `9967a8eb5f4f5cd7be2b6717d31ddb7ff84c4751`，使用隔离的构建与依赖安装前缀。系统包管理器提供构建工具和已声明的系统前置依赖。Linux 使用系统 GLib ≥ 2.64。Windows 的 GLib 来自 vcpkg，macOS 复用 Homebrew 的 GLib，所需的非系统运行文件随包交付。Linux 两个架构保持 Ubuntu 20.04、GCC/G++ 10.5、glibc 2.31 及 Focal 官方动态 C++ 运行库，Windows 保持 VS 2022 x64/v143 与 `/MD`，macOS 保持 ARM64 与部署目标 15.0。 [CI 环境与 ABI](../../implemented/architecture/2026-10-20-ci-system.md#环境与-abi) · [Darwin 原生构建基线](../../implemented/architecture/2026-11-05-darwin-aarch64-native-build-and-ci.md)

| 输入 | 生产及交付 |
| --- | --- |
| x264 `0.165.3222` | 使用 vcpkg 的 `asm` 功能。Linux 和 macOS 将带 PIC 的静态库链接进 `x264enc`。Windows 链接 MSVC 导入库，随包交付 `libx264-165.dll`。 |
| x265 `4.3` | 使用 vcpkg 构建共享库，保留各平台的汇编优化。Focal ARM64 使用 GNU assembler 2.42，通过本模块的 vcpkg overlay 将 SVE2 和 SVE2 BitPerm 目标写成 `armv8.5-a+dotprod+i8mm+sve2` 及 `armv8.5-a+dotprod+i8mm+sve2-bitperm`，保留运行时 CPU 分派。 |
| librtmp | 使用 vcpkg 固定的 RTMPDump 源码提交 `6f6bb1353fc84f4cc37138baa99f586750028a01`。共享库及实际运行所需的 OpenSSL、zlib 等非系统库随包交付。 |
| Orc `0.4.41` | 作为 GStreamer 的 Meson 子项目显式启用，构建并随包交付 Orc 共享库。 |

生产安装步骤明确收集插件和工具的非系统动态依赖，并保留对应许可证和来源。FFmpeg 作为已有独立包由版本化闭包获取。Linux 和 macOS 的库引用按安装树与精确依赖前缀修正，Windows 的应用和扫描器通过进程级 DLL 搜索路径加载包内库。开发元数据从搬迁后的包前缀解析。项目进程显式使用包内 `gst-plugin-scanner` 和插件目录，并使用独立 `GST_REGISTRY_1_0` 文件。默认插件搜索限定于项目指定目录。硬件设备所需驱动由宿主提供，Jetson 与 RK 的插件按下节显式接入。 [GStreamer 插件搜索规则](https://gstreamer.freedesktop.org/documentation/gstreamer/running.html)

### 首批插件与硬件边界

显式启用清单中的必需插件。依赖缺失或 Meson 无法编译必需插件时，构建报错并指出相关插件。`base`、`good`、`bad`、`ugly` 中的其他插件优先纳入能够在该平台基线构建并完成运行依赖交付的项，发布时记录各平台实际交付的插件。`x264` 和 `x265` 使用所需的 `gpl=enabled`。 [上游 Meson 选项](https://github.com/GStreamer/gstreamer/blob/1.28.9/meson.options)

| 适用平台 | 必需能力及代表元素 |
| --- | --- |
| 四个平台 | `appsrc`、`appsink`，H.264/H.265 parser `h264parse`、`h265parse`，软件编码 `x264enc`、`x265enc`，软件解码 `avdec_h264`、`avdec_h265`。 |
| 四个平台 | MP4 输入 `qtdemux`、Matroska 输入和输出 `matroskademux`、`matroskamux`，RTMP 收发 `rtmpsrc`、`rtmpsink` 与 `flvmux`，RTSP 接收和发布 `rtspsrc`、`rtspclientsink` 及 H.264/H.265 的 RTP payloader、depayloader。 |
| Linux x86_64 桌面 NVIDIA | `nvcodec`、`gst-cuda` 库和开发文件，`nvh264dec`、`nvh265dec`、`nvh264enc`、`nvh265enc`。设置 `cuda-nvmm=disabled`。普通 CI 检查构建产物，GPU 实机验证元素注册和编解码，驱动运行库由宿主提供。 |
| macOS ARM64 | `applemedia` 的 `avfvideosrc`，以及显示所用的 `glimagesink`。 |
| Windows x86_64 | `mediafoundation` 的 `mfvideosrc`，`d3d11screencapturesrc`、`d3d11convert`、`d3d11download`，以及显示所用的 `autovideosink`。 |

Jetson 使用同一 Linux ARM64 通用包，通过明确的 JetPack 插件路径加载本机的 `nvv4l2decoder` 和 `nvvidconv`，检查 NVMM 帧及 CUDA 读取。RK 的 DMA32 补丁插件按包内 1.28.9 开发文件单独编译，RK/RGA 验收使用该插件。两类设备插件由各自设备环境管理。`xxautolib` 发布平台身份与通用依赖闭包继续沿用现有四平台模型。 [Jetson 加速插件](https://docs.nvidia.com/jetson/archives/r36.5/DeveloperGuide/SD/Multimedia/AcceleratedGstreamer.html)

### 阶段与操作边界

第一阶段交付四平台通用包及直接和搬迁消费的证据，包含 Linux 桌面 NVIDIA 的 `nvcodec` 编译与打包，以及 FFmpeg、OpenCV、ViSP 的回归。第二阶段以第一阶段已验证的通用成品执行桌面 NVIDIA、Windows 与 macOS 采集、Jetson 和 RK 的实机验收。第一阶段通过后由使用者验收并确认第二阶段的目标设备、目录和产物身份。

正式任务分支以 `master` 为基线，正式设计提交为分支首提交。四平台预验收在任务分支运行，仅保留 GitHub Actions 临时产物和日志。两阶段验收通过后，使用现有 `Representative releases` 与 `Synchronize Gitee` 发布。确认发布阶段时明确构建提交、所选模块和目标仓库。正式发布后，用现有下游入口验证首次下载和离线复用。远端实机涉及源码、素材或成品传输时，沿用已有的明确机器和目录授权，其余设备以第二阶段确认的范围为准。 [现有生产与发布流程](../../../development.md#ci-开发与运行)

## 备选方案

**直接安装 Ubuntu 官方包。** Focal 的 x264 为 0.155，低于 `x264enc` 要求的 0.156。两版 Ubuntu 的 Orc 低于 0.4.34，x265 分别为 3.2.1 和 3.5。插件需要本方案固定的运行库版本。 [Ubuntu Orc 版本](https://ubuntu.com/security/notices/USN-6964-1) · [Focal x265](https://manpages.ubuntu.com/manpages/focal/man1/x265.1.html) · [Jammy x265](https://packages.ubuntu.com/jammy/libx265-199)

**分别新增 x264、x265、librtmp 和 Orc 配方。** 这些库在首批作为 GStreamer 插件的私有构建输入。四平台探针验证了 vcpkg 与 Meson 子项目的组合，依赖可静态链接或随包提供。只有现有供给方式无法满足已确认的版本、汇编或搬迁要求时，才重新评估对应的独立配方。 [四平台探针](https://github.com/xxf1ow/xxautolib/actions/runs/44910276043)

**两种 Linux 架构统一升级到 GCC 12.5。** 两架构均可完成构建，所得 `libx265.so` 都需要 Focal 官方运行库缺少的 `GLIBCXX_3.4.29`。GCC 10.5 配合 ARM64 局部汇编适配的两份成品使用 Focal 原运行库通过消费。 [GCC 12.5 对照](https://github.com/xxf1ow/xxautolib/actions/runs/44901347462) · [Focal ARM64 消费](https://github.com/xxf1ow/xxautolib/actions/runs/44910276043/job/136865517224)

## 验收标准

1. 四平台通过普通 CMake 入口构建、安装和打包。从空的下游缓存导入并实际链接运行。解包到另一位置，在隔离 vcpkg、Homebrew 和生产前缀的消费环境中核对 GStreamer 1.28.9、`.pc`、共享库、插件 `Filename`、扫描器及独立 registry。两架构各自使用同一份 Linux 归档在 Ubuntu 20.04 和 22.04 验证。20.04 以官方 GCC 10.5 编译运行消费者，非系统库从交付闭包加载，产物满足既有 Linux ABI 检查。
2. 四平台用实际短素材执行 H.264/H.265 编码与软件解码、容器写入和独立回读。用本地测试服务验证 RTMP 收发和 RTSP 收发。核对 FFmpeg 的四项 `.pc` 均来自同一精确包，并验证 `avdec_h264`、`avdec_h265` 处理实际帧。OpenCV 回归 RTSP 读帧及 MP4 写入读回。ViSP 运行现有消费测试。正式下载后在离线状态重新链接并运行。
3. 桌面 NVIDIA 实机完成 H.264/H.265 硬编解码并检查 `CUDAMemory`。macOS 和 Windows 实机分别验证要求的采集与显示元素。Jetson 实机验证 NVMM、CUDA 读取及实际输出回读。RK 用固定的 92 帧 H.264 素材跑含 `xxrkprocessor` 和叠加的完整管线，记录 parser 与 MPP 输出的色彩 caps，并独立回读 92 帧。素材为 `street-first-3s.mp4`，SHA256 为 `c85bc36262df6f3b02b83d5b5c0bb57ed99f38a3426a05ce0bf26c869a907526`。

## 风险

RK 探针使用 92 帧素材在 1.28.9 上完成了单独 MPP 转码和回读，完整 `xxrkprocessor` 管线报 `not-negotiated`。相同素材的 MPP 输出 caps 从系统 1.16 的 `bt709` 变为 1.28.9 的 `0:4:0:0`，色彩变化与失败的因果关系待实机核实。桌面 NVIDIA 探针仅跑通 H.264 硬编解码。Jetson 探针的 CUDA 帧读取与 92 帧回读使用了设备目录内的 `x264enc`。实机验收须以正式包和对应设备插件复验这些路径。
