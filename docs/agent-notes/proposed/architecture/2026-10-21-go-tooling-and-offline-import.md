# Agent Note: Go 工具层与严格来源的二进制导入

Status: proposed

## 问题

下游项目应只依赖已有的 CMake 和本仓库提供的可执行工具，即可获取并导入预编译库。要求下游另行安装 Python、uv、Go SDK 或语言依赖，会增加环境准备步骤，也无法满足离线机器从本地发行目录完成首次导入的要求。

现有 TOML 模块定义、补丁、平台输入、依赖接线和原生 ExternalProject 已有本地验证。新的交付工具不应重复实现 CMake 构建与链接语义，也不应为了减少一个解析依赖而迁移配置格式、拆走维护注释，或重写已经可用的库配置。

## 方案

以 Go 统一本仓库自有工具层，保留 CMake 构建与导入、TOML 模块声明和每库的包内导入脚本。Go 工具使用纯 Go 依赖，正式二进制禁用 cgo。用户使用发布好的对应宿主平台程序，不在导入时编译工具或准备语言环境。

本设计覆盖生产端工具替换、打包、消费者入口、获取协议和工具发行，按阶段实现。生产端替换及本地二进制链路已实现；HTTPS 与三宿主工具发行仍为后续设计。当前接口由[架构](../../../architecture.md)和[开发指南](../../../development.md#本地打包与消费)说明；按名称消费、可搬迁适配、固定槽、生产缓存和远端发布的完整约束仍由[二进制交付设计](2026-10-20-name-only-artifact-delivery.md)拥有。本文补充其语言实现、引导过程和严格来源规则，不引入另一套发布坐标。

### 职责划分

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| 模块目录 | `module.toml`、补丁、专用构建文件、`autolib-import.cmake` | 通用下载器、环境管理器、共享生成逻辑 |
| `autolib-builder` | 声明解析、校验、平台选择、生产依赖闭包、路径编码、原生 CMake 生成、暂存修正、打包及发行元数据生成 | 自行执行源码下载、补丁、编译、安装或跟踪构建 stamp；为下游准备二进制包 |
| CMake / ExternalProject | 生产端实际获取、补丁、配置、编译、安装和增量步骤 | Go 模块解析、二进制发行选择 |
| `src/autolib.cmake` | 单文件 CMake 入口，识别宿主、按 JSON 清单获取并校验 importer、调用 importer，准备后加载全部包内 adapter | 解析完整模块定义、实现库包获取协议、依赖旁置 CMake helper 或安装语言环境 |
| `autolib-importer` | manifest 校验、二进制包获取、校验和解包，返回准备好的包目录 | 生产端生成与打包、代替 CMake 执行 `include`、猜测上游导出 target、编译消费者或自动获取消费依赖闭包 |
| 包内 adapter | 在全部所请求包准备好后，定位本包及显式 sibling 包，提供 `AutoLib::<name>` | 下载、安装解释器、编译源码或自动补齐缺包 |

消费端保留 `autolib.cmake` 与 `autolib-importer` 两层：CMake 只处理最小引导及目标加载，可测试的文件与获取逻辑集中在 Go 中。importer 是原生可执行文件，而不是复杂 CMake 脚本集合。入口自身完整保存在 `src/autolib.cmake`，不拆成需要一起分发的 helper；每库 adapter 仍随各自归档发布，不搬到 importer 维护一份按库名分支的适配表。

Go 源码采用一个根 Go module、两个独立可执行目标，按生产与消费职责组织。布局如下；只在实现对应能力时创建文件和目录：

```text
go.mod / go.sum                 根 Go module 的依赖声明与内容校验
src/autolib.cmake               简洁、自包含的单文件消费入口
src/autolib-builder/            生产端 Go 入口及实现；保留必要生产 CMake helper
src/autolib-importer/           消费端 Go 入口及实现
src/dependencies/<name>/        既有声明、补丁及每包导入适配
build/                         Git 忽略：可执行程序、生成文件、staging 和发行包
```

builder 提供生成与打包能力，importer 提供消费端准备能力；两者不相互调用业务命令，不增加进程间服务或插件框架。生产端的产物处理源码归 builder，消费端的获取与解包源码归 importer，不设独立 `src/artifacts/` 或预建 `common/shared` 层。两个目标遵守同一发行协议，但不因此强行共享实现；只有实际出现有维护价值的重复逻辑时才考虑抽取。源码目录不保存生成产物，暂存和归档均进入忽略的构建目录。

### 生产端：替换工具代码，保留业务契约

以 Go 重新实现当前 `definition.py`、`generate.py`、`cmake.py` 的职责，不逐文件翻译 Python 类结构，也不继续在 Python 上叠加新功能。模块 TOML、补丁、库版本、构建选项和根 CMake 骨架保持已有决定；只修改调用 Go 所需的接口。沿用的契约与维护理由见[流水线设计](../../implemented/architecture/2026-10-19-toml-externalproject-zlib.md)、[本地输入与平台选择](../../implemented/architecture/2026-10-20-local-reuse-and-platform-inputs.md)及[依赖接线](../../implemented/architecture/2026-10-20-flann-opencv-dependencies.md)。

生成器仍在 configure 阶段一次处理本次选择，生成可直接检查的 ExternalProject 声明。生产端 `BUILD_LIST` 仍计算稳定依赖先序闭包；这个行为不扩大为消费者的自动下载闭包。未知字段、缺失模块和依赖环仍报错，未选平台也执行声明合法性校验。保留输入变更触发重新配置、内容不变不改写输出时间戳，以及生成失败不加载旧结果。

根 CMake 的公共入口自动准备项目私有的 Go SDK，增量构建本地 `autolib-builder` 到 `build/`，再调用其生成命令；跟踪 builder 的 Go 源码、`go.mod`、`go.sum`、SDK 元数据及本次实际模块输入。首次开发构建自动获取固定 SDK 和缺失模块，后续复用缓存；用户不需要手工安装 Go、设置 PATH 或单独执行依赖下载。普通生成失败不得隐式执行依赖升级。生产端仍需 Git、C/C++ 工具链及各模块实际依赖的工具，不把语言迁移描述为取消这些构建要求。

SDK 固定放在仓库根相对路径 `.tools/go/sdk/go<版本>/<宿主平台>/go/`，不放在容易清理的 build 下；Go 模块缓存与编译缓存也在 `.tools/go/` 内，并由 Git 忽略。入口只使用这一私有 SDK，不从 PATH 或 `GO_EXECUTABLE` 选择系统 SDK。版本由 go.mod 固定为 1.27.3，三宿主官方归档的 SHA256 纳入 `go-sdk-versions.cmake`，版本修改须同步核对摘要；不查询 latest。CMake 从官方 HTTPS 地址下载缺失归档，显式验证 TLS，先校验固定摘要、在临时目录解压并检查可执行版本，成功后才提交 SDK。已安装且版本匹配的 SDK 直接复用；只有归档时校验后重新解压。缓存损坏、下载失败、版本不符或构建失败明确报错，不运行残留 builder，不自动覆盖异常 SDK。

所有 Go 调用使用确定的 SDK 绝对路径，环境设置仅传给对应子进程：固定项目内的 GOROOT、GOPATH、GOMODCACHE 和 GOCACHE，设置 `GOENV=off`、`GOWORK=off`、`GOTOOLCHAIN=local`、`CGO_ENABLED=0`，并按宿主选择 GOOS/GOARCH。不修改全局 PATH、用户 Go 配置或父进程环境，不执行 `go env -w`；代理与联网策略可以通过调用方进程环境提供。只读模块构建按 go.mod/go.sum 自动获取并校验缺失依赖，不升级依赖、不改写这两个文件。缓存完整时可离线复用，离线缺输入时明确失败；开发和测试入口共享相同准备与环境逻辑。这是生产端工具准备，不改变消费者本地来源绝不联网、无需 SDK 的契约。

Release、父生成器完整身份、CRT、公共默认值优先级、直接依赖查找位置、资源引用、补丁顺序、原生步骤、持久来源及 sentinel 的行为均保持现有契约。原生来源获取继续交给 ExternalProject；例如 FreeType 的 tar.xz 不因为 Go 工具接入而改由 Go 重新实现解包。

本仓库自有 Python 测试随对应功能迁移到 Go 测试及必要的 CMake fixture，不长期维护两个生成器。新入口验收前保留旧实现作为对照，不让同一次 configure 同时运行两套引擎。切换完成后移除被替换的自有 Python 代码、Python 测试及仅服务于这些工具的 `.python-version`、`pyproject.toml`、`uv.lock`；已有 `.venv/` 是用户本地数据，不自动删除。个人技能自带的外部 Python 校验器不属于本仓库代码，不为本次迁移重写。

### Python 与第三方源码的边界

不打包 Python 环境，不向消费者引入任何 Python 依赖。上游源码是否使用解释器必须依据实际选定功能及构建规则判断，不能从检测日志、传入的路径或绑定开关单独推导。

当前 OpenCV 已关闭其他语言绑定和对应生成器；现有 cache 中有 Python 路径、摘要显示构建用 Python，不足以证明当前 C++ 构建必需解释器。Go 切换时分别核查 OpenCV、HarfBuzz 的 `<PYTHON_EXECUTABLE>` 引用：对不需要解释器的已选配置去掉注入并验证，而不是将其改成系统 Python 回退。不得以更换工具语言为由开启绑定、改变模块功能或重写上游代码。

如果实际构建证明某个保留功能必须执行 Python，暂停该模块的受影响切换，提交具体命令、原因和最小调整建议，由用户决定；不能据此悄悄保留全仓库的 uv 环境或增加解释器自动安装。这是现有证据尚未闭合的验证风险，不是当前已经证明的 Python 必需条件。

### 配置和 Go 依赖

维护者编辑的配置继续使用 TOML 和原生 `#` 注释，不迁移 JSON/YAML，不自行实现解析器，也不将注释变成待解析的自定义格式。Go 读取配置，不自动回写 TOML；现有注释、字段顺序与排版保持原样。

标准库优先，但不以零第三方依赖为目标。TOML 优先采用 `github.com/pelletier/go-toml/v2` 的稳定读取接口，具体版本在首阶段计划中确定并记录；不引入用于自动编辑文档的 unstable API。已有字段校验仍由本项目承担，解析库不能代替平台合并、路径限制和业务校验。

HTTP/TLS、摘要、路径、文件、子进程、简单命令行、日志和测试优先使用标准库，不预先引入 HTTP 客户端框架、CLI 框架、日志框架或测试框架。发行包沿用 tar.zst 方向时，可引入纯 Go 的 `github.com/klauspost/compress/zstd`；上游源码的 XZ 等格式继续由原生构建工具处理，不为支持任意归档引入通用格式框架。

`go.mod` 声明 module、Go 版本要求及依赖版本；`go.sum` 保存模块内容校验值，不是与 `uv.lock` 一一对应的锁文件。依赖更新是显式开发操作，不在生成或用户导入时更新。依赖代码随正式二进制交付，不要求消费者安装 Go 包。选择和升级依赖时检查许可证、所需 Go 版本及是否引入 cgo；不为形式上的少依赖维护自研替代品。

### 消费入口与数据流

消费者显式提供一个 URI、需要的包名和匹配的目标平台；工作目录默认在消费者 build 下，不写全局安装位置。URI 是本次消费的唯一权威来源，不维护隐含备用源、镜像搜索或“本地缺了再联网”的规则。同一 configure 的全部请求在获取前汇总，先去重并准备全部包，再加载任何 adapter。

公共 CMake 入口维持最低版本 3.20，以一次调用接收 `URI`、`PACKAGES` 和可选的工作根目录；目标平台优先读取 CMake 已配置的目标信息，按既有平台规则归一，无法确定时要求显式提供。入口只调用 importer 的准备操作，不执行启动前版本查询或协议协商，不调用 builder，也不要求下游准备 builder。命令参数拼写在阶段计划中落实，不增加另一个公开配置层。

```text
消费者 CMake
  → autolib.cmake 读取 JSON 发行清单，按宿主平台取得并校验 importer
  → 调用 importer，根据 URI 与目标平台准备全部请求包
  → importer 完成校验与解包，返回准备好的包目录
  → CMake 加载包内 adapter
  → 下游链接 AutoLib::<name>
```

入口通过固定命令行参数向 importer 传入来源 URI、独立工作目录、明确目标平台、请求包名和结果文件路径；已为本次引导取得 manifest 时，同时传入该清单的本地路径。发行清单只描述发行物，不包含本次消费请求，也不以已下载清单的本地目录推断原始来源。结果使用受控生成的 UTF-8 CMake 文件列出包名与准备后的绝对目录，供入口加载；文件只含数据，不含网络或目标定义，路径按 CMake 字面参数编码，不执行路径中的变量或命令。参数通过 argv 传递，不经 shell 拼接路径和命令，不额外生成一份请求文件。

importer 成功返回 0，失败返回非零；stderr 提供人类可读诊断，标明失败对象、来源或路径及失败原因，不要求结构化错误或为每种错误分配独立退出码。prepare 的机器结果只通过显式结果文件交付，进度信息写 stderr。只有全部请求包就绪才提交本次结果文件，入口仅在本次调用成功后加载它。获取失败、摘要错误、缺包、目标平台不支持或 importer 调用失败均终止 configure，不加载上次残留结果。命令参数和结果变量名在第二阶段计划中同时固定，并由真实 CMake 调用验证；importer 独立更新保持这一调用接口。

发行根使用一份 UTF-8 `manifest.json`，顶层严格只有 `importers` 和 `packages` 两个数组。`importers` 每条记录严格包含 `os`、`arch`、`asset`、`sha256` 四个字符串字段，同一宿主 `(os, arch)` 唯一；`packages` 每条记录严格包含交付设计规定的 `name`、`os`、`arch`、`asset`、`sha256` 五个字符串字段，同一包槽唯一。`sha256` 为 64 位十六进制，`asset` 只能是发行根内的单个文件名。未知字段、字段类型错误和重复槽均失败；清单不包含 `protocol` 字段，包记录不加入版本、URL、build ID、依赖或历史。

JSON 只用于生成的发行信息，模块声明继续使用带注释的 TOML。CMake 入口用原生 JSON 能力读取 importer 记录，不执行清单内容，也不自行实现 TOML 解析器；importer 校验同一清单并处理包记录。入口已为本次引导读取清单时，把该文件交给 importer 复用，不要求两端再次从发行源各取一份清单。

发行根平铺放置 `manifest.json`、各宿主 importer 和 manifest 指定的包归档。入口脚本可以随发行目录一起搬运，也可以由项目预先保存。生产端使用 `autolib-importer-<os>-<arch>`，Windows 加 `.exe`，普通库包使用 `<name>-<os>-<arch>.tar.zst`；消费时两类资产均以相应记录的 `asset` 为准，不从名称重建地址。importer 单独登记在 `importers` 中，不作为 C++ 库包。builder 在开发和生产环境本地构建，不是消费发行目录的必需文件。

### 严格区分联网与本地来源

两种模式都按“来源根 + 文件名”定位发行物，使用同一平铺布局：清单固定为 `manifest.json`，importer 和库包文件名只取所选记录的 `asset`。联网模式进行 URL 路径拼接并下载，本地模式进行文件系统路径拼接并读取或复制，不将本地路径改写为 HTTP 地址，也不需要本地 HTTP 服务或预先解包库。

联网模式的 URI 指向一个明确 Release 的资产根地址，不自动发现 latest、其他仓库或镜像。bootstrap 只从这个根定位 importer，importer 只从这个根定位 manifest 和包。初始 URL 与每次重定向均须使用 HTTPS，并验证服务器证书；CMake 引导显式启用 `TLS_VERIFY ON`，Go 获取也不得关闭证书校验。允许发行源通过 HTTPS 重定向委托其他资产主机，不维护额外主机白名单；这不构成地址失败后切换来源。来源不可用、协议降级或校验失败即报错，不自动寻找另一 Release。第三阶段须验证 CMake 引导和 Go 获取具有一致的重定向策略，不能只验证 importer。

发行来源由用户手动指定，是否信任该来源由用户决定；本地模式使用用户手动准备的发行输入，联网模式验证 HTTPS 及其重定向。清单中的摘要分别检查 importer、库包与发行记录的字节一致性，不独立认证发布者。首版不增加发行源信誉判断、签名、独立发布者认证或不可信代码沙箱；importer 会被执行，包内 adapter 会由 CMake 加载。

本地模式的 URI 是本地目录路径，Windows 盘符、UNC 与普通路径先按路径解析，不能把盘符误当网络 scheme。相对路径由入口按消费者顶层源码目录解析成绝对路径后传给 importer。该目录必须由用户手动准备好 importer、manifest 和请求包的归档；不要求先解包所有库。

本地来源下，bootstrap 只复制本地 importer，importer 只读取本地 manifest 和归档。任何缺失、摘要错误或身份错误都报告具体路径及应准备的文件，不执行 HTTP 请求、Go 构建、SDK 获取、解释器安装、上游下载或镜像回退。manifest 的 asset 只允许来源根内的单个文件名，不能携带 URL、绝对路径或越界路径；本地模式没有可被清单触发的网络出口。

工作目录按规范化 URI 与目标平台区分，包再按包名定位并核对包内名称及平台身份；importer 自身按来源和宿主隔离，并保存取得时的清单副本用于核对本地字节。已有匹配 importer 和已完成的匹配平台包是本地权威，不为比较发行源当前状态而读取远端清单或自动覆盖。用户显式移除对应 importer 缓存或包目录后才重新获取，不要求同时删除其他工具、包或平台数据。来源目录不是缓存目录，消费流程不改写用户准备的发行输入。

同一 URI 的固定槽允许更新，不要求发行根不可变，也不新增刷新参数。已有本地包仍保留原字节，只有缺包才按当前 manifest 获取，因此不承诺跨包发行批次一致；需要整体刷新时，用户清理该来源与目标平台对应的消费包目录后重新导入。该操作不要求删除其他来源、其他平台或生产端产物。

只有缺少 importer 或存在待获取包时才从发行源读取 manifest，同一次 configure 至多获取一份。入口已为引导取得清单时，importer 使用该次文件；否则 importer 仅在缺包时读取来源清单。全部输入已准备好的重复导入只使用本地状态，不要求重新读取来源清单。已有 importer 可继续准备当前清单中的缺包，不因其中的 importer 记录更新而自动更换自身。首次导入的离线保证必须由未预热的工作目录验证，而不是依赖这一复用行为。

同一工作目录的并发写入不属于首版支持范围；多个独立 build 使用各自目录，不预建全局锁服务或共享缓存协调器。

### importer 引导与校验

`autolib.cmake` 只保存获取固定名称 JSON 清单、按宿主选择 importer、校验并按固定接口启动程序的稳定引导流程。入口不内置 importer 发行文件名或 SHA256，不随每次 importer 构建重新生成摘要表。生产端从实际可执行文件生成清单中的资产记录；保持调用接口的 importer 可以通过替换发行资产及其记录独立更新，无需修改入口。

首次引导由 CMake 自行读取 JSON，选择唯一宿主记录，在工作目录的临时文件中获取 importer。SHA256 通过后才放入可执行位置；Linux 设置所需执行权限。入口随后直接调用准备操作，不执行启动前版本查询。摘要错误不执行；缺少匹配宿主记录、程序无法启动或准备失败均明确失败，不回退 Python、系统工具或源码编译。已有本地 importer 按取得时的记录校验复用，异常时保留并报错，不自动覆盖。

离线发行目录只需包含遵守固定调用接口的 importer、描述实际字节的清单和所需包。缺清单、宿主记录或 importer 文件时，在启动 Go 程序前就能明确失败。独立更新指发行与入口解耦，不表示每次 configure 自动刷新已有副本；刷新仍由用户显式移除相应本地缓存触发。

### 宿主平台、目标平台与发行

importer 根据运行 CMake 的宿主平台选择，不根据 C++ 库目标平台选择。内部平台名继续统一为 `windows`、`linux` 与 `x86_64`、`aarch64`，Go 编译参数分别映射到 `windows`、`linux` 与 `amd64`、`arm64`。首批 importer 发行矩阵为 Windows x86_64、Linux x86_64、Linux aarch64；不支持的平台报错，不下载“最接近”的程序。

两个 Go 目标的正式构建均使用 `CGO_ENABLED=0`，依赖不得通过本地 C/C++ 动态库破坏各自的单二进制交付。importer 可以从一个宿主交叉编译到该矩阵；每个承诺支持的平台仍需执行工具 smoke 和消费 fixture，交叉编译成功不代替运行验证。builder 随生产端入口在开发或构建环境本地构建验证，不要求向下游发布第二套工具矩阵。SDK 版本在构建配置固定，依赖版本纳入仓库；发布构建不依赖自动选择新工具链。

纯 Go importer 不应动态依赖 glibc 或 libstdc++；它仍受所选 Go 版本的操作系统、内核和 CPU 下限约束。首版使用保守 CPU 基线，不用发布机本机优化替代通用目标。具体最低系统要求在工具发行阶段记录并验收，不能根据 C++ 库的 ABI 基线推定 importer 的最低系统版本。

Go 工具交叉编译不扩大 C++ 库的交叉编译范围。库继续按[原生 CI 与 ABI 方向](../process/2026-10-20-native-platform-ci.md)构建；importer 可运行不保证库包的 glibc、GLIBCXX、CRT 或系统依赖兼容。打包和消费验证必须继续核对库本身的运行要求。

### 打包、导入与发布

只有显式提供 adapter 的模块才具备二进制发布资格；本地可构建资格保持独立。builder 从安装树复制到构建目录内的独立 staging，放入模块自己的 adapter，按交付设计的相对路径规则只修正 staging 中的已知生产前缀，不改原 `3rdparty/`、库的编译方式或功能选项，再生成归档和发行元数据。CMake 加载时按实际包目录把相对定位解析成当前绝对路径，不原地改写已解包文件，也不由 importer 扫描并修补任意 target。归档中只有与包名一致的顶层目录，并携带身份与导入文件。

包内 `autolib-import.cmake` 由 builder 在模块 adapter 正文前生成固定身份头，依次使用 `set(AUTOLIB_PACKAGE_NAME "<name>")`、`set(AUTOLIB_OS "<os>")`、`set(AUTOLIB_ARCH "<arch>")` 三个单行字面赋值。importer 只按该固定格式读取并核对名称及平台，不执行 CMake，不解析正文；CMake 随后加载同一文件。身份只维护在这个生成头中，不另存重复 BUILDINFO。

importer 严格匹配 manifest 的名称、目标平台、唯一记录和摘要，使用记录中的 asset，不推导文件名。不接受未知字段或重复槽。解包前验证归档路径不越界，链接不能指向允许目录之外；保留库包需要的内部符号链接。完成归档及身份检查后才将结果移入最终目录，失败不覆盖已有包，只清理本次受控临时输入；已准备好的其他包可以供下一次重跑复用。

归档拒绝绝对路径、Windows 盘符及 UNC 路径、规范化后越出包根的路径，以及宿主文件系统不能无歧义表示的成员名。规范化后不得重复定义文件或链接，不得有文件、目录、链接类型冲突；重复目录声明只允许保持目录类型。只接受普通文件、目录及安全的内部符号链接，拒绝硬链接、设备文件、FIFO 等不需要的类型。符号链接链不得循环或解析到包根之外，解包不得沿已创建的符号链接写入成员；仅做字符串前缀检查不满足这些要求。宿主无法创建所需链接时明确失败，不自动提权或静默改变包内容。

每包在最终目录所在文件系统的独立临时目录准备，完整校验后提交到尚不存在的最终目录；不覆盖已有最终包，不承诺跨包事务或断电持久性。路径越界、重名冲突、链接绕过及特殊文件拒绝须由恶意归档 fixture 验证。首版不预设脱离实际包规模的文件数和解压大小配额，也不承诺处理任意不可信压缩输入；不得按未校验的归档大小一次性分配整个文件内容。

adapter 只能在本包或显式 sibling 包中选择交付设计允许的精确导入机制。所有包就绪后才导入，不依赖调用者列出包名的顺序；需要依赖 target 时，adapter 显式加载已准备好的 sibling adapter，不下载它，也不从系统环境补齐。必须有 include guard，重复加载不创建冲突目标。调用者漏列依赖包时明确报错。

固定槽、manifest 包记录的五字段、内部 build ID、缓存命中检查、发布先资产后 manifest、镜像顺序和默认分支限制继续由交付设计拥有。Go 替换对应自有工具时直接调用宿主命令或标准 HTTP 能力，不因语言变化引入 GitHub SDK、后台服务或新的远端状态数据库。GitHub/Gitee 地址、凭据和远端写操作不从参考仓库继承。

首版工具发行不要求先实现整个 CI、生产缓存或镜像系统。先用本地生成的完整发行目录和受控 HTTPS fixture 验证协议；真实上传、触发远端 CI 或镜像写入均需单独授权，不能以本设计确认视为隐含远端授权。

### 分阶段交付

以下是分阶段验收边界，不是具体实施步骤；每阶段只在前一阶段由用户验收、后续假设复核后再规划和执行。

1. Go 生产生成器替换：建立根 Go module 和 `autolib-builder` 目标，实现 TOML 读取、生成和公共入口接线，迁移相关测试，保留现有模块行为；闭合 OpenCV/HarfBuzz 解释器验证，移除不再需要的自有 Python 工具。此阶段不以二进制发布或远端 CI 为验收条件。
2. 本地二进制闭环：为 builder 增加 staging 打包和本地 JSON 发行清单生成，建立独立 `autolib-importer` 目标及 prepare 操作，并在 `src/autolib.cmake` 实现仅本地来源的单文件入口。本地发行目录同时包含实际构建的 importer、清单和包归档，不把引导校验推迟到下一阶段。代表集为 queue、lz4、flann，覆盖头文件库、编译库、动态库及 `flann → lz4` 显式包依赖链；不为覆盖形式同时发布全部模块。未预热且无 Go/Python/uv、无网络的消费 fixture 必须完成首次获取、搬迁后编译链接和动态库最小运行，并覆盖缺包失败。FLANN 保留既有编译选项，AutoLib 管理的包依赖仍只有 lz4；OpenMP 属于编译器及系统运行环境要求，不新增 OpenMP 发行包。
3. 联网引导与工具发行：为入口和 importer 增加指定 Release URI 的受控 HTTPS 获取，构建三宿主 importer，逐平台运行最小消费验证，在统一清单中完成三宿主工具记录及可手动搬运的发行目录。真实远端发布与原生 CI 接入另按既有提案确认，不作为本阶段默认写操作。

第 1 阶段不批量重建无关库。已有真实验证可复用，但不能用旧 Python 环境中的构建成功冒充 Go 入口成功，也不能用 sentinel 全部命中冒充移除解释器后的实际构建。验证只针对受影响入口和代表模块，平台实机证据缺口如实保留。

## 备选方案

**继续用 uv 与 Python，或将解释器打包交付。** 开发环境方便，但消费者需要额外准备，或者由本仓库承担环境包体积和维护成本；不满足本次选择的直接可执行交付方式。

**全部使用 CMake 实现。** 用户无需额外运行时，但复杂获取、元数据与文件操作会扩大脚本和测试负担；CMake 保留引导、实际构建和导入职责，不承担完整工具层。

**使用 C++ 实现工具。** 可以利用已有语言经验，但 HTTP/TLS、配置和压缩依赖以及多平台工具发布增加额外工作。当前任务主要是工具编排，不需要将工具链接到 C++ 库，选择纯 Go 降低交叉编译及运行库交付负担。

**模块声明改用 JSON 以实现零第三方依赖。** 无法原生保留贴近配置的注释，迁移和说明拆分的代价超过一个 TOML 解析依赖；模块声明保留 TOML，不维护自定义注释 JSON 或解析器。生成的发行清单不承担手写维护注释，使用 JSON 使 CMake 和 Go 均可直接读取。

**在入口内置 importer 文件名及 SHA256。** 能固定某一版二进制，但每次 importer 更新都要求重新生成入口，违背独立更新和精简引导的目标。选择由用户指定的发行源通过统一清单描述工具及库包，入口只约束稳定流程和固定调用接口。

**通过 `protocol` 字段和启动前版本查询检查命令兼容性。** 只能提前拒绝不兼容程序，不能让入口获得新的调用方式。当前采用固定命令参数和结果格式，不支持多套调用协议，无需增加该字段、额外查询和协商逻辑。

**把本次消费输入写入请求文件，只向 importer 传入该文件路径。** 来源、请求包、目标平台、工作目录和结果位置仍需由 CMake 提供；固定命令行参数已经能够传递这些输入，不为减少参数个数增加中间文件，也不把请求数据写入共享发行清单。

**长期同时维护 Python 生产者与 Go 消费者。** 保留两套工具语言和测试环境；本项目自有工具统一到 Go，过渡只为安全切换，不作为长期架构。

**单个 Go 程序同时包含生产与消费命令。** 减少一个可执行目标，但混合独立的调用入口与生命周期，并向下游交付其不需要的生产能力。选择同一 module 下的 builder/importer 两个目标，共同遵守协议，不预建共享实现层。

**本地来源缺包后联网补齐。** 违背用户手动准备发行输入和明确离线边界的要求；缺失即报错。

**要求手工安装 Go，或把 SDK 放在 build 下。** 增加首次使用的环境配置，并使普通构建清理丢失已下载 SDK；选择仓库根 `.tools/go/` 自动准备与缓存，既不污染全局环境，也不因清理 build 重复下载。

## 验收标准

- 根 Go module 下可分别构建 `autolib-builder` 与 `autolib-importer`；生产逻辑不进入 importer，消费流程不依赖 builder，不预建独立产物源码层或共享层。程序、生成文件、staging 和归档均位于 Git 忽略的构建目录。
- builder 生成命令通过现有行为对应的公共回归，真实根入口仍生成原生 ExternalProject，模块配置、依赖接线、增量输入及数据保护边界不变；自有 Python 入口退出正式路径。
- 未安装系统 Go 的生产入口自动获取固定宿主 SDK、校验摘要并准备缺失 Go 模块；清理或更换 build 后仍复用 `.tools/go/`。下载、摘要、解包、版本与依赖获取失败均停止，不执行旧 builder；私有环境不改变用户 Go 配置或全局环境，不升级工具链及依赖，重复构建保留未变化的生成文件时间戳。
- OpenCV/HarfBuzz 的解释器引用有针对当前功能的实际证据；不以 Python 被检测到证明必需，也不以关闭绑定证明构建已验证。若存在真实必需项，先取得用户决定再完成受影响切换。
- `src/autolib.cmake` 单文件可独立搬运，不依赖旁置 CMake helper；本地发行目录包含 importer、manifest 和所需包时，消费者仅凭该入口、CMake、系统可执行能力及编译链接所需工具即可首次导入，不依赖 Go/Python/uv、builder 或其他语言包；来源输入保持不变。
- 同一 `manifest.json` 描述 importer 与库包，importer 记录为四字段，包记录为五字段，入口不内置工具发行摘要；缺清单、缺宿主记录、非法 asset 及错误摘要均在执行相应程序前失败。保持固定调用接口的 importer 替换并显式刷新后，无需修改入口即可导入；已有本地 importer 不自动更新。真实 CMake fixture 验证来源、请求包、目标平台、工作目录、结果位置及本次已取得的清单路径通过参数传入，入口不执行启动前版本查询或协议协商。
- 首次本地导入缺 importer、manifest、包或依赖包时明确失败；带网络请求记录的隔离 fixture 验证完整输入与缺失输入路径均未发起网络访问，不能只靠错误文本或预热缓存证明离线性。
- 受控 HTTPS fixture 证明 importer 和包都取自指定发行根；摘要错误的 importer 不执行，程序启动或准备失败时不加载残留结果。错平台、非法 asset、错误摘要及越界归档的包不导入，失败重跑不损坏已有最终包。
- CMake 引导与 importer 均验证证书，接受 HTTPS 资产重定向并拒绝降级；归档 fixture 覆盖规范化重名、类型冲突、链接越界和特殊文件；结果路径包含中文、空格及 CMake 特殊字符时仍为数据。
- 代表包在不同前缀搬迁后实际编译链接，动态库完成最小运行检查；包内 adapter 可重复加载，依赖按显式 sibling 定位，不回退系统包。打包不修改原安装树。
- 两个 Go 目标均以禁用 cgo 的配置构建；三宿主 importer 二进制在对应平台执行最小工具与消费验证，builder 随生产端入口验证。记录工具最低运行要求与库 ABI 要求，缺实机证据的平台不得标为已验收。
- Windows 消费 fixture 通过真实 CMake 验证盘符、UNC、中文及空格路径、`.exe` 选择和结果文件读取；各宿主验证临时目录提交与失败保护，不能用 Linux 成功推定 Windows 文件语义。
- 阶段完成时更新当前架构、开发、测试及模块技能的实际所有者文档；全部完成后再运行整体回归。真实远端结果必须有对应授权及证据，不以本地协议测试冒充远端发布成功。

## 风险

Go 会引入 SDK 和第三方模块的首次下载成本，但这些不进入消费者安装流程。生产端由 CMake 自动准备并在 `.tools/go/` 复用；无缓存且无网络的源码构建仍不能凭空获取输入，不能把消费者离线保证扩大为任意源码环境无准备构建。

两个目标需要分别构建和测试，发行格式或固定调用接口变更须核对受影响的生产端、入口与消费端。通过同一发行协议及端到端 fixture 保持一致，不为减少目标数量合并生命周期，也不为避免少量重复提前增加共享框架。

移除解释器路径可能暴露上游实际要求，必须按已选配置验证。既有 C++ 安装成功和 importer 不依赖 glibc，均不能证明库包已经自包含或可搬迁；系统开发包、运行库和预编译输入的兼容性仍需独立说明。

发行清单必须与目录中的 importer 和归档字节一致，资产与清单更新期间的不匹配会由摘要校验拒绝。importer 独立更新须保持固定命令参数和结果格式；若确需改变这一接口，必须同步修订入口，清单不承担调用方式发现。固定槽更新也可能被已有本地工具或安装包遮蔽；遵循显式刷新而非自动覆盖，不增加历史版本选择、后台更新或恢复服务。
