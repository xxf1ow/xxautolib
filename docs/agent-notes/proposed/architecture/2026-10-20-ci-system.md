# Agent Note: CI 系统与三平台代表库发布

Status: proposed

## 问题

本地构建、打包和消费链路已经可用，但没有 CI 生产可下载的 Release 资产。先实现 HTTPS 消费仍缺少实际发行源；先批量增加第三方库也不能验证发布流程。首期需要用少量代表库建立三平台构建、缓存、打包、发布和真实消费的闭环，再按需增加耗时模块。

本地双平台安装验证不能替代三平台二进制发布，也没有定义发布环境 ABI。按依赖层分别启动 job、重复准备环境和传输完整包，会增加时间及存储；单平台单 job 则改变重跑边界与资源占用，需要保留依赖顺序和失败语义。

## 方案

CI 是独立的生产与发布系统，本文统一拥有其目标、范围、组件协作、触发、环境、缓存编排、发布汇总、失败处理及验收要求，不作为 Go 工具层迁移或 HTTPS 消费的子阶段。首期建立手动触发的三平台原生单 job 流水线。本仓库尚无 CI，本文为待实施设计；本地交付与当前消费接口保持可用，HTTPS 消费暂缓。系统之间的接入顺序由[路线图](../../../roadmap.md)拥有。

CI 调用既有 Go 工具及 CMake 构建入口，不另造模块声明或消费协议。[Go 工具层设计](2026-10-21-go-tooling-and-offline-import.md)继续拥有工具准备、importer 调用与来源协议；[二进制交付设计](2026-10-20-name-only-artifact-delivery.md)继续拥有包格式、可搬迁规则和缓存完整性。本文拥有这些能力在 CI 中如何组合运行，不要求普通本地构建依赖 GitHub 或 workflow。

环境主要参考 `D:/Work/AutoLibBuilder` 的最终设计 `docs/agent-notes/proposed/process/2026-10-08-native-linux-single-job-tiers.md`，参考基线为 `4ae4d92`。该方案本身尚未实施；不复制参考仓库现有 manylinux、多 job 传完整包、Python 工具及 YUM 元数据再重写，也不继承历史清理操作或远端授权。

### 首期范围与入口

首期构建、生产缓存与 Release 发布只覆盖 queue、lz4、flann。queue 覆盖平台无关头文件包，lz4 覆盖源码静态库，flann 覆盖源码动态库与显式 `flann → lz4` 依赖。复用 `tests/autolib/` 已有本地消费夹具，并补齐 Linux x86_64 的真实执行证据。OpenCV 等其余模块不进入首期构建或验收，不因已能本地构建便自动加入 CI；流程验收后再按需增加，不要求先补新库。

仅提供 `workflow_dispatch`，输入为目标平台、代表集内的模块选择和强制重建；默认选择三平台及三库。生产计划复用 builder 的稳定依赖闭包，选择 flann 时带上 lz4；未知或超出首期集合的模块报错。首期不增加 push、PR、定时或自动发布触发。

平台和模块输入采用逗号分隔的完整标识列表，去除各项两端空白后去重；平台标识为 `windows-x86_64`、`linux-x86_64`、`linux-aarch64`。省略输入使用默认值，显式空列表、空项、未知标识及非法强制重建值均在规划时失败。仅选 lz4 或 queue 合法，仅选 flann 得到 lz4、flann；单平台请求只执行该平台，不额外启动未选平台。

发布目标为 `xxf1ow/xxautolib` 的固定 Release tag `autolib-release`。只有默认分支可写，workflow 和发布程序分别检查；其他分支可构建和验证，但不创建或替换 Release 资产。非默认分支仅可读取通过全部完整性与 build ID 检查的生产缓存；新构建的本地产物只在本 job 内复用，不承诺换 runner 或手动重跑后仍存在。成功层的跨运行发布复用仅适用于获准写 Release 的默认分支运行。

写入前以目标仓库 API 返回的默认分支名核对运行 ref，要求为对应 `refs/heads/<分支>`，并核对实际 checkout HEAD 等于本次运行记录的 SHA；禁止从默认分支事件改为 checkout 其他代码后发布。分支判定及代码一致性检查在创建 Release、替换任一资产或提交清单之前完成，tag ref 不作为可发布分支。默认分支在运行期间新增提交不要求本次自动追赶最新 HEAD。

所有受支持的 Release 写入，包括手动重跑、初始化、平台上传和 finalize，均由同一 workflow 入口协调；整个运行使用按目标仓库和固定 Release 命名的同一并发组，不按 ref、平台或 workflow 名拆组，不取消正在运行的替换操作。同一运行的平台只写各自获准的槽位，统一元数据仅由 finalize 写。独立直接调用发布程序、其他 workflow 或人工编辑不支持与它同时写入；人工维护须先等发布结束，不为此增加分布式锁或清单 CAS 协议。

Release 不存在时，唯一初始化步骤在分支检查后创建；固定 tag 缺失时以本次获准 SHA 初始化，已有 tag 则复用，不自动移动或删除。固定 tag 是资产集合入口，不表示全部资产都由该 tag 指向的提交构建；各槽位的生产提交记入生产元数据。已有 tag 或 Release 不能读取、认证或网络失败时停止，不当作不存在，也不强制修复 tag。

workflow 默认仅授予 `contents: read`；确实执行 Release 初始化、上传或 finalize 的默认分支 job 才授予 `contents: write`，其余权限不额外开启。checkout 不持久保存凭据，发布凭据只传给需要它的步骤，不写入源码、日志或持久配置。权限按 job 生效；同 job 内保留成功层发布能力，不承诺构建与发布步骤之间存在独立安全隔离。

确认目标仓库和 tag 只确定设计对象，不授权立即 push、触发远端 CI 或写 Release；这些操作需另获明确授权。本设计不包含 Gitee 镜像、历史资产迁移、远端删除或自动清理。

### 组件职责与数据流

workflow 负责手动输入、原生 runner/container、具名步骤、权限和失败汇总；builder 负责模块计划、内部 build ID、缓存校验、暂存打包、Release API 操作及清单汇总。新增公共编排仍归现有生产工具，不引入独立产物源码层、Python 工具、后台服务或持久步骤数据库。CMake/ExternalProject 继续负责源码获取、补丁、配置、编译和安装；importer 只处理消费协议，不调用生产流水线。

规划输出选中平台、模块依赖层和通用包唯一 publisher；各平台准备一次环境，复用有效缓存或构建缺失库，暂存打包并完成消费验证，随后上传获准发布的资产和本次成功槽位元数据。独立汇总步骤合并记录，最后更新唯一的 `manifest.json`。规划及汇总只传实际需要的小型元数据，不通过 Actions artifacts 传完整包。

CI 沿用已有本地打包链路生成本机 importer 和对应记录，随本平台发行物提交，并在该原生平台执行 smoke 和本地消费验证；importer 仍严格按宿主平台区分，不使用 any/any。这里不实现消费入口的 HTTPS 下载：CI 可通过 GitHub API 获取生产缓存，消费验证仍从本地完整发行目录进入 `autolib.cmake`，本地来源绝不联网的契约不变。

规划成功后才启动选中平台；规划失败不执行发布。平台之间不因一个平台失败而取消其他已选平台，矩阵使用 `fail-fast: false`。finalize 在平台成功或失败后均检查可取得的成功记录，校验其代码、计划和目标一致，不以依赖 job 默认成功条件跳过失败汇总，也不将缺失记录视为成功。成功层的验证与元数据提交不能只依赖最后一个全库验证步骤。

手动取消、runner 中断及超时均不能保证 finalize 或清理必达。超时值在 workflow 中显式配置，不设置后台恢复任务；这些运行不计为验收成功，已进入统一清单且仍匹配字节的槽位可复用，其余按下文缓存规则重跑。临时文件只在本次受控构建目录内准备，不清理用户目录或历史远端资产。

### 原生分层与并行

Windows x86_64、Linux x86_64 和 Linux aarch64 各使用一个原生构建 job，平台间可以并行。C++ 库不使用交叉编译、Zig 或 QEMU；Go importer 的交叉编译与逐宿主运行验证由 [Go 工具层设计](../architecture/2026-10-21-go-tooling-and-offline-import.md)拥有。Linux 每个平台共用一个 Actions 原生 container job；Windows 保留 Visual Studio/MSBuild，不传 Linux Make 参数。规划和最终汇总可保留独立辅助 job。

每平台按具名步骤执行环境准备、实际依赖层、消费验证和产物汇总；首期只有代表集需要的层，不为参考方案的 tier 数量或 OpenCV 创建空步骤。依赖层顺序执行，不增加后台调度器；非空前置层失败时不继续依赖构建或报告成功。后续加入 OpenCV 时仍按实际依赖排序，不预建专用调度机制。

环境和该计划所需系统依赖集中准备一次；后续层复用本 job 已校验的安装产物、归档和元数据。每个成功层保留固定槽 Release 发布能力，让失败后重跑可复用成功产物，不另存步骤完成数据库。只在获得发布授权时启用写操作，完整性和发布顺序遵循[二进制交付设计](../architecture/2026-10-20-name-only-artifact-delivery.md)。

不上传供层间传输的完整包 Actions artifacts，正式产物与固定槽缓存使用 Release；独立规划/finalize 实际需要的小型元数据仍可用 Actions artifacts。单 job 不能单独重跑某一步，接受重跑时重新准备环境的成本。

### 环境与 ABI

| 对象 | 沿用的目标 | 边界 |
| --- | --- | --- |
| Linux 基础环境 | Docker Official Image Ubuntu 20.04，GCC/G++ 9.4 来自官方 APT | glibc 2.31；不加 Toolchain PPA，不逐包换编译器；实际镜像 digest 须覆盖两架构。 |
| Linux 运行库 | Ubuntu 官方配套 libstdc++ 与 libgcc，动态链接 | 不要求运行库包版本号等于 GCC，不静态捆绑运行库或切换旧字符串 ABI。 |
| Linux 并行 | GNU Make 4.4.1 FIFO jobserver | 公共入口传 `--jobserver-style=fifo` 并统一预算，父子用同一 Make，不逐包追加独立 -j。 |
| CI CMake | Kitware 官方 CMake 3.31.12，显式固定补丁版 | 版本更新须修改配置并验证；项目最低版本仍为 3.20。 |
| Windows | windows-2022 原生 VS 2022 x64、Release、普通模块默认 v143 | 保留完整父生成器身份和显式 CRT；不全局降为 v142，不承诺 runner 的 MSVC/SDK 补丁固定。 |

Linux 原生 runner 分别采用 `ubuntu-24.04` 和 `ubuntu-24.04-arm`；Ubuntu 20.04 是 job 内容器用户空间，不是 runner 宿主版本。首个远端运行前检查目标仓库可使用这些 runner，启动后校验 runner 与容器实际架构；标签不可用或架构不符即失败，不回退 QEMU、交叉编译或不同 ABI 基线。

实现配置固定一个覆盖 `linux/amd64`、`linux/arm64` 的 Ubuntu 20.04 多架构索引 digest，两平台引用同一索引并记录各自实际子镜像 digest；不能只写可漂移标签。首次固定及后续更新均从官方镜像索引检查两种架构，更新通过显式配置修改，并在受影响两平台正常运行中验证，不维护自动镜像升级器。具体 digest 是实施配置中的校验值，不从参考实验照搬。

APT 使用 Ubuntu 官方 Focal 源及其 updates/security pockets：x86_64 使用 `archive.ubuntu.com/ubuntu`、`security.ubuntu.com/ubuntu`，aarch64 使用 `ports.ubuntu.com/ubuntu-ports`。首期不接入 Ubuntu Pro/ESM 订阅，不承诺这些公开源仍提供持续安全维护；记录实际包修订和来源。源不可用或所需版本缺失即停止，不自动改用 old-releases、第三方源或升级发行版；涉及来源或基线变化时交由人工决定。[Ubuntu 官方支持状态](https://ubuntu.com/20-04)明确 20.04 已结束标准支持。

工具从官方来源取得并校验，版本更新须显式修改，不动态选择 latest。自有生成器与公共测试使用根 go.mod 固定的 Go SDK 和模块依赖，不在 CI 中维护第二套生成器环境。Linux 系统依赖只维护 APT，Windows 保留 Chocolatey；不为只支持一个 Linux 发行版的目标复制 YUM/DNF 准备。各模块声明自己的系统依赖，不靠其他模块缓存未命中时偶然安装。

后续公共配置沿用 `CMAKE_INSTALL_LIBDIR=lib` 与 `CMAKE_POLICY_VERSION_MINIMUM=3.5`，后者只提供低版本 policy 下限，不覆盖上游更高要求。policy 已由普通根入口传入子项目，机制见[模块扩展决定](../architecture/2026-10-20-module-expansion.md)；固定安装库目录仍待接入。Linux 源码构建产物的 glibc 需求不得高于 2.31；C++ 运行需求独立记录 GLIBCXX、CXXABI、libgcc 符号，不用 glibc 版本代替 C++ ABI 判断。静态归档须经实际下游链接验证，预编译输入单独记录兼容要求，不能因默认 GCC 9.4 就视为同基线源码产物。

正式构建记录工具版本、来源和实际发行版包修订，Windows 记录 runner image、cl、MSBuild、SDK 与 CMake 实际版本。容器内只对实际 checkout 设置必要的 Git 信任，不修改用户机器的全局信任列表。镜像更换不等于现有 build ID 自动失效；新仓库不复用旧发布集合，不为此预建通用工具链状态管理。

GCC 9.4 是配置决定，不是全部模块已成功的声明；不额外全包试编译来重新决定选型。正常 CI 失败如实报告，不自动升级编译器。Ubuntu 20.04 的工具来源可信不等于仍有免费安全维护，落地时须明确镜像及补丁来源；任何改变基线的方案须另行确认。

### 并行预算与 CI 历史核验

Linux 每个平台在容器内以 `nproc` 得到当前可用 CPU 数，取至少 1 的整数 N；顶层 Make 仅在公共入口设置 `-jN --jobserver-style=fifo`。同平台的各依赖层顺序执行并各自使用这一预算，平台间不共享 token；准备工具和测试进程不属于 Make 编译任务预算，也不与库构建后台重叠执行。

公共入口及生成逻辑确保父子构建使用同一 Make 4.4.1，保留嵌套调用所需的 `MAKEFLAGS` 和 FIFO 路径，向子 CMake 正确选择相同 `CMAKE_MAKE_PROGRAM`。子构建不重新传入独立 `-j` 或带数量的 `--parallel`，不让 `CMAKE_BUILD_PARALLEL_LEVEL` 覆盖继承预算。不逐包修改构建命令，也不以必须升级到 CMake 4 的 pipe jobserver 修复替代 FIFO 方案。

首次有真实编译的 CI，以及修改并行接线后的首个相应运行，必须及时查看运行历史、job 日志和实际父子构建命令，不等全部库扩展后才判断 `-j` 是否有效。记录运行 URL、提交 SHA、平台、N、Make 版本、jobserver 传递、warning 及 worker 探针峰值；仅记录相关参数，不输出完整环境或凭据。结合小型嵌套 Make 探针验证参与任务的峰值不超过 N，N 大于 1 时确有重叠工作，并检查真实 lz4/flann 构建没有独立预算重置或 jobserver 单线程回退。

历史记录只对相同并行接线和相关环境提供证据，不用旧的通过结果掩盖本次失败；仅有顶层命令带 `-j`、无 warning 或墙钟缩短，都不足以单独证明有效。缓存全命中时没有真实编译证据，应如实标记；需要补证时，在获得运行授权后仅选择一个受影响平台和小型编译库强制重建，不扩成耗时库或反复全量测试。发现预算失效先处理公共接线，不通过逐库追加 `-j` 继续扩大发布范围。

### 固定槽缓存与汇总

生产缓存按[二进制交付设计](../architecture/2026-10-20-name-only-artifact-delivery.md#缓存与发布)核对 manifest、私有 build ID、GitHub digest、实际下载字节和包内身份；安装 sentinel 的存在性不能代替发行缓存完整性。内部 build ID 覆盖相关模块、来源、补丁、adapter、依赖构建输入和共享生产代码，不进入公开清单或文件名。强制重建绕过相应缓存判断。

生产缓存复用同一份正式包资产，不另存一套缓存归档。包名为 `<name>-<os>-<arch>.tar.zst`，工具为 `autolib-importer-<os>-<arch>`（Windows 加 `.exe`）；`manifest.json` 为消费清单，`build-cache.json` 为保留给生产者的私有缓存元数据资产，不进入消费清单的包或工具数组。两份元数据均由 finalize 单独合并写入；私有记录按包槽保存 build ID、归档 SHA256 和生产提交，缓存命中时其摘要必须同时匹配公开记录和实际资产，不能只信私有 ID。importer 随本机工具构建验证，不在首期增加独立 importer 生产缓存。

build ID 的可测试输入包括归一后的本模块有效 TOML 配置、固定来源版本及已登记归档摘要、实际引用的补丁和专用文件内容、adapter、传递依赖的构建输入，以及共享生成、暂存、打包和缓存身份代码；保留依赖 adapter 独立变化不传播到使用方的既有规则。机器码包包含 OS/架构及生效的生成器、工具集、CRT、Release 配置和构建选项；通用包不包含 publisher 宿主身份。配置文件中显式维护的工具/基线选择属于共享生产输入，相关修改使对应缓存失效；不散列全部进程环境、系统包修订或 hosted runner 补丁，不建立通用环境指纹。更换未被输入覆盖的实际 ABI 基线前须先修改显式基线配置，不能仅换环境继续复用旧缓存。

强制重建覆盖本次所选平台上的完整模块依赖闭包，包括自动补入的 lz4；绕过 Release 包缓存及本地安装 sentinel 短路，使用本次隔离的构建安装目录，仍可复用校验合格的源码输入和工具下载。未选平台、闭包外模块和其他槽位不受影响。构建或验证失败且尚未上传时，旧有效槽位保持不变；强制重建成功允许以实际新摘要替换同 build ID 的固定资产，不以归档字节不同判定为可复现性失败。

各平台仅替换自身获准写入的固定资产，不单独覆盖统一 manifest。汇总只有一个写者，从已有清单保留本次未更新的平台与包记录，合并本次已成功上传且核验的槽位；只运行一个平台不得清空另两个平台。首期沿用清单顶层 `importers`、`packages` 及其既有四字段、五字段结构，私有缓存信息不混入公开记录。

finalize 在持有该运行并发约束期间读取现有清单，先核对本次成功资产，再写私有缓存元数据，最后提交公开 manifest。首次无 manifest 按空集合初始化；已有 manifest 无法解析或读取失败则停止，不用空清单覆盖。读取和写入都在同一串行运行内，不支持外部写者穿插修改，因此不另增乐观版本协商。

对每槽区分四个事实：构建并验证成功、资产上传且核验成功、公开清单已提交且引用匹配字节、消费者可按清单获取使用。上传成功不能单独算发布成功；私有元数据也匹配时，该已发布槽位才可作为生产缓存命中。某槽完成不要求所有选中平台都成功，但整次运行只有全部请求通过且所需发布提交成功才算成功。

某平台或后续层失败时，汇总仍处理可取得的成功槽位元数据，但整个运行保持失败，不发布依赖于失败前置工作的产物。已发布并进入清单的成功槽位可供重跑复用；失败槽位不能借旧缓存或其他平台成功而算作本次通过。若固定资产替换后、清单提交前中断，旧清单可能与新字节不匹配，消费者或缓存按摘要拒绝并由显式重跑修复，不承诺跨资产原子性、自动回滚或持续可用。

重跑时，缺包、build ID 不符、私有记录缺失或字节/身份检查失败均按该槽缓存未命中处理，记录原因并重新构建、验证、上传和提交清单，不直接把孤立新资产补成可信发布。认证、API 网络错误及已存在清单的解析错误使运行失败，不归类为可用缓存或悄悄当作空集合。只修复本次计划覆盖的槽位；其他不一致槽位报告而不自动重建或删除，待显式选中后处理。

### 平台无关头文件单槽位

只对模块显式声明且安装树及导出配置均不含平台相关内容的包启用通用槽，不以“没有 DLL/so”推断。首期对象为 queue：安装仅复制六个原始头文件，adapter 不包含平台路径或生成配置。manifest 和包内身份统一使用成对的 `os=any`、`arch=any`，唯一固定资产为 `queue-any-any.tar.zst`；不支持半通用槽，同包不得同时有通用和平台限定槽，不增加回退优先级。

规划在本次选中平台中按 Linux x86_64、Linux aarch64、Windows x86_64 顺序唯一选择 publisher。其他已选平台继续正常消费验证，可使用既有缓存或本地产物，不上传、不等待 publisher，也不在失败后自动接管；未选平台不执行验证。publisher 失败不取消其他已选平台的工作，最终该包发布失败并使整次运行失败，保留各平台实际验证结果。切换 publisher 不改变包身份。

模块声明维护者负责核实通用资格，builder 在通用打包时核对安装内容与声明；queue 限定为声明的六个原始头文件和平台无关 adapter，发现额外二进制、生成配置、平台路径或不符合已声明输入的内容即阻断通用发布，不仅发 warning，也不自动降级为平台槽。首期不开发可判定任意头文件库平台无关性的通用分析器。各平台本地验证包可有不同归档时间、权限等元数据及压缩摘要，不要求压缩字节相等；实际文件内容必须符合共同声明，唯一 publisher 上传的实际字节决定公开摘要。

模块声明、规划、内部 build ID、打包、包内导入、manifest、缓存、importer 和测试须同步支持通用身份；queue 的发布身份和 build ID 不因 publisher 宿主变化而变化。通用包适用于已有支持的平台，不扩大操作系统支持；lz4、flann 及 importer 继续严格匹配各自 OS/架构。参考方案的 Eigen 不进入首期集合。新仓库从空发布集合开始，不迁移旧发布资产，不新增历史槽位兼容或自动远端清理；未来镜像若接入，须遵守相同身份约束。

### 发布前检查与消费验证

每槽上传前必须通过声明与身份检查、实际字节摘要、适用的 ABI 检查及相应真实消费验证；任何必需项失败禁止上传该槽。平台仅选择部分模块时，只验证实际依赖闭包：queue 执行入出队，lz4 执行压缩解压并比对原文，flann 在 lz4 就绪后执行索引创建、释放及动态库加载路径检查。复用 `tests/autolib/` 的真实行为并适配模块选择，不为了让固定三库夹具通过而补建未选库；完整代表集仍执行发行目录及准备包搬迁后的编译、链接、CTest 运行和字节不变检查。

Linux 两架构分别以 glibc 2.31 及该发行版官方配套 libstdc++、libgcc 为消费基准，记录 GLIBC、GLIBCXX、CXXABI、libgcc 实际需求；GLIBC 高于 2.31、所需运行库符号无法由基准环境提供或真实链接运行失败均禁止发布。静态 lz4 通过真实消费者最终链接与运行检查，不只扫描 `.a`。预编译模块不在首期，后续增加时须以登记版本与归档摘要参与身份，并独立验证其运行要求，不冒充同基线源码构建。

Windows 首期使用 VS 2022 x64/v143、Release 和显式 `MultiThreadedDLL`（`/MD`）；生产者、直接依赖和消费者核对实际 CMake cache、完整生成器身份、编译/链接命令及运行结果。hosted runner 的 MSVC/SDK 补丁变化可在仍满足这些要求且本次必要检查通过后发布；工具集、CRT、目标架构或显式基线变化须修改配置、失效相关缓存并重新验证。首期不承诺 v142 产物，v142 实机验收不阻塞 v143 发布；未来显式增加 v142 或改变相关支持承诺时再安排专项人工验收。

已有 importer 测试覆盖本地来源禁止联网、具体平台错配和危险归档拒绝；any/any 选择、半通用身份与槽共存拒绝、publisher 选择及局部发布为本次增量覆盖。各承诺平台仍须执行对应原生测试，不能以 Windows/aarch64 的本地历史证据代替 Linux x86_64。日志版本、耗时和磁盘峰值是诊断信息，不单独作为成功门槛；无空间等实际错误仍使受影响工作失败，不为首期额外设容量配额或多轮性能基准。

### 触发凭据与运行证据

人工或助手触发 CI 使用调用方提供的凭据，不把本地 token 上传为仓库 secret，也不以本地 token 代替 job 内的 `GITHUB_TOKEN`。实施前分别确认身份、仓库访问和 Actions 查询能力；读取公开 workflow 或运行列表成功不证明具有触发权限。fine-grained token 的 dispatch 需要目标仓库 Actions 写权限，首次真实 dispatch 必须在 workflow 可用且取得远端运行授权后执行，并确认对应 run 产生；没有 workflow、没有历史或未做 dispatch 时如实记录未验证，不发送伪造请求冒充权限测试。权限依据见 [GitHub dispatch 文档](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)。

实施过程中通过运行历史及时查看与当前提交对应的 job、失败步骤和原生构建日志，尤其核验上文 `-j` 与 jobserver 证据；不可只看 workflow 总状态。无历史时先记录证据缺口，不能据此声称并行已经生效，也不因此未经授权创建或触发远端工作。

## 备选方案

**每层独立 job。** 可以单独重跑并跨 runner 并行部分层，但重复环境准备和整包传输；选择单平台共享环境，保留具名步骤。

**交叉编译或预制第三方构建镜像。** 前者增加目标工具链与运行验证，后者增加镜像发布及补丁维护；采用原生 runner 和官方小镜像现场准备，实际瓶颈出现后再评估。

**升级 CMake 4 或逐包追加 -j。** 前者提高最低要求，后者可能超额并行；沿用公共 FIFO jobserver 方案。

**三个头文件平台记录共用一个资产。** 仍维护重复摘要和身份映射；显式 any/any 单槽直接表达范围，机器码包不放松检查。

## 验收标准

- 获得远端授权后，queue、lz4、flann 在三平台各自原生单 job 完成所需依赖层、打包、搬迁后的真实编译链接与最小运行；本机 importer 完成运行验证。准备只执行一次，不执行 OpenCV 等其余库，不为形式完整建立空层。
- 手动选择平台和模块、flann 依赖闭包、强制重建以及 workflow/程序两层默认分支写限制均可观察；非默认分支不产生 Release 写操作，无 push/PR 自动触发。
- 缓存全命中、部分缺失、输入变化和强制重建遵守 build ID 与完整性规则，损坏缓存不能当作成功；重跑复用已成功发布的槽位，不通过 Actions artifacts 传完整包。
- 单平台发布保留其他平台记录，资产先于 manifest，只有一个汇总写者；前置层失败阻断依赖工作，部分平台失败仍保留成功槽位且整个运行失败。用小型协议 fixture 验证这些分支，不反复重建完整代表集模拟每种故障。
- Linux 嵌套构建在 N 大于 1 时有实际重叠 worker 证据、参与任务峰值不超过 N 且无 jobserver 单线程回退；同一公共预算覆盖父子 Make，不靠逐包命令修改。首次真实编译及并行接线变更后的 CI 及时检查历史与日志，记录相应 run 和命令证据，缓存全命中不冒充有效性验证。
- 正常发布的必需检查按上文执行，部分模块不补建全代表集；记录工具与符号需求，源码与预编译覆盖分开报告。Windows v143 工具链和 `/MD` 实际一致，不以未承诺的 v142 作为首期门槛。
- queue 在多平台及单平台请求中只有唯一 publisher 和一个 any/any 槽；三平台正常消费成功，其他平台不上传、不等待或自动接管。混合身份、槽共存和机器码错平台均拒绝，选择与冲突以小型 fixture 覆盖。
- 在一致模块与缓存条件下报告环境准备、平台/整体墙钟、累计 runner 时间和磁盘峰值，不承诺单 job 必然更快。
- 输入错误在规划时拒绝，非默认分支仅只读复用匹配缓存，强制重建覆盖本次依赖闭包；缓存元数据与公开摘要绑定，资产/清单中断后的显式重跑修复被本地 fixture 验证。首次获授权的真实 dispatch 确认凭据可触发运行，认证或只读 API 成功不能替代该证据。

## 风险

合并 job 减少跨 runner 并行，可能增加整体墙钟；同 job 构建与产物长期共存会提高磁盘峰值，不能提前删除后续层仍需内容。运行环境、下载源和 hosted runner 会变化，本记录不把历史局部实验当作三平台全量验证，也不以提前增加自动恢复或自托管 runner 消除此限制。
