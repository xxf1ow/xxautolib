# Agent Note: 本地安装产物直接消费与统一目录

Status: proposed

## 问题

本地源码构建将库安装到 `3rdparty/<包名>/`，但 importer 只识别另一个准备目录，且消费 adapter 和包内元数据直到打包才生成。因此，编译成功的库仍不能直接通过 `autolib_import()` 使用，用户需要额外打包再解包。已有本地 importer 只能执行获取流程，不能补足这些消费描述。

本地构建安装应首先交付可直接消费的产物，Release 是这些产物的后续分发方式。消费描述的生成属于 builder，不能由 importer 推测，也不能由 CI 维护另一套生成规则。

## 方案

普通本地构建自动生成宿主 importer，并为提供消费 adapter 的模块生成包内身份、依赖及 CMake 导入文件。消费者将本地根指向安装根即可导入，不需要移动库目录、创建归档或手工复制工具。下载解包与源码安装使用相同的 `<本地根>/<包名>/` 布局。

本设计拥有安装产物的消费准备时机、宿主工具输出和扁平本地目录，部分替代[无全局清单包消费](2026-10-24-manifestless-package-consumption.md)的 `packages/<平台>/` 准备位置与打包时生成包头的规则，以及[按目标导入设计](2026-10-25-target-import-and-release-consumption.md)继承的本地布局。四行包头、名称依赖遍历、损坏校验、远端发现和 CMake 公共接口仍由这两份记录拥有。[Go 工具层设计](2026-10-21-go-tooling-and-offline-import.md)与[固定槽交付设计](2026-10-20-name-only-artifact-delivery.md)继续约束独立可执行目标、安全解包及 staging 搬迁修正；本文只将消费文件生成提前到安装完成。

GitHub 下载阶段已经验收，其证据与 Gitee 后置安排保留在按目标导入设计中。本设计不重做远端协议，不实施 Gitee，不新增清单、版本求解、工具链变体、自动更新、恢复服务或跨运行生产缓存。

### 统一本地目录与平台检查

以 Windows x86_64 安装根为例：

```text
3rdparty/
  autolib-importer-windows-x86_64.exe
  queue/
    autolib-import.cmake
    include/
  lz4/
    autolib-import.cmake
    include/
    lib/
  flann/
    autolib-import.cmake
    include/
    lib/
    bin/
```

本地归档可按既有固定文件名放在同一个根下。importer 对每个请求包及依赖依次检查 `<本地根>/<包名>/`、本地归档、显式远端；本地归档和远端缺包都解包到同一个包目录。可复用目录只读检查包头、依赖声明及导入文件可读性，adapter 加载时检查其要求的安装文件；不逐文件散列，不证明载荷的全面完整性。不检查被目录遮蔽的归档或远端更新。缺省本地来源时，继续使用本次工作目录交付结果，不引入另一个隐式缓存来源。

包头中的名称、OS 和架构是消费身份依据。机器码包必须匹配当前目标，显式平台无关包继续使用 any/any；错平台、半通用身份及非法元数据直接报错，不靠目录层级判断平台，也不搜索另一个平台目录。普通本地构建沿用当前原生目标；本设计不增加交叉编译或多平台共根管理。

只有候选不存在才继续查找。目录已存在但缺少导入文件、类型错误、读取失败或身份不匹配时立即失败，不能从归档或网络覆盖它。权限、临时读取或符号链接异常同样失败，诊断给出包、失败路径及底层原因，不增加自动重试。通用与目标平台归档同时成为候选时，继续按原协议拒绝歧义。所有实际依赖位于同一本地根，保留 FLANN 与 lz4 的 sibling 布局。

归档文件名给出预期身份，解包后包头必须与之相符，并符合目标平台或 any/any 规则。沿用独立暂存目录、完整压缩流及安全解包校验，全部成功后才提交到不存在的最终包目录；失败不污染该目录。多个独立 builder/importer 进程或构建入口向同一本地根写入，由调用方串行安排，不支持与消费交错，不新增进程锁。同一次原生构建图可以按依赖并行构建不同模块，每个包目录只有该模块的单一安装和消费准备链路写入。

新 importer 不探测或自动搬迁 `packages/<平台>/`。已有数据不删除、不改写；需要复用的本地安装通过正常生产构建补齐消费文件，其他缓存由用户选择保留或重新准备。刷新仍只针对用户明确选择的 `<本地根>/<包名>/`，不因刷新一个包而删除共享依赖或整个根。

### builder 在安装后准备消费文件

模块作者继续在 `src/dependencies/<包名>/autolib-import.cmake` 维护 adapter 正文，在 `module.toml` 声明直接包依赖。builder 负责将当前模块的身份和归一后的直接依赖写入固定四行头，再附上 adapter 正文，输出到 `<安装根>/<包名>/autolib-import.cmake`。身份与依赖不另存第二个文件。

消费准备接入正常构建目标，执行关系为声明依赖模块完成、本模块安装成功、消费文件准备成功、本模块目标成功。提供 adapter 的依赖模块完成包含其消费文件准备完成；依赖失败阻止本模块继续。实际安装路径与 sentinel/stamp 复用路径都必须执行消费准备，不能只依赖可能被安装 stamp 跳过的后置命令。单独构建所选模块及其依赖也应满足该关系，用户不增加打包或独立准备命令。准备失败使本次构建失败，不自动恢复或删除已经安装的库。

实际安装命令修改载荷前，builder 先检查已有有效包头的名称和平台，再将自己负责的 `autolib-import.cmake` 置为明确的未完成内容，不含有效四行头；不能保留可误用的旧描述。只有本次安装成功路径才可将这份未完成内容替换为有效消费文件。安装失败保留载荷和未完成文件供人工处理，importer、打包及仅复用安装的准备路径均拒绝它。用户须保留需要的数据并重新准备受影响安装与原生构建状态，使真实安装成功；不能只凭残留 sentinel 补齐描述。此规则仅使用既有生成文件，不增加状态文件或自动恢复。

安装 sentinel 继续决定是否获取和重编第三方库，但不跳过消费准备。命中 sentinel 或已有原生安装成功 stamp 时，可补齐确实缺失的生成文件；已有文件若包头非法或名称、平台与当前模块不匹配则报错，不改标或修复。缺失包头的历史安装沿用既有 sentinel 存在性信任，身份来自当前生产配置，不是对历史机器码的认证；已知冲突拒绝，来源和编译选项变化仍由用户准备重建。不增加历史身份追溯或 ABI 证明。

生成输入覆盖当前平台生效的 `module.toml`、adapter、身份配置及消费生成代码；声明和代码变化进入原生重配置/构建依赖。直接依赖沿用 ASCII 排序去重，单纯调整声明顺序不改变输出，归一化逻辑变化通过生成代码输入生效。构建依赖决定何时重新检查，生成时复用 `writeIfChanged()` 比较最终字节；相同内容不写入、不改变时间戳，不依赖生成目标的时间戳推断内容。

消费准备只写 builder 负责的生成文件，不在原安装树中重写上游 CMake Config、pkg-config 或库文件。没有 adapter 的模块仍正常构建安装，不生成虚假的可消费声明；有 adapter 的包若声明依赖没有 adapter 的模块，消费准备失败并指出依赖，不能交付无法导入的闭包。本次不补 adapter，代表集继续使用 queue、lz4、flann。

通用包必须在消费准备时通过实际载荷资格检查，缺少历史包头不豁免检查。queue 仍只允许六个约定头文件，且核对固定来源的实际字节；唯一额外允许的文件是包根下 builder 负责的 `autolib-import.cmake`，不接受其他 `.cmake` 文件、机器码或额外载荷。打包沿用同一资格规则，不另建允许集合。

### 本地构建输出宿主 importer

生产端入口使用既有固定 Go SDK、模块缓存及禁用 cgo 的环境，独立编译 `src/autolib-builder` 和 `src/autolib-importer`。importer 输出到实际安装根，采用发行时相同的 `autolib-importer-<宿主OS>-<宿主架构>` 文件名，Windows 加 `.exe`；自定义安装根同样生效。它是普通本地构建输出，不要求用户复制 `build/tools` 中的程序，也不从 Release 下载。

生产入口在配置阶段将实际安装根确定为绝对规范路径，作为库安装、宿主 importer 输出及 builder 调用的同一个值。`AUTOLIB_INSTALL_ROOT` 相对值以顶层源码目录为基准，含空格路径作为单个参数传递；构建阶段不按另一工作目录重新解析，也不重新读取环境改根。更换根须重新 configure。

正常生产 configure/build 必须保证该工具为当前源码构建结果。输入跟踪覆盖 importer 生产源码的增删改、`go.mod`、`go.sum`、固定 Go SDK 与构建入口、构建参数及项目控制的 Go 环境配置；不追踪任意宿主环境变量。沿用 `go build -mod=readonly -trimpath` 和 Go 编译缓存，以构建成功退出为准，输出可以字节或时间戳不变；不自行诊断缓存内部状态。工具编译失败使生产入口失败，不能以根下旧程序存在作为本次成功依据；更新范围仅为该固定宿主工具文件，不清理根目录。Linux 输出需具备执行权限。

builder 和 importer 保持独立源码、独立可执行目标；生产入口可以分别构建它们，但不得把消费实现导入 builder 或在运行 builder 时嵌入 importer。消费者仍只需单文件入口、预编译 importer 和 C/C++ 消费环境，不在消费端准备 Go SDK 或调用生产构建。

同一次源码构建分别编译两工具，使用仓库共同约定的固定四行协议；协议变更同步修改两端，不兼容格式明确拒绝，不增加版本协商或任意历史工具混用保证。

### 打包与 CI 复用

`builder package` 要求选中安装产物已具备有效的消费文件。打包复制安装树及其中的导入文件，核对包身份与声明，不从另一套模板重新生成 adapter 或依赖头；缺失或不符直接失败，不把打包变成隐式修复安装的入口。

可搬迁处理继续只作用于独立 staging 副本：检查允许的本包和 sibling 生产引用，修正已知前缀，再生成带内容校验的固定名 tar.zst。归档顶层、包头协议及 Release 文件名不变，已有合规归档仍可按新布局解包。原始安装树的直接消费不增加任意搬迁承诺，归档产物继续接受搬迁链接运行验证。

CI 通过 builder/CMake 获得同样的安装结果，再调用 builder 打包和 importer 验证；发布工具复用本地构建生成的宿主 importer。[CI 系统设计](../../implemented/architecture/2026-10-20-ci-system.md)继续拥有平台环境、生产编排、发布权限、并发和汇总。适配只调整工具与安装产物的接线，不将生成规则放进 CI，不改变每轮重建、默认分支限制和同名替换策略。

### 消费接口、文档与实施范围

`autolib_import(TARGET app PRIVATE queue flann)`、一次性来源变量及其默认值保持不变。用户将 `AUTOLIB_LOCAL_ROOT` 指向生产安装根即可复用；宿主工具和所需包依赖闭包均在本地时，CMake 消费入口与 importer 不请求远端，显式空远端保证消费流程不联网。该承诺不覆盖生产端首次准备 Go SDK、Go 模块或第三方源码，也不覆盖用户工程自己的联网操作。缺包且配置 GitHub 时仍按原协议补齐，默认 Gitee 未实现时不隐式回退。

实现涉及 builder 安装后消费准备及宿主工具输出、importer 的最终目录计算、CI 与本地/远端验证夹具的接线。同步更新当前架构、开发测试指南、README 的本地使用说明及新增模块技能中的产物约定；不改 example 的调用形式，不新增 example 专用 helper 或 README。文档在实现时按实际行为更新，不提前将本提案写成已可用功能。

当前架构拥有组件职责与目录布局，开发指南拥有生产和消费操作，测试指南拥有验收命令及证据；README 提供用户接入示例并链接指南，新增模块技能描述贡献步骤并引用产物规范。四行包头和获取协议继续由已有包消费设计拥有，本文拥有安装时机与扁平布局；其他文档不各自维护协议副本。

本设计作为一个可验收的本地消费闭环实施，先证明正常本地构建可直接消费，再验证打包及下载链路。没有独立的后续功能阶段，不将 Gitee 或其他库接入混入计划。真实远端写入、CI 触发和新机器验证仍须另行授权，既有目录内的验证继续遵守数据保护约束。

## 备选方案

**保留安装目录与 `packages/<平台>/` 两套查找位置。** 可以继续探测现有缓存，但需要维护重复来源优先级及依赖跨目录组合；本地安装与下载产物使用同一布局即可保留 sibling 定位，不为缓存兼容增加查找分支。

**要求本地用户打包后再导入。** 可以沿用仅在 staging 生成消费文件的流程，但会让已经安装的库经历复制、压缩和解压，不满足本地编译完成即可消费的目标。

**将库专用链接规则塞进 importer，取消包内 CMake 文件。** 每接入一个库都需要修改并重新发布工具，且 Go 获取程序仍不能替代 CMake 创建链接目标。选择通用 importer 读取数据头、CMake 执行随包 adapter，同一个文件同时承载身份和链接规则。

## 验收标准

- 普通根 configure/build 选择 queue、flann 后，安装根具有宿主 importer、三个模块的完整安装和消费文件。消费者不执行 package、不移动目录、不手工复制工具，设置空远端后直接构建运行；通过既有真实消费夹具验证 queue、LZ4 和 FLANN C/C++ API，不额外补链。Windows 与原生 Linux 验证本地闭环，未执行的平台如实记录。
- 定向 fixture 以并行构建验证依赖安装及消费准备、本模块安装、消费文件准备的顺序；直接构建单模块不能漏执行。初装及重装失败都不交付有效描述，残留 sentinel 不能让未完成文件被补成有效包。sentinel 命中及原生成功 stamp 复用时可补齐真正缺失的文件且不重编第三方库。
- 内容不变或仅调整依赖顺序时保留消费文件时间戳；adapter、有效依赖和生成逻辑变化能更新对应结果。已有非法或错平台包头失败且不被改标。没有 adapter 的独立模块仍可构建，有 adapter 的包依赖无 adapter 模块时消费准备明确失败。queue 必须通过六头文件载荷检查，额外文件不因新增生成文件而放行。
- 正常本地构建自动输出正确命名的宿主 importer，含空格和相对的自定义安装根与库实际位置一致，Linux 工具可执行；源码及 Go 模块输入变化进入生产依赖，编译失败不能被旧工具掩盖。消费者无需 Go/Python，生产与消费可执行目标保持独立。
- 目录、本地归档和 GitHub 补齐均使用扁平位置。完整本地闭包零远端请求；已有坏目录或错平台包不回退好归档/远端；any/any 正常匹配，机器码错平台失败。下载和安全解包失败继续不覆盖已有输入，不探测旧的嵌套缓存。
- 打包复用安装中的生成文件，缺文件、未完成文件或身份不符失败；比较所选安装树打包前后的相对路径、文件类型、内容、符号链接目标、可用权限位及修改时间，不要求访问时间、所有者或全部系统元数据不变。归档保留固定名、包头和 Zstd 校验；真实搬迁后链接运行通过。
- CI 定向测试证明正常构建、打包、验证与固定名发布继续衔接，不复制 adapter 生成规则。GitHub 受控下载/引导和既有包归档验证沿用已有测试，仅适配目录；可使用已发布的合规资产验证新 importer，不能用旧阶段验收自动推定改动后的链路通过。不为该回归擅自重新发布资产。
- 局部验证针对受影响部分，整项完成后执行一次受影响工具的完整回归和文档校验。已有不受修改影响的证据复用，不重复开展上一阶段全盘审查，不制造新的公网异常资产。
- Windows 覆盖 `.exe` 输出、含空格根及既有 DLL 运行路径，原生 Linux 覆盖执行权限、并行依赖时序及实际链接运行；不以一端通过推定另一端通过，不穷举配置矩阵。未具备授权或环境的平台验收留作明确未完成项，不宣称整项验收通过。

## 验证结果

Windows x86_64、VS 2022/v143 通过普通根入口选择 `queue,flann`，命中已有安装并补齐三库消费文件，输出 `3rdparty/autolib-importer-windows-x86_64.exe`。直接消费 driver 使用原安装根、空远端，不打包或移动产物，CTest 1/1 实际验证 queue、LZ4、FLANN C/C++ API。打包复用该安装及工具，双搬迁两次 CTest 均为 1/1，安装、归档与消费包字节未变。三个独立工具的完整 Go 测试与 vet 均通过；builder 全集累计超过默认十分钟，验证使用 `-timeout=30m`。命令由[测试指南](../../../testing.md#本地二进制闭环)拥有。

原生 Linux 直接消费尚未验收。授权机器 `lxx@192.168.0.127` 的 `/home/lxx/xxautolib` 当前为 example 消费工程，缺少生产源码、Go SDK 和三库安装树；本轮未写入、传输或覆盖它。本记录保留 proposed，等待用户准备生产环境后验证 Linux 执行权限、并行依赖时序及真实链接运行；既有 GitHub 下载验收不替代本项。

## 风险

扁平目录不同时容纳同名库的不同平台或版本。平台错误由包头拒绝，目录不自动切换、覆盖或删除。嵌套缓存不自动迁移，用户保有其原始数据；本地编译使用已有 sentinel 的存在性假设，缺失包头的历史安装不能凭补写描述证明机器码身份或 ABI。

builder 新增写入范围限于安装根的宿主工具和模块消费文件。写权限不足或生成失败会阻断本次构建，不增加自动回滚。调用方不能交错修改或消费尚在安装中的目录；只读复用和覆盖所有写入者的共享根串行规则继续有效。未完成描述使失败安装不能被普通消费误用，但不能识别用户删除描述后重新声明为可信历史安装，或所有手工载荷修改。

可直接导入不等于任意模块都有 adapter，也不等于所有自定义编译选项均兼容现有链接配置。系统运行库、Windows DLL 查找、CRT 和 Linux ABI 仍由实际消费环境满足。平台元数据不是完整性校验或来源认证，本设计不扩大这些保证。
