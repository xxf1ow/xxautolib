# Agent Note: importer 压缩分发与功能分支手动发布

Status: proposed

## 问题

宿主 importer 是下游首次消费二进制包时需要取得并执行的工具。直接发布包含符号和调试信息的裸程序会增加下载体积；引导入口若依赖系统解压工具，又会增加消费者的环境要求。工具供给与引导必须使用一致的资产格式，并在损坏或校验失败时阻止执行。

CI 仅允许默认分支发布，功能分支无法在集成前通过同一条真实供给与消费链路验收。允许手动选择功能分支需要保留提交身份、发布权限和固定 Release 的并发保护，不能等同于开放任意引用或自动发布。

## 方案

正式 importer 去除符号和调试信息，Release 使用单程序 tar.xz 归档；CMake 原生完成工具引导。功能分支可在同仓库手动触发既有发布流程。工具压缩生产与消费成套交付，这些能力不依赖 Gitee 镜像流程。

### importer 瘦身与生产

正式宿主 importer 构建使用 `-ldflags="-s -w"`。固定 Go SDK、禁用 cgo、只读模块、路径裁剪和 Go 默认优化保持不变，不改变 builder 或 autolib-ci 的编译参数，不引入 UPX 或其他压缩运行壳。本地安装及 builder 打包附带的 importer 仍是裸程序。

CI 先执行宿主 importer 验证，再用 CMake 将该程序压缩一次，归档内只包含顶层同名程序。GitHub Release 资产分别为 `autolib-importer-windows-x86_64.exe.tar.xz`、`autolib-importer-linux-x86_64.tar.xz`、`autolib-importer-linux-aarch64.tar.xz`。库包仍使用既有 tar.zst，不改包布局或消费协议。

裸程序名与归档资产名分别表达本地执行和远端发布身份。发布校验、上传输入、运行结果与 finalize 的 importer 身份和 SHA256 均指向实际归档字节。归档生成失败属于必需生产失败，禁止上传；不增加新的 job、重打包阶段或发行清单，不删除远端旧裸工具资产。

### CMake 引导

查找顺序为本地已解压程序、本地同平台 `.tar.xz`、配置的远端同名 `.tar.xz`。只有候选不存在才继续；已有程序损坏、归档读取或解压失败、缺少预期程序均直接失败，不回退远端裸资产或其他来源。

解包在现有 `_autolib_bootstrap_importer` 中使用 CMake 自带能力，不要求系统 tar、xz、Python 或 Go，不提高项目最低 CMake 版本。先解包到工作根的独立目录，检查退出状态、错误输出及预期程序，再设置执行权限并放入既有工具位置；失败不执行或提交半成品，不改写归档输入。截断归档可能返回零退出码但输出错误信息，因此不能只凭退出码判定成功。

有本地根时后续 configure 复用解压后的程序；工具或本地归档齐全时不查询远端，远端显式为空时仍可使用本地归档。GitHub 引导要求唯一、uploaded 状态及有效 API SHA256，校验针对归档下载字节；分页及同次 configure 的响应共享保持不变。

不增加裸资产兼容回退、工具自动升级、下载重试、通用解包框架或其他解压格式。默认远端值及尚未接通的 Gitee 消费能力不变，本方案不启用 Gitee 引导。

### 功能分支手动发布

同仓库非空 `refs/heads/` 引用允许手动发布，tag 和 PR ref 拒绝。workflow 检出事件提交，autolib-ci 核对固定目标仓库、事件 SHA、运行记录 checkout SHA、实际 HEAD 及令牌。workflow 和程序采用一致的分支规则，提交身份检查在远端写入前完成。

沿用现有固定 GitHub Release、最小 job 权限、按仓库与 Release 串行和不取消进行中发布的规则。不同分支仍写入相同正式 Release，不是沙箱。不新增 push、PR、定时或自动触发，不把本机令牌作为 job 发布凭据。

### 职责与设计归属

[CI 系统设计](../../implemented/architecture/2026-10-20-ci-system.md)拥有生产编排、环境、并发、发布与验证规则；本提案仅替代其中的默认分支发布限制，并将 importer 发布资产改为压缩归档。[按目标导入与 Release 消费设计](2026-10-25-target-import-and-release-consumption.md)拥有公共接口、来源默认值与后续消费阶段；本提案补充工具压缩分发，不改变库包消费协议或启用 Gitee 消费。

Gitee 初始化、逐资产同步、镜像结果汇总及凭据注入不属于这些能力，构建与 GitHub 发布不因本方案引入 Gitee 运行依赖。Gitee 同步 workflow 的设计和验收独立，不为其预留调用接口。

本提案尚未交付，不将上述行为提前记为当前实现。交付时同步更新现有设计中受影响的约定和交叉引用；当前职责、使用限制及测试入口分别由 `docs/architecture.md`、`docs/development.md`、`docs/testing.md` 拥有，不在此复制操作指南。

## 备选方案

**只去符号，继续发布裸程序。** 能减少体积，但没有利用传输压缩；选择保留本地裸程序，以单程序归档降低发行下载体积。

**使用压缩运行壳或依赖系统解压程序。** 会增加可执行文件处理或消费者环境要求；选择 Go 链接去符号和 CMake 原生 tar.xz 解包，不增加运行时依赖。

**只允许默认分支发布。** 降低功能分支覆盖正式资产的风险，但无法在集成前直接验收同一条发布链路；选择显式手动入口，保留仓库、引用、提交身份、权限及并发检查。

**将工具分发与 Gitee 同步一起交付。** 两者没有必需的运行依赖，共同验收会让工具分发依赖网络镜像结果；供给与引导成套交付，镜像机制独立验收。

## 验收标准

- 正式 importer 实际去除符号及调试信息，原安装位置和裸程序名不变，构建及启动验证通过；记录实际字节数，不承诺各平台固定体积或压缩比例。
- CI 在宿主验证后只生成一次单程序 tar.xz。实际 GitHub 上传正文、归档输入及结果 SHA256 一致，finalize 使用归档身份；归档失败不上传，原有库包生产和失败语义不变。
- CMake 验证本地程序优先、本地归档离线引导、远端归档下载及摘要校验、解压字节一致、后续复用、含空格路径和无需外部解压程序。坏或截断归档、缺预期程序及错误远端资产不得执行半成品或回退其他来源。
- 分支手动发布验证任务分支获准、tag/PR/空分支拒绝、错误仓库、缺令牌及提交身份不符时拒绝；固定发布并发规则保留，不增加自动触发。
- 本地在隔离目录及受控远端执行针对性回归和三个 Go 工具的项目全量测试与 vet，不覆盖已有安装、发行包或工具缓存，不为本方案反复重建真实第三方库。文档及 Agent Note 校验通过，当前文档与实际交付范围一致。
- Windows、Linux x86_64、Linux aarch64 和最低 CMake 版本分别记录验证结果及缺口。本地 fixture、其他代码版本的真实运行均不能替代本方案的跨平台或远端验收；真实远端运行及写入须另获授权。

## 风险

发布端和消费端的资产名、摘要及解包约定不一致会导致首次引导失败，必须成套验证实际归档字节和发布身份。

远端入口只选择压缩工具资产，只有裸工具的远端供给不满足该入口；不增加旧格式兼容或清理远端资产。已有本地程序继续优先，刷新由用户显式处理。

去符号会降低源码级调试便利性，压缩增加首次解包成本；不通过删除 HTTPS 或包准备能力继续压缩体积。不同分支手动发布会替换同一正式 Release 的固定名资产，调用者必须信任所选分支并单独授权真实远端运行。
