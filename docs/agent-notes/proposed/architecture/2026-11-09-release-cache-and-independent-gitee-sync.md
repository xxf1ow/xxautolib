# Agent Note: Release 成品缓存与独立 Gitee 精确同步

Status: proposed

## 问题

用户需要将多次原生构建得到的合格成品累积保存，再以独立流程低成本同步到 Gitee。一次运行中某个库、某个平台或整个运行失败，不能丢弃其他已经验证并打包成功的成品，也不能阻止无依赖关系的库继续构建。

现有发布流程要求来源 run/attempt 整体成功及原计划平台齐全，CI 又在整个平台消费验证通过后统一打包。这使失败运行中的成功结果难以复用。Gitee 发布还逐附件下载远端归档重新计算摘要，等待全部上传结束后才集中登记元数据，普通开始、完成和跳过缺少实时日志。慢请求或作业超时可能使已经替换的附件仍对应旧摘要。

长期成品集合也需要随源码配方变化：删除版本或取消平台支持后，缓存和 Gitee 的对应产物及摘要都应清理；同版本配方及其依赖变化后，旧缓存应自动失效，由后续构建更新。Release 是成品缓存，不能代替源码决定哪些包应该存在。

## 方案

源码配方确定有效版本、平台、精确依赖和包级 latest。GitHub Release 是唯一跨 run 的成品缓存；Actions Artifacts 只保留诊断材料。原生 CI 逐项构建、验证、打包及入库，独立 Gitee workflow 根据触发分支的最新源码快照清理两端，并只用 Gitee Git 摘要索引决定库和 importer 是否需要上传。

无依赖关系的同步项保持并发；需要更新的依赖者先等待其精确依赖的当前成品摘要在 Gitee 确认。每项先更新附件，成功后立即在共用 Git 锁内写入摘要、commit 和 push，确认后才报告该项完成；importer 还须先等关联入口上传成功。相同摘要直接跳过；摘要缺失或不同，以及失败后的重试，都按上次上传未成功处理，删除已有同名附件后重新上传，不回读 Gitee 归档验证内容。入口不登记摘要，只随实际更新的 importer 交付。

### 事实来源与职责

缓存失效和发布进展都从已有事实重新判断，不增加持久化完成清单、失效队列、恢复服务或发布数据库。下游继续只使用 Gitee 的 Git 元数据和归档，不认识 GitHub 缓存的交付信息。

### 源码快照与清理集合

构建固定自身实际检出的源码提交，成品保留该原始生产身份。独立同步开始执行时，解析触发分支的最新提交并固定为本轮源码快照；自动触发取原构建的普通分支，手动触发取用户选择的普通分支。运行中不追赶后续提交，不用构建记录的旧提交代替清理快照。

源码仓库来自可信 GitHub 运行上下文，不能由成品记录自报。构建来源提交和本轮清理提交可以不同；缓存是否适用由输入指纹判断，不要求所有成品同属一个 run、attempt 或源码 SHA。普通分支及 fork 继续适用；tag、PR ref、跨仓库伪造来源仍拒绝。

本轮清理集合来自完整源码快照中的包、精确版本和有效平台身份，包含 any-any 的唯一通用身份。它不受本次构建的模块子集、过滤后平台子集或缓存命中数量限制。删掉版本、整个包或平台资格，以及从机器码槽改为 any-any 等身份变化，按不再存在的精确身份清理旧归档及摘要，不保留自动兼容槽。

源码快照无法取得或完整枚举时，不执行删除。某个配方声明、latest 或依赖错误按该配方记录，不把无法解析解释为该配方被删除，不由此清空其尚无法确定的身份；其他可确定配方继续处理。认证、目标仓库身份、目录边界和共享输入损坏等无法限定到单个配方的错误，仍使整个操作失败。

### Release 成品缓存

缓存使用当前可信源码仓库的固定可修改 Release，tag 为 `autolib-cache`。该 tag 是成品集合入口，不代表全部成品来自其指向的提交；既有 tag 不自动移动。构建 workflow 的共享准备步骤负责查询及必要初始化，完成后才启动各平台写入；不存在时只由该步骤创建，普通查询失败不作为缺失。专用缓存中，源码明确对应的精确归档名及同名加 `.publication.json` 的名称属于受管缓存；手工放入这些名称的文件也会被替换，其他未知名称保留。初始化与实际写入按远端授权执行。

库与 importer 保留当前完整归档名，直接保存最终 `.tar.zst` 和 `.tar.xz` 字节，不把全部库包进一个跨运行大归档，也不把生产身份塞进消费者包格式或 asset label。每个归档旁保存同名加 `.publication.json` 的交付记录。记录至少包含明确类型和精确身份、最终文件名、归档 asset ID、大小及 SHA256、原 run/attempt/分支/源码提交、该项验证归属、输入指纹及精确依赖指纹。库保留原构建的包级 latest 候选；importer 额外携带与原构建源码逐字节一致的原始入口内容及其摘要。

交付记录不包含 Gitee 上传完成标记、同步时间或待重试步骤。缓存项只有在归档和对应记录齐全、身份唯一、来源合法且字节信息一致时才可用；只有库文件名或只有记录不算就绪。先完成验证与打包、上传归档，再保存与该归档绑定的记录，才报告入库成功。中断产生的缺项或不匹配项不可用于同步，后续构建重新准备该项；其他完整项不受影响。

需要替换或修复缓存项时，先完成本地验证与打包，再使旧交付记录失效并删除，删除该精确身份的旧归档及上述受管名称的同名残留，然后上传新归档，最后上传绑定新 asset ID、大小和摘要的记录。删除失败时停止该项，不直接上传同名文件；未落入上述精确受管名称的内容不自动删除，歧义同名项报告错误，不扩大删除范围。当前有效完整项直接复用，不执行该替换链。

GitHub 上传接口不覆盖同名附件，同名上传返回 422；502 可能留下 `starter` 状态的空附件。后续尝试重新枚举该身份，确认归档与记录是否完整有效；若仍需重建，按上述顺序删除已确认的残留后重传，不反复向同名附件执行盲上传。[Release 附件上传规则](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset)是该处理的接口依据。临时网络错误、429 和 5xx 采用有界退避，首次尝试外最多重试十次，沿用本提案的退避序列；认证、权限及不能明确归因于同名残留的 422 直接报告失败，不无限重试。

平台 runner 可以并发写入各自不同完整文件名的归档和记录。共享准备步骤固定本轮各平台的精确写入身份，校验每个身份只有一个写者；`any-any` 仍只分配一个 publisher。各项独立记录，不在多个 runner 间读改写同一个缓存总清单。Release 初始化、跨 run 替换及同步清理由共享准备和运行级互斥保护，不为不同身份上传新增分布式锁。

同步可以先读取小型记录及 Release 附件元数据，取得库和 importer 的预期摘要，再比较 Gitee Git 索引；摘要相同的归档不下载。只有需要 Gitee 上传或本轮构建使用的成品才下载，并重算实际归档大小和 SHA256。GitHub API 提供的 asset ID、状态及 digest 用于绑定缓存文件，不代替配方身份和验证归属。读取列表须完整分页，不能把分页失败或半成品过滤后的集合当作删除依据。

Actions Artifacts 仅保存计划、逐项结果、日志和测试报告，不再保存供同步下载的第二套成品。发布不依赖这些诊断材料仍未过期，也不依赖来源运行整体成功。历史 artifacts 及旧 Release 不批量迁移；缺少新交付信息的历史输入不自动视为新缓存。

GitHub 官方将 Artifacts 定义为有保留期限的运行产物，公开仓库可配置期限上限为 90 天，不适合作为本任务长期完整成品集合的唯一存储。[Artifacts 保留规则](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)与[Release 附件接口](https://docs.github.com/en/rest/releases/assets)提供两种存储的依据。Release 和 Artifacts 的读写均通过网络；本方案取消本机中转及额外存储服务，不承诺跨 runner 零网络。

### 输入指纹与链式失效

每个精确版本及产物平台计算确定的输入指纹。指纹覆盖该项配方、补丁、步骤声明的本地输入、adapter，以及实际影响生产的 builder 输入、固定工具配置和目标构建上下文；直接依赖按精确身份及其输入指纹纳入。使用现有 builder 输入描述作为基础，补齐真实生产所需输入，不以整仓库源码 SHA、文档或日志变化替代相关输入。

文件集合和依赖集合按稳定顺序计算，路径采用仓库相对路径并同时纳入文件内容；新增、删除或修改相关文件都改变指纹。公共生产输入改变可以使全部受影响项失效。工具指纹覆盖 importer 生产输入及原始入口，不能误用库包指纹。any-any 使用通用产物身份，保留唯一 publisher，不因读取缓存的宿主平台不同生成四份通用缓存。

包级 latest 是独立版本选择，单独校验和维护。仅修改 latest 指针不使所有版本归档失效；选择解析后发生的精确依赖变化仍进入相关项指纹。实际版本声明、构建或消费内容变化不能因版本字符串未变而忽略。

当前指纹与交付记录不一致即缓存失效。因为依赖指纹进入依赖者指纹，失效沿反向依赖传播：B 变化时，B 和直接或间接依赖 B 的 A、C 失效，无关 D 不失效。无须逐条保存另一份失效状态。旧缓存字节可以保留到替换完成，但不再当作当前可用成品；下一次选择到该项的构建自动重建，不要求人工删除或替换。

缓存失效、缺失和源码身份删除分别处理。尚有配方的失效项不因此删除 Gitee 上最后确认的归档或摘要；同步报告该项待构建，不能上传已失效的旧缓存。只有源码已删除的身份进入两端删除集合。有效缓存可跨 run 复用，原成品来源保持不变，不重新打包或改写成品生产身份。

### 逐项执行与失败隔离

规划保留平台、精确版本、直接依赖及通用包 publisher。配方解析和 latest 校验须能产生逐包错误，不能因一个包的坏声明、悬空 latest 或缺失依赖而丢弃所有无关包的计划。请求格式、目标平台和共享工具准备等全局错误仍明确失败，不伪造成单包成功。

同一运行中，精确依赖先于依赖者准备；同一精确依赖只处理一次。有效缓存可直接用于交付，需要参与本轮生产时经现有身份检查和安全解包进入该 run 的隔离安装根，不复用其他运行的裸安装树或 sentinel。缓存不能绕过目标 ABI、有效精确闭包及本平台必要消费检查。

未命中项由同提交 builder 完成安装，沿用既有独立根消费、平台来源及打包验证。共享闭包可复用已取得的有效检查，不新增每库专用测试工程，不撤销 Taskflow 和 ONNX Runtime 等已确认的 API 验收例外。验证通过后立即打包并入库，不等待平台中的其他库或其他平台全部结束；工具和入口也有独立验证结果，零库仍可交付工具。

构建、验证、打包或入库失败使该项失败；依赖它的项记录具名依赖链并连锁失败，不继续执行依赖者，不取消其他无关项或平台。一个共享依赖失败只造成其依赖闭包失败，不能扩大为整层或整个平台的提前退出。单个配方所需系统依赖准备失败也按该项及其依赖者处理；公共工具或平台环境无法准备时，依赖该环境的该平台项失败，其他可执行平台继续。

单项结果至少区分成功入库、有效缓存复用、失败、依赖失败和资格过滤；不能用空结果代表完成。平台及运行最终汇总请求、有效、成功、失败和阻断项，只要存在本应执行的失败项就返回失败。成功项及其原始证据留在 Release，不因汇总失败删除，不把累计多次证据重标成一次全量成功。

### latest 校验与删除修复

源码包级 `package.toml` 必须具有合法非空 latest，且指向实际存在、包含合法 `module.toml` 的版本。测试应验证删除被选版本后的悬空指针能够被发现。实际运行遇到无效 latest，报告该包错误，并阻断受影响的依赖项；其他无关包继续编译、验证及入库，不以自动选择其他版本掩盖错误。

普通同步保留已有仍合法的 Gitee latest；缺失项沿用原构建携带的候选初始化，候选必须仍是本轮源码中的有效版本。若原候选版本已经从源码删除，改用本轮源码快照中合法的包级 latest；源码 latest 无效则报告该包错误，不写猜测值。显式 latest 映射保留独立入口和优先级，也必须指向本轮源码存在的合法版本。补旧版本、补平台和无变化重跑不自动推进已有合法指针。

清理删除了既有 Gitee latest 指向的版本时，使用本轮源码快照中合法的包级 latest 修复指针。源码 latest 无效则报告该包错误，不写猜测值；若旧指针指向已明确删除的版本，删除该悬空指针。整个包已删除则清理其版本摘要和包级 `package.toml`。删除摘要和相应指针修复应在同一次该包 Git 提交内完成，不能报告清理成功却留下指向已删除版本的指针。

这里的空版本指源码不存在对应合法版本，不新增全部平台成品齐备才允许维护 latest 的门槛；成品尚未生成必须在交付覆盖报告中显式体现，不能宣称裸名消费已通过。latest-only 不构建、不打包、不要求 importer 实际更新，也不触发入口上传。

这一规则允许首次初始化、显式切换或删除修复后的 latest 指向源码合法、但某些支持平台成品尚未发布的版本；该平台的裸名消费者可能下载失败。已有合法 latest 仍按前述规则保留，不因另一个平台先发布新版本自动推进。交付覆盖报告只说明缺口，不构成消费可用性保护；本方案不增加单包全平台齐备门槛，也不把源码指针合法等同于所有平台已可消费。

### 运行互斥与自动入口

不支持多个 run 同时编译、替换同一个目标集合中的同一包。构建入库及独立同步在 workflow 层使用覆盖同一缓存和 Gitee 目标的 GitHub 原生 concurrency 互斥，明确设置 `cancel-in-progress: false` 和 `queue: max`，保持正在执行的运行，并保留平台队列容量内的等待项，不采用会被后续请求替换的默认单等待项模式。互斥不按触发分支或 workflow 名拆开，不在同一 workflow 的子 Job 中重复申请同一互斥组；同一运行内部的平台及不同同步项继续并发。

原生队列最多容纳 100 个等待项，超限的新请求仍可能被平台取消；不承诺无限排队或按触发时间严格排序，不新增持久队列、跨运行冲突合并、分布式锁或自动选胜者机制。超限及取消必须保留真实运行状态，不能记为同步成功；后续成功构建触发的同步或手动同步仍处理全部有效缓存，不依赖被取消请求携带的成品。[GitHub concurrency 规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)是配置与容量限制的依据。

构建入库和同步、清理不能作为相互独立的写者同时修改共用 Release。两种 workflow 的互斥接线和自动触发须在真实调度验证中核对，不能只凭单次同步的线程锁声称跨 run 已互斥。人工直接修改缓存或 Gitee 附件不与自动运行并发执行。

独立同步保留手动入口，不需要 source run/attempt 参数、构建结果 artifacts、原计划平台齐全或某次运行成功。构建整体成功、成品入库完成后自动触发同步；自动触发只提供可信仓库和分支上下文，不把同步范围限制为触发它的构建集合。失败运行的合格缓存可由后续成功构建触发的同步或手动同步发布，不默认增加失败运行自动触发。

同步不编译库、builder 或 importer，不重新生成归档。它可以在没有新构建的情况下完成配方删除清理、已有成品同步或 latest-only 操作。成功同步当前有效缓存不等于源码所需成品已经全部生成；缺失、失效和仍失败项单独报告，整体交付按累计覆盖验收。

### Gitee 摘要比较与逐项登记

同步固定实际 `GITEE_REPOSITORY`、`GITEE_RELEASE_TAG` 和 `GITEE_TOKEN`，沿用已有仓库身份、初始化、普通请求及参考 multipart 实现。同步在一个 Job 的单个进程内执行，线程池并发上传；每轮只取得一份 Gitee Git 工作副本，由该进程内的同一把 Git 锁保护，不拆成多个 Job 或 runner 分别 push。库摘要继续位于 `<name>/<version>/<完整归档名>.sha256`，工具摘要继续位于 `autolib-importer/<完整工具归档名>.sha256`，格式仍为 64 位小写 SHA256 加 LF；不改变消费者的 ASCII 空白处理。

工作副本中的合法摘要与本次有效缓存归档摘要相同，就直接跳过该项，不查附件内容、不下载 Gitee 归档、不为了证明附件仍存在而改变跳过判定。不同或不存在才准备上传；本地实际文件仍须与记录一致。正常路径完整读取一次 Gitee 附件列表，为替换和删除定位同名附件及 ID，不按每个库重复枚举。

每个同步项执行“固定待上传字节 → 删除已有同名附件 → 上传 → 加 Git 锁 → 更新该项摘要和必要 latest → commit/push → 确认完成”；importer 在上传与加 Git 锁之间，按下节规则等待本轮入口上传成功。无同名附件直接上传；存在歧义或无法确认列表、删除结果时失败，不猜测或盲目覆盖。上传期间不持有 Git 锁；Git 工作树修改、add、commit、push 及已确认 HEAD 更新均在同一把锁内，不引入独立末尾协调提交。

正常失败重试不回读远端内容。只要 Gitee Git 摘要未确认更新，就默认上次上传失败，刷新附件信息，删除当时存在的同名附件后重新上传相同本地快照；上次上传成功但响应丢失也按此执行。保留既有有界附件重试和脱敏诊断，首次尝试外最多重试十次，退避仍为 `2、4、8、16、32、32、32、32、32、32` 秒。认证、权限、非法输入及响应结构错误不改为无限重试。重试会产生额外列表请求，不能宣称所有运行固定只查询一次。

不预设 Gitee 删除具有某种未验证的异步延迟。明确识别为临时故障的同名冲突可以在上述次数和退避内重新枚举、删除重传；未分类的 409/422 仍报告该项失败，不将全部校验错误改成可重试，也不新增无限轮询。平台响应分类须有可核对的接口依据或实际脱敏响应证据，不以其他服务的行为代替。

每项 push 成功才更新已确认元数据 HEAD 并报告该项成功。Git 提交或 push 未确认使本轮元数据写入失败，不继续复用未确认的工作副本提交其他项；已经在途的上传可能完成，不能声称已经回滚。下一轮重新取得 Git 索引后决定跳过或删除重传，不建立单独恢复数据库。部分成功项不因其他项失败回滚；全部相同且 latest、清理均无变化时，不产生新提交或无意义 push。

Git 锁持有到 push 确认或失败，后续项不能在前一次 push 尚未确认时提交。单次 push 变慢只延长等待；外部写入引发的非快进拒绝或无法确认的远端结果按上述失败语义退出，不自动 rebase、强推或批量补写未确认项。逐项 push 的请求成本是即时登记的取舍，不以未经验证的限流猜测改成末尾集中提交。

### 精确依赖的发布顺序

同步主进程按本轮源码中的精确版本及产物平台建立依赖图，先比较有效缓存记录与 Git 索引，确定需要更新的项。实际更新依赖者 A 前，必须确认其所有直接依赖及递归闭包的当前有效成品：每项都有适用缓存提供预期摘要，且 Gitee Git 摘要已经相同，或该项已完成上传及摘要 push。依赖附件只上传成功但尚未确认摘要，不算就绪；不得只因源码版本号相同就沿用其旧摘要作为当前依赖已发布的证据。

依赖缓存缺失、失效或同步失败时，依赖它的待更新项记录具名阻断链，不开始下载及替换这些依赖者；无关库和平台继续并发。相同摘要的项仍可直接跳过，不为补充依赖检查重新上传或回读 Gitee 归档；其依赖存在交付缺口时，汇总仍须单独呈现，不能把摘要跳过报告成整组依赖消费已验证。只要存在实际同步失败或由失败产生的阻断，运行就报告失败；尚待构建的覆盖缺口沿用独立报告，不伪造成上传成功。

该顺序防止依赖 B 更新失败后仍把依赖新 B 的 A 作为新成品发布，但不提供整张依赖图的原子切换。同版本原地替换 B 后、A 替换完成前，远端可能同时保留新 B 与旧 A；若 A 后续失败或运行中断，这种状态可能延续到后续同步成功修复。保留仍有配方的旧产物、链式缓存失效及逐项即时登记都不能消除这个窗口。本方案接受这一边界，不新增消费者快照、代际归档或整组事务，不承诺替换期间及中断后所有依赖组合始终 ABI 一致。

### importer 与入口关联交付

`autolib.cmake` 是特殊附件，不登记 Git 摘要。只有本轮至少一个 importer 因 Git 摘要缺失或不同而实际上传成功，才更新一次入口；所有 importer 均跳过或只更新库时，不上传入口。

入口取自有效 importer 交付记录保存的原始源码字节，核对记录摘要及来源后，仅在上传副本中按既有规则注入实际 Gitee 目标和编码 tag。原始源码、缓存及本地安装入口不回写。同步主进程在调度前以本轮固定源码快照确定唯一原始入口及摘要，核对参与工具记录中的入口与其一致；不一致的记录不能参与交付，不由 worker 完成先后选择入口。

唯一入口上传任务由同步主进程拥有，在至少一个 importer 归档实际上传成功后启动一次，使用与附件相同的有界重试。该任务由主进程调度执行，不排入可能已被等待入口的 importer 项占满的上传线程池。各实际上传的 importer 共享其结果；入口任务正常失败或抛出异常时必须使所有等待项收到失败结果，不能留下永久等待。整个同步进程退出后不选举接管者，下一次运行依靠未更新的 importer Git 摘要重新交付。

实际上传的 importer 项先完成工具归档上传，再等待本轮唯一入口上传成功，最后各自立即在 Git 锁内登记工具摘要。入口失败时，这些工具项不登记新摘要，本轮报告失败；下次运行仍看到旧摘要，按删除重传规则再次更新 importer 和入口。无需入口摘要、入口完成标记或每次包含 importer 就强制上传入口的例外。库项不用等待入口。

入口单独变化会使工具缓存指纹失效；后续构建重新准备有效记录，但若 importer 最终归档字节未变，Gitee 摘要仍相同，入口也继续跳过，直到下一次 importer 实际更新。缓存失效不等于触发 Gitee 上传，不通过伪造工具归档差异触发入口上传。工具源码与入口协议改变时须保持配套，不能把入口单独修改描述成会自动发布。

### 两端精确清理

两端分别对照同一源码快照，删除已明确不存在的精确库产物身份。Release 删除对应归档及交付记录；Gitee 删除对应附件、SHA256 文件，并按上述 latest 规则修复或删除指针。一个端清理失败不使另一个端已经成功的删除回滚；下次仍按源码快照重新判断并补齐。

Gitee 清理不能只遍历现有 Git 摘要，还须检查附件列表中符合项目库产物身份、但没有摘要的残留项；同样不能只删摘要而遗漏附件。对仍有配方的缺失或失效缓存，不执行远端删除。工具及无摘要入口不冒充普通库配方，不因 `src/dependencies` 中没有同名目录而删除；保留四个宿主工具和入口的专用身份规则。

清理只管理所配置 Release 中可确认为本项目产物的附件及专用元数据路径，不删除整个仓库、其他 tag、README、LICENSE 或身份文件；除专用 `autolib-cache` 中源码明确对应的精确归档及记录名外，未知内容不按文件名猜测归属。完整列表、明确目标和可判定的源码身份先于删除。不存在明确源码删除证据时，即使缓存为空，也不能把 Gitee 全部清空。

### 权限、初始化与退役

构建入库需要当前源码仓库的 Release 写权限，独立同步清理 GitHub 缓存时也需要相应权限；只读计划、测试和诊断不因此获取 Gitee 凭据。GitHub 凭据用于 GitHub 侧，`GITEE_TOKEN` 只注入独立 Gitee 写入步骤，不进入第三方编译、依赖安装、缓存或日志。checkout 继续不持久保存凭据，输入不拼接成 shell 源码。

缓存 Release 采用允许更新和删除附件的配置；若启用 immutable release 则明确失败，不尝试绕过保护。[GitHub 不可变 Release 规则](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)说明其附件限制。单文件必须小于 2 GiB，单 Release 最多 1000 个附件，归档与交付记录都计入数量。[Release 容量规则](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)是当前限制的核对来源。

每轮构建在平台并发写入前，由共享准备步骤完整读取现存附件，固定本轮计划可能新增的完整文件名集合，按“现存全部附件数加本轮净新增数”预检容量。未知附件、残留及记录均计数；不能把尚未完成的源码删除清理算成已释放空间。超限时在任何缓存替换前明确报出当前数量、预计新增量和上限，停止本轮缓存写入准备，不等上传过程中才发现容量不足。每个成品最终大小在删除旧缓存前检查；超过单文件限制只失败该项及其依赖者。

同一身份原位替换，不按 run 保留无限历史副本；源码已经删除的身份按清理规则释放空间。容量不足不驱逐源码仍需要的有效成品，不自动删除未知内容或改用其他存储。当前设计采用单 Release 的明确容量边界；确有超过上限的源码集合时再确认分片方案，不预建分片、轮转或额外云服务。

首次空缓存只表示成品尚未入库，不代表源码配方全部被删除，也不触发 Gitee 全量清空。已有 Gitee 附件与源码快照核对后，相同摘要可以直接跳过，不安排逐包远端回读、历史数据迁移或批量重传。已有不一致项只在有效缓存可用且摘要不同或缺失时按删除重传处理；本方案接受 Git 索引记录的信任前提。

最终退役指定成功 run/attempt、下载 `ci-package-*` 成品 artifacts 和整平台全成功门槛的旧发布路径，不保留第二套生产发布入口或旧运输格式兜底。旧 artifacts 按原保留策略存在，用户安装及消费缓存不受本任务清理影响。常规架构、开发、测试文档和 Action 接口说明随相应阶段实现更新；原始上游 README 和 multipart 参考本体保持原有维护规则。

### 阶段交接

整体设计分为两个可独立验收阶段，共用本记录和普通任务分支；只为即将执行的阶段编写实施计划。

| 阶段 | 交付内容 | 独立验收结果 |
| --- | --- | --- |
| 第一阶段：构建与 Release 缓存 | 逐配方规划和 latest 错误隔离、依赖调度、持续执行、输入及依赖指纹、逐项验证打包和入库、跨 run 成品复用、仅诊断使用 Artifacts | 构建故障不阻止无关项；成功成品独立保留；第二次运行复用有效成品，只重建失效闭包，原运行身份保持真实 |
| 第二阶段：独立 Gitee 同步 | 从 Release 读取有效成品、按源码清理两端、Git 摘要比较、依赖顺序及无关项并发、Git 锁和逐项即时登记、importer/入口关联交付、独立手动及成功构建自动触发 | 无变化零产物传输与新提交；变化项即时可见；依赖失败阻断新依赖者；失败后删除重传；配方删除清理对应归档和摘要，latest 不指向源码已删除版本 |

第一阶段不执行 Gitee 发布或删除，暂不让新的缓存构建触发旧的 run 绑定发布路径。第二阶段接通新的独立自动入口，不同时维护两套自动供给。阶段实现和审查完成后先取得用户验收，再检查后续设计假设；有实质变化只修订受影响部分，确认后进入下一阶段计划。

本文是待实现设计，不把已有三平台或四平台验收、受控测试和旧发布成功当作新流程已通过。书面设计确认后，在当前工作目录创建普通任务分支，按 pre-commit-checks 将初始设计作为该分支首提交，再使用 writing-plans 生成第一阶段计划供审核并选择执行方式；不创建 worktree。

书面设计确认涵盖本任务范围内的初始设计及后续本地提交。push、远端合并、真实 CI 触发、GitHub Release 初始化或写入、Gitee 发布及两端实际删除，仍须取得对象和阶段明确的远端授权；本提案不恢复已取消的 Actions，也不代替真实故障注入和数据清理的授权。

## 备选方案

**继续按成功 run/attempt 整批发布。** 可以复用现有输入检查，却无法取得失败运行中的合格成品，也仍依赖某次运行覆盖全部计划平台。逐次选择几个成功批次不能替代逐库失败隔离与成品缓存，不能满足本任务。

**将 Actions Artifacts 作为唯一跨 run 成品库。** 可以保留来源运行和成品，但保留期限及运行删除会使成品消失；若把消失直接映射为 Gitee 删除，会混淆配方删除与缓存过期。采用 Release 保存成品，Artifacts 只保留诊断，避免维护两套供同步使用的成品。

**在本机、额外服务器或固定自托管 runner 保存共享目录。** 可以获得持久磁盘，但当前托管 runner 仍需要网络传输，还增加机器和存储维护，不满足用户选择的 GitHub 侧存储范围。GitHub 内建缓存同样经网络且会淘汰，不作为完整成品库。

**保留远端归档回读及整批末尾提交。** 回读可检测人工改写的附件，末尾单次 push 数量较少，但增加 Gitee 传输成本并扩大附件与摘要不一致的等待窗口。本任务明确改为信任 Git 摘要、逐项登记，代价是不再例行验证远端真实字节。

**只失效修改的单个缓存，或要求人工替换。** 会留下仍引用旧依赖的下游成品，且需要人工追踪反向依赖。采用递归依赖指纹自动失效，下次构建更新受影响闭包，无关成品继续复用。

**以单包全平台齐备作为 latest 更新条件。** 可以避免指针指向尚缺平台成品的版本，但改变现有 latest 初始化、显式映射及删除修复规则。本方案保持源码合法性及原选择规则，接受并明确报告平台交付缺口，不新增齐备门槛。

**整组依赖通过消费者快照原子切换。** 可以进一步约束同版本更新时的新旧组合，但需要改变消费者识别或归档寻址协议。当前范围采用依赖先确认、再更新依赖者的调度，保留逐项即时提交与普通归档名；不以顺序调度宣称获得整组原子性。

## 验收标准

### 第一阶段

1. 在现有依赖及生产接口下验证 B 被 A、C 依赖、D 独立的代表图：B 失败使 A、C 连锁失败，D 继续成功；A 自身失败不阻止 C、D；已验证打包的成品在运行最终失败后仍独立入库，结果不误报全量成功。
2. 至少两个不同 run/attempt 的合格成品可以累积复用，不要求整体成功、同源码 SHA 或原计划所有平台都有成品；来源、版本、平台、大小和 SHA256 错误以及半成品不能作为有效缓存。
3. 第二轮有效缓存归档字节不变，不重新编译或打包；所需依赖通过受控安装准备供真实消费者使用。修改 B 的配方、补丁、adapter 或有效本地输入后，B、A、C 失效而 D 命中；下一轮自动更新受影响项，无需人工替换。只有 latest 改变不重建全部版本归档。
4. 删除源码 latest 指向的版本后，测试明确失败；实际执行报告该包错误，无关包仍完成构建、验证及入库。坏配方和依赖错误不得静默记为过滤或成功。
5. 保持四平台工具、零库输入、精确版本和 any-any 唯一 publisher 规则。跨平台和工具缓存按其真实身份验证，复用既有有效 ABI 与 API 例外，不以受控协议夹具声称原生平台执行通过。
6. 用受控 GitHub 附件接口覆盖同名 422、502 后 `starter` 残留、只有归档或只有记录、归档替换后旧记录残留，以及上传响应丢失。重跑能确认有效完整项或按规定删除残留重传；记录绑定实际新归档，不发布半成品，不删除未知身份内容。
7. 不同平台身份能并发独立入库，初始化只在共享准备执行一次，重复写入身份在平台启动前被拒绝。容量预检计入记录、未知附件、残留和全部计划净新增项；超限在替换前失败，不靠驱逐有效成品通过；单文件超限不先删除旧缓存。

### 第二阶段

1. 手动同步不读取原 run 成功状态、成品 artifacts 或编译工具；一次成功构建仍自动触发一次独立同步，范围是按本轮源码确认的全部有效缓存。失败运行合格项可在后续同步发布。
2. 全部摘要相同时，库、工具和入口均零产物下载及上传，零新元数据提交，Gitee 无归档内容回读。只变化一个库时，仅下载、替换该库并立即确认其摘要，其他库不重传；入口和工具关联规则单独验证。
3. 用受控阻塞证明无依赖项并发上传真实重叠，一个已成功库在另一个慢项结束前已经完成 Git push，且观察到对应摘要；单 Job、单进程内 Git 写入串行，前一次 push 未确认时后续项不能提交，不同项摘要不丢失、不混入错误项，日志逐项及时输出开始、跳过、重试、成功或失败及最终汇总。
4. 注入上传响应丢失、入口失败及 Git push 未确认：下次根据 Git 索引判断；摘要未更新的项刷新附件事实后删除重传，不下载 Gitee 归档；摘要已确认的其他项跳过。入口只在 importer 实际上传时更新一次，入口失败的 importer 不提前登记摘要。
5. 删除版本、整个包和平台身份后，Release 归档与记录、Gitee 对应附件和 SHA256 以及必要包级指针正确清理；没有摘要的受管附件残留也能清理。保留配方但缓存为空、缺失或失效时，不删除 Gitee 对应产物；源码或列表获取失败不能触发全量删除。未知附件、其他 Release、仓库身份及用户消费缓存保持原样。
6. 删除被选版本时 latest 不指向源码已删除版本；已有合法指针不因补旧版本或补平台而推进，显式映射仍具有既定优先级。首次初始化、显式切换和删除修复保持原规则，不等待全部平台成品；缺失平台出现在交付报告中，不把它作为全平台裸名消费通过证据。
7. importer 并发上传时只有一次入口任务，不同完成顺序不改变入口字节。工具全部跳过或上传全部失败时不启动入口；入口任务失败或抛出异常会结束全部等待项，无线程池互锁，库项继续。入口单独变化且 importer 归档摘要相同时，工具缓存按指纹重新准备而 Gitee 仍跳过，不登记入口 Git 摘要或伪造工具差异。
8. 用 B 被 A、C 依赖、D 独立的图验证发布顺序：B 摘要 push 确认前 A、C 不开始替换，D 可以并发完成；B 缓存缺失、失效或上传失败会阻断需更新的 A、C。B 已确认但 A 失败时，不伪报整组一致；后续运行跳过已确认 B 并继续更新 A，不引入整组回滚。
9. 在真实 workflow 调度中验证两个 workflow 共用互斥组、`queue: max` 和 `cancel-in-progress: false`，等待中的同步不会被队列容量内的新构建替换，构建与同步不同时修改缓存；不只检查线程锁或静态 YAML。未分类的 Gitee 409/422 明确失败，不把认证、权限或普通校验错误当成临时同名冲突重试；未知 push 结果终止本轮元数据写入，不自动 rebase 或强推。

### 验证范围与证据

按实际影响验证 builder 描述、CI 规划和执行、缓存读写及同步 Git/API 接口。优先加强现有生产入口和临时 Git 裸库、受控 HTTP 测试；用轻量真实库验证成品恢复、精确闭包消费及归档原样交付，不为本任务重编全部第三方库或新增逐库测试矩阵。

第一阶段结束只运行本阶段增量及受影响接口检查；用户验收后规划第二阶段。全部阶段完成后执行仓库要求的全量检查；输入未变化的有效原生、ABI 和消费证据可复用，不因审查轮次重复测试。实际远端写入、删除和故障注入须按授权范围验证，日志记录实际 run/attempt、生产身份、目标、摘要和已知缺口，不以成功数量或 HTTP 响应代替闭环证据。

文档使用 Agent Note、项目文档链接及预算校验和 `git diff --check`；源码、测试、Action 接口说明及当前架构、开发、测试指南在对应实现阶段保持一致。正式设计自查覆盖条件、例外、职责、阶段边界和未实施状态，实施计划放在忽略的 `.superpowers/`。

## 风险

信任 Gitee Git 摘要意味着合法索引相同时，即使附件被人工删除或改写，本次也会跳过；这是用户明确选择的信任模型，不新增例行回读或后台探测。附件上传与 Git push 仍非原子操作，取消、网络故障或进程退出可造成暂时不一致；未更新的摘要使下一轮删除重传，已确认项保持成功。

latest 合法性以源码版本为准，允许部分平台尚缺成品时初始化或切换，相关平台裸名消费可能失败。依赖发布顺序约束新依赖者的提交资格，同版本普通文件名的替换仍可能留下新依赖与旧依赖者混用，失败后可持续至后续运行修复。这两项是明确保留的交付限制，交付覆盖报告、链式失效和单项成功均不构成全平台可用或整组 ABI 原子一致的保证。

逐项 commit/push 增加变化项的 Git 请求数，换取成功项及时可见；正常无变化不写 Git。变化项仍需从 GitHub 下载并向 Gitee 上传，缓存入库和恢复也经网络，不能把独立同步描述成零网络。入口无摘要且仅随 importer 实际更新，给定规则下的入口单独修改不会立即发布。

指纹只能覆盖显式仓库输入、选定依赖及声明的生产上下文；未固定的外部系统包或上游同名资源变化不属于自动发现任意环境漂移的保证。实际工具环境继续记录，不新增通用环境探测或可复现构建项目。遗漏实际输入会错误复用，指纹覆盖和依赖传播必须由真实相关文件变化及受控消费者验证。

两端清理有实际删除副作用。删除资格以完整源码事实限定，配方错误、缓存失效及网络读取失败均不能扩大为删除证据；实际首次清理须按授权核对目标和范围。源码不同分支指向同一目标时，执行哪条分支就使用其固定最新快照，不承诺合并多分支期望集合，也不支持绕过运行互斥的人工并发写入。

Release 是可修改缓存而非 Git 管理的期望状态；来源和校验信息与归档不匹配的项不得发布。单 Release 容量上限通过预检阻止越界写入，不自动驱逐或分片；原生 concurrency 队列仍有容量上限，不提供无限请求保留。GitHub 存储配置、单文件及附件数量限制需要在真实启用前核对，当前设计没有新流程的真实网络耗时、四平台缓存恢复或远端删除通过证据，也没有 Gitee 删除后同名冲突发生概率的证据。
