# Agent Note: JSON 交付元数据与有序双来源下载

Status: proposed

## 问题

用户需要让已经进入 GitHub Release 缓存的合格成品可被实际消费，既减少 Gitee 同步传输，也避免单个附件超过 Gitee 限额后长时间等待并拖累同步。Windows PCL 归档已有合格缓存，但超过普通 Gitee 项目的单附件限额；相关运行和已接受的阶段边界见[缓存与独立同步验收](../../implemented/architecture/2026-11-09-release-cache-and-independent-gitee-sync.md#windows-真实构建与独立同步验收)。

当前 Git 元数据仅保存 SHA256，CMake 引导和 Go importer 各自拼接单一归档地址，无法表达一个产物可从多个托管平台下载，也无法表达只在 GitHub 保存的大包。消费者对大包沿用固定五分钟总超时，无法区分正常慢速下载和长时间没有数据。

本设计的成功标准是：普通库及 importer 优先从 Gitee 下载，遇来源故障后自动尝试 GitHub；超限包直接使用 GitHub；所有来源必须匹配同一摘要和大小。同步仍只依据 Git 索引判断是否完成，每项确认后立即提交，不回读 Gitee 归档。项目当前没有外部用户，不要求保留旧协议、旧工具或历史元数据兼容。

## 方案

由同步端为每个库归档及 importer 生成独立 JSON，保存完整、有序的下载地址。CMake 和 Go 读取同一格式，负责依次下载、校验及安全提交。GitHub Release 继续作为跨 run 的成品缓存，并提供匿名下载来源；Gitee Git 仓库继续作为唯一交付元数据来源。Go importer 拥有包下载的完整错误分类、取消及传输计时；CMake 只承担简单的工具引导，不复制这套下载器。

### 两种 JSON 的职责

GitHub 缓存中的 `<归档名>.publication.json` 继续描述生产身份、原始来源、输入和依赖指纹、验证证据及绑定的归档字节。它属于 CI，不直接交给消费者，也不写入 Gitee 完成状态。

Gitee Git 中的消费者记录改为 `<归档名>.json`：库位于 `<包名>/<版本>/<归档名>.json`，工具位于 `autolib-importer/<归档名>.json`。包级 `<包名>/package.toml` 仍只保存 latest。独立 `autolib.cmake` 没有交付 JSON，也没有摘要；仍只随本轮实际上传成功的 importer 更新一次。

每份消费者 JSON 只包含以下三个必填字段；字段顺序和排版不参与相等判断，`urls` 的顺序参与。

同步端统一用 UTF-8、按键名排序、两空格缩进并在末尾写一个 LF。消费者按字段语义读取，不要求输入排版相同；已有记录语义相同时不为统一排版创建提交，不引入额外 Canonical JSON 协议。

| 字段 | 约束 |
| --- | --- |
| `sha256` | 恰好 64 位小写十六进制字符串 |
| `size` | 正整数，单位字节；不得为布尔值、字符串或小数，且小于既有 GitHub 缓存单文件上限 |
| `urls` | 非空、有序、无重复的完整 HTTPS 地址数组；每个地址提供同一份归档 |

结构示例中摘要与大小仅用于说明格式：

```json
{
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "size": 1048576,
  "urls": [
    "https://gitee.com/xxf1ow/autolib-release/releases/download/autolib-release/eigen-3.4.0-any-any.tar.zst",
    "https://github.com/xxf1ow/xxautolib/releases/download/autolib-cache/eigen-3.4.0-any-any.tar.zst"
  ]
}
```

归档身份仍由受校验的目录及完整文件名确定，不在 JSON 重复保存包名、版本、平台、附件 ID 或运行号。仓库身份文件 `.autolib-repository.json` 的 `schema` 改为整数 `2`，其余身份规则保留；每份归档记录不再保存独立版本号。新格式不接受 `.sha256` 记录或额外业务字段。

### 地址由生产端确定

同步端从可信运行上下文取得 GitHub 源码仓库，以固定 `autolib-cache` tag 和完整归档名生成 GitHub 下载地址；从已配置的 Gitee 仓库、tag 和归档名生成 Gitee 地址。各路径段只编码一次。JSON 保存公开稳定的 Release 下载地址，不保存 GitHub API 地址、临时签名 CDN 地址、令牌或凭据。

普通项使用 `[Gitee, GitHub]`；超过 Gitee 单附件阈值的项只使用 `[GitHub]`。消费者严格使用记录中的完整地址，不拼接缺失地址、不从文件名猜测来源，也不调用托管平台 API 发现附件。初始地址要求 HTTPS、非空主机且不带用户凭据；非法地址使该记录失败，不能跳过它后使用其他地址掩盖元数据错误。Go 保留现有对重定向的 HTTPS 校验；CMake 引导使用原生下载并开启证书校验。

公开 GitHub 仓库及可匿名下载的缓存 Release 是提供该来源的前置条件。可信 fork 的地址必须取自 fork 自身，不回退固定上游仓库；私有缓存不能通过在元数据写入访问令牌来提供匿名下载。真实匿名可用性由交付验收确认，不能用有令牌的缓存读取成功替代。

### Gitee 大小判断

当前项目按普通仓库配置，固定阈值为 `100000000` 字节。`size <= 100000000` 走普通交付，`size > 100000000` 走仅 GitHub 交付。该字节值是对官方“100M”的保守解释，避免依赖未明确的十进制或二进制换算。阈值在同步端集中定义和输出；不自动识别 GVP、不新增配置矩阵。

大小来自已验证缓存记录的归档信息，判断发生在缓存归档下载及 Gitee 删除、上传之前。超限项不下载归档到同步 runner，不尝试 Gitee 上传。它将仅含 GitHub 地址的 JSON 立即提交并确认后，删除该精确受管身份在 Gitee 的同名旧附件，避免同版本归档跨越阈值后长期占用配额。删除失败保留已确认 JSON，在汇总中报告错误；下次同步即使 JSON 完全相同，也继续尝试旧附件清理，不新增持久化清理队列。未知或歧义附件继续受保护。JSON 变化时该项交付记为仅元数据更新，不能被当作待构建或普通上传；JSON 已相同时可记为 skipped，但仍执行上述旧附件清理。

普通项发生认证、网络、后端或其他容量错误，仍沿用有界重试及明确失败，不因上传出错自动宣称仅 GitHub 交付成功。普通仓库的附件总容量还受平台限制，本轮不增加总容量规划、自动驱逐或失败后改换交付策略。[Gitee 附件限制](https://help.gitee.com/repository/release/create)列出单附件 100M、GVP 200M 及普通仓库总附件 1G 的限制；最后一项独立于本设计的逐附件阈值。

### 同步判断及逐项确认

每项交付按“GitHub 归档和 publication 记录入库确认 → 需要时上传 Gitee 归档 → 提交并确认 Gitee JSON”完成。超限项省略 Gitee 归档上传，仍须在 GitHub 入库确认后提交 JSON。这里的最后提交是每项各自立即执行，不等待全部库或平台完成；importer 继续保留下述入口关联顺序。

源码快照、有效缓存及 Git 元数据仍分别拥有期望身份、合格字节和最后确认的交付状态。同步只比较 Git 中现存 JSON 与本轮生成的期望记录；不下载、探测或重新计算 Gitee 附件摘要。摘要、大小和完整有序 URL 数组都相同才报告 `skipped`，不下载 GitHub 归档、不替换附件、不创建元数据提交。

不完全相同的项进一步决定实际操作，避免把元数据变化一律变成大文件重传：

| 状态 | 操作 |
| --- | --- |
| 本轮只需 GitHub 来源 | 确认期望 JSON，不传输归档；确认后清理该受管身份在 Gitee 的同名旧附件 |
| 本轮需要 Gitee，现存确认记录具有相同摘要、大小及相同 Gitee 地址，仅其他地址或顺序变化 | 只更新 JSON，不重新上传已确认的 Gitee 附件 |
| 本轮需要 Gitee，但上述已确认字节及目标条件不成立 | 下载并校验 GitHub 缓存，删除 Gitee 同名附件后重传，成功后提交 JSON |

缺少 JSON 时没有附件已确认的依据；即使 Gitee 有同名附件，也按上次未成功处理。JSON 的摘要或大小改变时亦然。若原记录只含 GitHub、本轮新增 Gitee 地址，必须先完成实际 Gitee 上传，不能只补写一个未经确认的地址。

每项 JSON 和由该项初始化的 latest 在现有共用 Git 锁内提交并 push，确认后更新内存索引、报告成功并释放依赖者。未确认的 push 停止本轮后续元数据写入，下轮重新读取 Git 判断；不回滚附件，也不伪报成功。仅元数据更新使用同一确认规则。

归档替换先于元数据确认，期间旧 JSON 可能遇到附件缺失或摘要不符；仅 GitHub 项也接受这个窗口。若构建或同步失败，该状态可持续到后续同步完成。元数据提交确认表示本项交付完成，不表示更新过程中旧记录始终可消费。本方案不增加不可变归档、旧字节保留或为消除该窗口而改变自动触发条件。

同步保留无关项并发，以及待更新依赖者等待当前有效依赖及递归闭包确认的规则。依赖可通过完整相同的 JSON 跳过、实际上传完成或仅元数据提交完成来确认；仅有旧摘要、缺少有效缓存或依赖 push 尚未确认都不能释放依赖者。超限依赖的 GitHub JSON 确认后同样可以释放依赖者，不强制其附件位于 Gitee。

importer 实际上传后的入口顺序仍是“工具归档上传 → 主进程唯一入口上传 → 各工具 JSON 确认”。仅修改工具地址记录不触发入口上传。当前 importer 远小于大小阈值；本轮只验收普通 importer 双来源引导，不新增超限工具与入口的另一套关联发布规则。

### 消费下载与失败边界

Go importer 的单地址归档描述改为摘要、大小和地址列表。它在下载前验证完整记录，按 `urls` 顺序逐个尝试，每个来源最多一次，不另加来源内部重试循环。每次使用新的临时文件；换源前关闭并清理本次文件，从零开始。Content-Length 不能替代元数据大小，缺失 Content-Length 不算失败；最多读取 `size + 1` 字节，发现超长立即停止该来源，不等待其结束。实际接收字节必须与 `size` 一致，最终 SHA256 必须匹配。

以下细分错误及恢复规则由 Go importer 实现，不要求 CMake 引导逐项复刻。

| 失败类别 | 行为 |
| --- | --- |
| 连接、DNS、TLS、响应等待或传输超时，非成功 HTTP 状态，响应截断 | 记录当前来源失败，尝试下一地址 |
| 下载完成但大小或 SHA256 不匹配 | 丢弃本次字节，尝试下一地址 |
| JSON、字段或地址非法，缓存身份错误或已有候选损坏 | 直接失败，不切换来源、不覆盖已有缓存 |
| 创建、写入、关闭、清理或提交本地文件失败 | 直接失败；保留可定位的本地错误，不归类为网络问题 |
| 用户取消或父上下文取消 | 结束当前请求并退出，不发起下一来源 |
| 已通过大小和摘要校验后，解包、包内身份、依赖或 adapter 失败 | 报产物或消费失败，不重复下载相同受信字节 |

只有单一来源完全通过字节校验，才交给现有安全解包及包内身份检查；完成后才提交安装目录。完整本地缓存仍直接复用并保持零联网；损坏本地候选不因新增远端来源而被自动覆盖。已有 latest、精确依赖遍历及冲突拒绝保持原规则。

CMake importer 引导读取工具 JSON 的必要字段，按数组顺序调用原生 `file(DOWNLOAD)`，开启 TLS 校验并取得 `STATUS`。下载失败或最终大小、摘要不符时，清理本次临时文件并尝试下一地址；全部失败后统一报错。摘要由下载后显式计算，避免 `EXPECTED_HASH` 在第一个坏来源上直接终止配置。一个来源通过校验后，沿用已有单程序归档检查、安全解包及工具提交；该阶段错误直接失败。

CMake 不依赖 Go 或 Python，不新增错误分类框架、底层 I/O 探测、自定义连接或空闲计时、后台任务、重试退避或下载进度系统。原生命令直接报告的本地错误保持其失败行为，不包装成 Go 下载器的完整错误模型；下载命令内部没有暴露的细分原因不作额外识别承诺。JSON 字段、最终字节及已有归档安全校验仍须保留。

### 超时与进度

超时使用实现内的固定默认值，不增加用户配置入口。Go 库归档下载分别限制连接建立、TLS 握手和响应头等待为 30 秒，响应体连续 60 秒没有实际数据即取消该来源，每个来源的整体下载上限为 3600 秒。总时限覆盖该来源的完整重定向与传输，换源时重新计时；正常持续传输的大包不因原有五分钟总时限而被提前中断。

`net/http.Transport` 没有响应体读取期间的原生空闲超时字段。下载器自行维护响应体计时，在读取到实际数据时重置，并用请求 context 取消中断停顿；不把连接池 `IdleConnTimeout` 当作传输停顿计时。取消必须传到实际请求，关闭响应体并收回计时资源；不为每次 Read 启动协程，不留下后台下载或跨来源延续的计时器。连接、TLS、响应头及请求总时限继续使用标准库接口；[Go HTTP 传输说明](https://pkg.go.dev/net/http#Transport)拥有这些原生字段的语义。

本轮不设最低传输速率，也不承诺慢源快速切换。只要持续收到数据，极低速来源可能用满 3600 秒才换源；有序换源处理来源失败，不能保证选到最快来源。需要较短首来源预算或低速判定时，另行确定策略，不暗中加入测速或竞速。

CMake 只引导体积较小的工具归档，使用原生 `INACTIVITY_TIMEOUT 60` 和 `TIMEOUT 300`，每个来源分别计时；不承诺原生接口未提供的独立连接时限。源码现有最低 CMake 要求不变，不为本设计测试或安装旧 CMake。[CMake 下载参数](https://cmake.org/cmake/help/v3.20/command/file.html#transfer)定义空闲与总体超时，本文不以新版本独有选项实施引导。

包下载进度使用 JSON 中的大小，显示当前来源及尝试序号；换源时显示上一来源失败类别，并将本次下载进度从零计算，不把多次尝试字节累加为成功进度。全部地址失败时，错误列出包或工具身份、已尝试来源及原因，不输出令牌或临时重定向查询参数。成功使用备用来源时仍正常完成消费，不把一次来源失败当作整体失败。

入口和工具获取保持现有安静的成功路径；发生工具换源或最终失败时才输出必要诊断。成功导入的 `[Info]` 信息保持原约定，完整缓存复用不增加下载日志。

### 汇总及清理

同步汇总明确区分 `uploaded`、`metadata_only`、`skipped`、`failed` 和依赖阻断。`metadata_only` 附带 `gitee_size_limit` 或 `delivery_metadata_changed` 原因；超限日志包含归档名、实际字节、阈值和仅 GitHub 交付。`uploaded` 仅计真实完成附件及元数据确认的项，不把超限项计入上传数量。

配方、版本或平台身份从源码删除时，继续删除 GitHub 缓存归档与 publication 记录、Gitee 同名附件及对应 JSON，并修复或删除悬空 latest。源码身份仍存在时，保留有效的 GitHub-only JSON；源码身份明确删除时，无论 Gitee 是否存在附件，都删除对应 JSON。GitHub-only JSON 同样证明受管身份。清理 Gitee 无摘要残留前保留 GitHub 归属证据的顺序继续适用；缓存失效但源码仍存在时保留最后确认交付，不把失效当作删除授权。

latest 保持源码合法性规则，不增加全平台齐备条件。依赖先确认不提供同版本整组 ABI 原子切换，双来源也不改变此限制。

### 首次运行前提及执行边界

项目没有旧用户，本轮不实现裸 SHA256 与 JSON 双读、旧 importer 识别或自动升级、旧入口兼容、历史记录转换，也不增加长期维护的迁移 workflow。新代码只支持 JSON；真实验收使用新入口、新 importer 和独立消费根。

首次运行使用没有旧协议数据的专用 Gitee 发布仓库；查询明确返回 404 时，沿用现有自动建库和初始化能力，以 schema 2 创建元数据。只做一次的旧库重置、旧流程停止及公开设置属于执行准备，不实现迁移或重置功能，也不维护旧记录转换规则。新建仓库仍默认私有，匿名消费以仓库公开为前提。

独立同步从有效缓存逐项建立 JSON 及 latest。普通项因没有确认记录而执行实际 Gitee 上传；超限项只登记 GitHub 地址。更新后的 importer 需要在相应原生平台构建验证并入库；它与入口的代码改变沿现有工具指纹失效规则处理。库的归档和安装协议未变，不能仅为交付 JSON 或同步逻辑变化而让全部库缓存失效；保持生产指纹及真实输入边界。

该切换允许元数据从空集逐项恢复，不要求某次构建一次完成全部平台和库。多 run 累积的有效库缓存可继续使用；新 importer 尚未入库的平台列为缺口，不伪报四平台消费可用。没有旧用户，不维护切换期间的旧远端消费可用性，也不要求 Gitee 元数据与唯一入口原子切换。

本轮按一个完整协议改动进行本地实现和受控验收，生产与两种消费者配套完成后再进行远端切换验收，不发布单边格式。开发及验证遵循[开发指南](../../../development.md)与[测试指南](../../../testing.md)：仓库管理的 Go SDK、`build/` 下隔离源码及缓存、编译最多四线程。设计草案本身不执行远端清空、push、CI 触发或发布；后续执行计划明确本地和远端阶段及相应授权范围。

## 备选方案

**同步端生成完整地址，消费者按序尝试。** 采用此方案。托管目标、大小策略及 URL 编码由交付方统一决定，消费者只执行同一条记录，超限包无需例外的消费逻辑。

**JSON 仅保存可选 GitHub 地址，消费者继续拼接 Gitee 地址。** 可以少存一个地址，但需要 CMake 和 Go 继续维护目标拼接和超限特例；记录无法独立表达来源顺序，目标改变还会影响消费者代码，不采用。

**运行时探测托管 API，或在同步失败后临时发现其他附件。** 可以从平台动态查询，但增加匿名限流、平台耦合和失败路径，不能满足只用 Git 索引及预先确定来源的要求，不采用。

**保留旧摘要和新 JSON 并逐步迁移。** 会增加双格式生产、解析、跳过和清理规则。项目当前没有用户，受控清空后重建即可达到目标，因此不承担该兼容维护成本。

## 验收标准

本地验证从真实入口和可观察结果出发，覆盖修改的所属测试及直接受影响接口，复用未失效的平台证据，不为 JSON 协议重编无关第三方库。

1. Python 生产和树校验、CMake 工具引导及 Go 包选择使用同一 JSON 格式；有效大小、地址顺序及身份能通过真实路径读取。非法字段、摘要、大小和地址在归档请求前失败；不再把 `.sha256` 当作受支持记录。
2. 以轻量归档验证普通 `[Gitee, GitHub]` 和超限 `[GitHub]` 的实际消费。精确阈值以下、等于及以上的同步判断可定向验证，超限项没有归档下载或 Gitee 上传请求。旧同名受管附件只在 JSON push 确认后删除；删除失败报告错误，相同 JSON 的下次同步仍重试清理。
3. 完整相同 JSON 的重同步没有归档传输或元数据提交；仅 URL 变化且 Gitee 字节已确认时只提交 JSON；从仅 GitHub 改为需要 Gitee 时必须真实上传。普通附件及其 JSON、唯一入口及工具 JSON 的失败后重试保持已有语义。
4. CMake 通过简单的原生下载循环，Go 通过所属下载器，在首来源 HTTP、传输截断及字节校验失败后成功使用第二来源；全部失败时诊断可定位来源。Go 的持续传输不受旧五分钟总时限误杀，超长响应在读取至 `size + 1` 后停止；空闲、总超时和取消用缩短的测试时限验证实际请求终止，不用长时间等待来构造测试。CMake 只验证原生下载、大小摘要校验及来源切换，不增加同等错误分类或计时夹具。
5. Go 本地磁盘写入、文件关闭或提交失败不触发第二次网络尝试；两种消费者遇到有效摘要下的坏归档或身份错误均不换源。已有缓存不变，失败尝试没有可被后续误认为完成的包或工具，重复完整消费及缓存搬迁后离线消费继续成立。
6. 使用受控 Git/TLS、实际同步 CLI、生产归档及独立消费者完成一次闭环：正常项上传、超限项仅元数据、依赖确认、重复跳过、源码版本或平台删除、JSON 清理及 latest 修复。一次失败不阻断无关项，未确认 push 不释放依赖者。
7. 远端阶段从干净的目标状态验证自动建库、schema 2 初始化及逐项交付，记录实际目标、Git 提交及汇总；使用新 Windows importer、普通代表库和实际 PCL 缓存消费。PCL 只登记 GitHub 地址且不尝试 Gitee 上传，独立空消费根能完成下载、校验和包准备；真正的 CMake 链接运行另按对应 smoke 的可用范围记录，不能以仅下载成功替代。
8. 若 Gitee 元数据仓库尚未公开，只能报告有授权访问的验证，不能声称匿名端到端通过。四平台消费者中未实际执行的平台列为缺口；文档和 Agent Notes 校验通过后才交付阶段验收。

## 风险

元数据和独立入口仍依赖 Gitee，双来源仅覆盖归档下载；Gitee Git 无法取得时无法首次准备缺失包。完整本地缓存仍可离线复用。本设计不新增元数据镜像或入口双来源。

GitHub 固定缓存 tag 的同名附件可被后续构建替换或源码清理删除，JSON 中的逻辑 URL 不保证长期指向旧字节。同步前后或消费者固定旧 Git 快照时，某个来源可能已不匹配旧摘要；消费者必须拒绝错误字节并尝试下一来源，所有来源均变化时明确失败。更新期间及失败后到下次同步前的暂时不可下载是已接受的交付边界，包含仅 GitHub 的包；不新增不可变代际归档或旧字节保留要求。

普通 Gitee 附件总容量和平台服务行为可能造成阈值以下的项仍上传失败。当前按失败诊断及重跑处理，不将其伪报为超限项成功；需要总容量分配或按平台错误自动降为仅 GitHub 时，应另行确认行为。

新协议不支持旧工具或旧入口；当前没有用户而接受该代价。现有本地数据不批量覆盖，不提供自动修复或升级旧消费者的承诺。专用旧发布仓库的重置属于一次性准备，其数据影响由具体执行清单说明；正常同步不因此获得自动删库或重置仓库的能力。

大小和 SHA256 只保证下载字节与受信 Git 记录一致，不能认证发布者或保证 ABI 兼容。元数据仓库、工具及包内 CMake 仍必须可信，来源切换不会放宽归档安全、身份校验或平台约束。
